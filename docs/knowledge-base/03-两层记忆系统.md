# 两层记忆系统（Short-term / Long-term）

**最后更新**：2026-09-11

## 解决什么问题

LLM 无状态，而招聘对话会跨天、跨咨询持续。系统不把全部历史无限塞进 prompt，而是按作用域分成短期和长期两层；工作记忆与 episodic 摘要是层内结构或计算产物，不是额外存储层。

## 两层与三个 7 天

| 作用域              | 内容                                    | 存储                           | 边界                                                                              |
| ------------------- | --------------------------------------- | ------------------------------ | --------------------------------------------------------------------------------- |
| Short-term 消息窗口 | 原始对话窗口                            | `chat_messages` + Redis 热缓存 | 通常从本批之前候选人最后一次开口往前滚动回看 7 天；300 条与字符预算才是物理硬上限 |
| Short-term 会话状态 | facts、岗位工作台、阶段指针             | Redis `factsv2:*` / `stage:*`  | 7 天；facts 另加 12 小时沉淀读取余量                                              |
| Long-term 关系档    | profile、job intent、episodic summaries | Supabase + Redis 2 小时缓存    | 候选人 × bot 的持久关系                                                           |

固定业务口径是 **7d / 7d / 7d**：消息回看 7 天、会话状态 7 天、连续闲置 7 天后划分咨询段并触发 consolidation。三个数字表达不同边界，不能互相替代：消息窗口决定模型能看到多少原文，会话 TTL 决定 Redis 工作状态能否继续，沉淀间隙决定何时把一段咨询结算到长期记忆。

消息窗口的 7 天是锚点回看口径，不是绝对时间硬上界。锚点会随连续未获回复的候选人消息后移；首次咨询找不到更早候选人开口时不按时间裁剪，因此窗口跨度可能超过 7 天，最终仍由 300 条硬上限和字符预算封顶。

`factsv2:*` 的物理 TTL 是会话事实 7 天再加 12 小时。额外 12 小时只保证 delayed consolidation 在业务边界到达后仍能读取事实，不延长会话，也不改变 7 天的咨询段口径。收资表单同样保留 7 天，但它是独立业务单据，详见 [[19-收资与预约事务状态机]]。

`turnHints` 只活在当前轮，是规则识别 sidecar；episode 只是消息裁剪和沉淀的计算边界。两者都没有独立存储层。

## 统一召回与 Prompt 消费

`MemoryService.onTurnStart()` 并行取得消息窗口、会话状态、阶段和当前候选人 × bot 的长期关系档，返回 `MemoryRecallContext`。Preparation 随后补齐 snapshot、计算共享裁决视图，再由 memory、turn-hints、hard-constraints 等 sections 消费。

同字段冲突遵循档案域宪法：本轮 accepted > session accepted > profile historical_unconfirmed；置信度只在同作用域内比较。模型可见的 `[会话记忆]`、`[用户档案]`、`[本轮解析线索]` 标签保持稳定。

## Short-term 当前存储契约

`factsv2:{corpId}:{userId}:{sessionId}` 是唯一会话状态 key。它使用 Redis hash，每个 `WeworkSessionState` 顶层成员占一个 hash field；写路径只 `HSET` patch 中出现的成员，避免无关状态互相覆盖。`facts.brand` 由 `BrandStateService` reducer 独占写入，阶段指针使用独立的 `stage:*` key。

读边界逐 hash field 做 schema 校验。一个字段损坏时只丢弃该字段，其余状态仍可使用；丢弃同时写执行事件并触发节流告警，观测数据只带字段路径和校验原因，不带候选人原值。运行时不读取 `facts:*` 单 blob，也不执行读时合并或惰性搬迁。

普通事实以 `{ value, confidence, source, evidence, extractedAt? }` 信封持久化。`source` 只接受 `candidate_quote / rule / model / system / manual / archive` 六种生产者；裸标量不是可持久化事实。`preferences` 允许 `value:null` 信封作为显式清空墓碑，避免旧值在后续合并中复活。

岗位候选池、已展示岗位、当前焦点岗位和查询签名属于 short-term workbench。它们与 facts 同属会话工作状态，不形成新的记忆层。

## 地理偏好的城市一致性

城市一旦由候选人明示、定位或可信地理解析确权，所有偏好写入都会在合并后执行 `pruneGeoPreferencesForCity()`：

- district/location 能由白名单确定性反推出另一座城市时删除；
- 无法反推城市的值保留，代码不猜地点归属；
- 当前没有城市事实时不做剪枝；
- 某组值被全部删除时写入 `value:null` 墓碑，并在 evidence 中记录移除原因。

文本扫描只把全国区县完整名称纳入通用词典匹配；镇和街道仅在紧随已命中区县时识别。这个边界防止自由正则把相邻文字吞成伪区县，同时保留白名单外地点供后续地理编码或模型澄清。

## Long-term 当前存储契约

长期关系档以 `(corpId, userId, botUserId)` 隔离。只有事实写入、预约办结和 consolidation 等有实际内容的路径创建或更新关系档；消息读取与回合开始不会为了记录元数据预建空行。

- `semantic_profile`：身份档案，逐字段置信度守卫合并；
- `semantic_job_intent`：最新咨询段的意向快照，整组覆盖；
- `episodic_session_summaries`：裸 `SummaryEntry[]`，每段求职咨询追加一条，最多 20 条；
- `consolidation_watermarks`：独立水位对象，记录各 session 已结算到哪条消息，不属于记忆内容。

长期事实沿用同一组六种 producer。读边界只接受上述规范形态并对摘要做 20 段封顶，不在读取过程中写回或修正数据库。

## Consolidation 的范围与水位

每个回合结束会刷新约 7 天后的 delayed job。任务到点后先以 `chat_messages` 的最新消息时间复核闲置边界，再从持久水位之后分页读取当前咨询段。

摘要模型首行输出 `范围：求职` 或 `范围：非求职`，正文统一为“求职目标、关键约束、进展与结果、未决事项”四节纯文本。格式归一发生在写入前，已写摘要不再交给 LLM 二次压缩。

结算顺序保持以下不变量：

1. 长期事实先写；重复执行为覆盖式幂等写。
2. `范围：非求职` 的段落不占用经历摘要额度，但仍推进 session 水位。
3. 范围标记缺失或无法识别时按求职段处理，保持对现有求职对话的宽容。
4. 摘要正文为空时任务失败，不推进为一条无内容经历。
5. 求职摘要追加与对应水位推进由长期记忆写路径绑定，最多保留最近 20 段。

## 数据库发布边界

应用代码假定长期记忆表已经满足规范 schema。仓库中的 `supabase/migrations/20260911120000_flatten_legacy_long_term_shapes.sql` 负责建立摘要裸数组、独立水位和 producer 规范值等前置条件；运行时没有惰性迁移兜底。

因此发布流程必须应用并验证该迁移后，再以当前读边界作为有效契约。文档和代码仓库只能说明迁移要求，不能证明任一环境已经执行；环境状态应通过迁移台账和数据库查询单独核验。

## 设计权衡

- 结构化招聘事实字段可枚举、需要审计，schema 化状态比默认引入记忆 RAG 更可靠。
- 消息窗口、会话 TTL 与沉淀间隙分别控制召回、工作状态和结算，统一为 7 天仍保持职责分离。
- profile、意向和经历采用不同写法：事实越证越硬，意向以新为准，经历只增不改。
- 收资表单是业务单据，归 `src/tools/collection/`，不属于记忆层。
