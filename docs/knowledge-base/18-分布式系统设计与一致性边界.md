# Cake Agent 的分布式系统设计与一致性边界

> 最后更新：2026-09-11。依据仓库代码与部署配置核对；不代表已核验线上实例数或做过多副本故障演练。

## 结论：单体应用中有明确的分布式协调设计

Cake Agent 是 NestJS 模块化单体，消息队列、共享状态、持久化与外部投递分别跨越 Redis、Supabase/Postgres、企微托管平台等网络边界。从整个业务系统看，它是分布式应用；从应用打包方式看，它仍然是单体。这两个判断并不矛盾，微服务也不是分布式系统的必要条件。

关键证据不是“用了 Redis”，而是代码显式处理了重复回调、并发消费者、租约过期、任务重放、并发写入和外部投递结果不明等问题。即使只运行一个应用实例，进程重启、异步任务交错和跨服务部分失败也会触发这些问题。

但应区分三个层次：

| 层次 | 当前可以确认的事实 | 不能据此推导的结论 |
| --- | --- | --- |
| 部署配置 | `docker-compose.yml` 定义一个 `cake-agent` 服务，固定容器名与宿主端口 | 不能证明生产已经运行多个应用副本；原配置不能直接用于同机多副本扩容 |
| 协调机制 | 共享 Redis 去重、per-chat 租约锁、Bull 恢复、数据库原子 RPC | 不能证明所有业务入口、定时任务和外部副作用都已具备多副本安全 |
| 故障保证 | 已实现有限重试、未确认消息保留、幂等水位和投递状态记录 | 不能承诺端到端 exactly-once、无限期不丢消息或任意故障下的高可用 |

`restart: always` 是进程恢复配置；优雅停机是重启时保护在途任务的机制。二者都不是滚动发布、多副本部署或零停机的证据。更稳妥的介绍是：**具备共享状态协调和故障恢复机制的 Agent 单体应用，部分核心链路为多消费者并发提供了基础。**

## 一条消息跨越哪些一致性边界

```text
企微回调
  → messageId 原子 claim（Redis，有限 TTL）
  → pending 消息列表 + Bull delayed job（共享 Redis）
  → Worker 领取 job，竞争 chatId 租约锁
  → 静默窗口检查 → pending 快照（此时不删除）
  → Agent 推理、工具调用、外部投递
  → 上报投递结局、标记消息、ack 已消费 pending
  → 等待 TurnFinalizer.whenSettled()
  → 停止心跳、按 owner 释放 chat 锁

短期事实：Redis hash 字段级写入
长期沉淀：Postgres 行锁 + 水位检查 + 原子追加摘要
收资预约：候选人 × 岗位表单 + precheck 早期查重 + booking 提交前查重
复聊投递：独立的触达槽与 outbox 状态机
```

这是一串局部协调步骤，不是一笔横跨 Redis、Postgres 和企微平台的事务。理解设计时，要逐段问：谁持有执行权、数据何时确认、失败后谁再触发、重复执行会产生什么效果？

## 1. 执行权：Bull job 锁与 per-chat 锁保护不同对象

Bull 负责队列任务的领取和 stalled 恢复；业务侧 `SimpleMergeService.acquireProcessingLock()` 则以 `chatId` 为粒度使用 `SET NX EX` 抢锁。多个不同 job 可以指向同一聊天，所以仅有 job 锁不足以保护聊天状态。

`MessageProcessor.handleProcessJob()` 为本次执行构造 `job:${job.id}:${Date.now()}` owner token。持锁期间定时续租；续租和释放都通过 Lua 原子比较 owner 后再执行 `EXPIRE` 或 `DEL`，避免旧持有者误续租、误删新持有者的锁。

锁冲突并非直接结束恢复链路：`scheduleLockRetryCheck()` 续期 pending 并按时间桶补建重检任务。静默窗口未结束也会显式补建下一次检查。具体时长与聚合策略见 [[02-消息debounce聚合与租约锁]]，本篇关注它们共同维护的条件：**数据仍保留，而且未来还有任务来检查它。**

**保证边界：owner token 不等于 fencing token。** 当前 `startLockHeartbeat()` 遇到锁过期、易主或 Redis 异常只记日志，没有因此中止旧 Worker，也没有让数据库或投递端拒绝旧持有者的写入。若进程暂停超过租约，另一 Worker 获锁后，旧 Worker 恢复仍可能继续产生副作用。因此，这是一种有条件的互斥机制，不能表述为任意网络分区或长暂停下都严格串行。

## 2. 故障恢复：保留快照、确认消费、显式再触发

`claimPendingSnapshot()` 读取 pending 快照而不清空；工作流在处理到可确认的路径后调用 `ackPendingMessages()`，按已消费数量裁掉列表前缀，保留执行期间追加的新消息。进程若在 ack 前退出，后续任务仍有机会读取原消息。暂停托管等终止路径也可能明确 ack，所以 ack 表示该批消息已被消费，不等同于一定向用户发送了回复。

这使重放成为可行的恢复手段，同时引入重复副作用窗口：外部平台已发送成功，但本地尚未 ack 就崩溃，恢复后可能再次执行。Bull 的 stalled 恢复解决“任务可能再跑”，不解决“外部动作只生效一次”。当前应按**任务可能重复执行**来设计，不能从队列重试推导端到端 exactly-once。

`MessageProcessor.onModuleDestroy()` 关闭队列并有界等待在途任务；`main.ts` 开启 shutdown hooks。实际能否排空还取决于部署平台的强杀宽限是否覆盖应用等待时间。pending 有 TTL、任务有重试次数，Redis 或消费者长时间不可用时，不能保证消息无限期保留和自动恢复。

另一个边界是“确认操作自身的重试”：当前 ack 使用 `LTRIM`，如果 Redis 已执行而客户端丢失响应，再按相同数量裁剪可能影响后续数据。保留快照减少了提前删除造成的丢失窗口，但不能将所有网络失败都转换为安全重试。

## 3. 幂等：每一层都需要自己的业务标识

| 层次 | 实现与幂等依据 | 实际保护范围 |
| --- | --- | --- |
| 回调入口 | `AcceptInboundMessageService` 调用 `markMessageAsProcessedAsync()`，按 `messageId` 原子 claim | TTL 内重复回调只有一个能继续；claim 不是业务处理成功凭证 |
| 同聊天执行 | `chatId` 租约锁与 owner 校验 | 协调执行顺序，本身不对外部副作用去重 |
| 长期记忆 | `consolidation_watermarks.bySession[sessionId]` | 已覆盖的消息时间边界不再次追加摘要 |
| 预约提交 | 候选人级 active booking + 同岗位时间窗判重 | precheck 提前阻止重复收资，booking 在外部提交前再次封闭并发窗口；追加候选人另行隔离 |
| 复聊触达 | `${sessionId}:${scenarioCode}:${anchorEventId}` 触达槽 | 区分已发送、处理中与结果不明；受槽 TTL 和渠道能力约束 |

入口 claim 与后续入队不是一个原子事务。claim 后、可靠入队前如果失败，重复回调可能在 TTL 内被拦住；TTL 到期后，原消息又可能被重新接纳。因此“Redis 原子去重”只说明这一条 claim 的竞争安全，不等于完整的可靠收件箱协议。

长期记忆的关键不只是应用层先查水位。`append_long_term_summary_atomic` 在数据库行锁下再次比较会话水位，同一事务内更新摘要和水位，挡住两个任务同时通过应用层检查后的重复追加。数据库写入幂等也不意味着前面的 LLM 摘要计算只会执行一次。

复聊的 `TouchLedgerService` 使用 `reserved → delivery_attempted → sent / failed / unknown` 状态机。进入外部发送区间后，失败响应不总能说明“没发出去”；`unknown` 保留这种不确定性，需要核对或补偿，不能盲目重投。它是 Redis 中的投递底账，不是与 Postgres 业务事务绑定的传统 transactional outbox。详细流程见 [[09-复聊独立生成链路]] 和 [二次主动回复流水线](../architecture/reengagement-pipeline.md)。

## 4. 一致性：缩小冲突范围，再明确提交边界

**聊天内的收尾顺序。** `ReplyWorkflowService` 在 `finally` 中等待 `turnFinalizer.whenSettled()`，然后才返回给 Processor 释放锁。否则上一轮的异步记忆写入可能在下一轮开始后才完成。这里的“结算”是应用内副作用收尾协议，不是数据库两阶段提交；其串行效果也依赖租约仍然有效。见 [[06-Agent回合编排与TurnFinalizer]]。

**短期 Facts 的写入粒度。** Redis hash 只写变更字段，减少整份 JSON 读改写导致的跨字段覆盖；同一字段的并发更新仍需接受或另行处理冲突。字段级写入也不会让“先读、业务合并、再写”的整个流程自动成为事务。见 [[04-Facts并发安全与字段级写入]]。

**收资与预约的提交边界。** 收资表单按候选人与岗位隔离，主候选人与当前代办候选人使用不同指针；表单整实体写依赖同一聊天的租约串行，不具备跨聊天 CAS。候选人级 active booking 则跨托管账号共享：precheck 用它提前返回已有预约，booking 在真正调用外部接口前用同一判据复核。前者改善交互并减少无效收资，后者才是靠近不可回滚副作用的最终竞态保护。见 [[19-收资与预约事务状态机]]。

**长期摘要的原子边界。** Postgres RPC 将摘要追加与水位推进放在同一事务，避免只写摘要未写水位造成重复沉淀，或只推水位未写摘要造成遗漏。这种原子性仅覆盖该数据库操作，不延伸到 Redis 缓存、LLM 请求或外部投递。见 [[03-两层记忆系统]]、[[15-数据库工程实践]]。

## 5. 如何评估是否可以扩成多个应用副本

以下是扩容前需要验证的条件，不是已经完成的能力声明：

- **部署与路由**：调整固定容器名、端口和流量入口，确认所有消费者使用相同业务命名空间；测试与生产必须隔离。
- **执行权与副作用**：枚举主消息、复聊、群任务、cron 等入口，逐一核对锁作用域；注入租约过期与旧 Worker 恢复场景，验证如何阻止过期执行者写入或发送。
- **进程内状态**：检查本地缓存、并发信号量、限流器和定时器；单实例额度不会自动成为全局额度，多副本也可能放大数据库、LLM 和渠道负载。
- **恢复链路**：覆盖 claim 后入队前、发送后 ack 前、Redis 已执行但响应丢失、数据库提交后客户端超时、停机超时等窗口；检查既不会静默遗留数据，也不会无界重试。
- **状态基础设施**：确认 Redis 的持久化与故障切换语义、数据库容量、队列积压和 TTL 的关系；共享存储不是天然无限容量或无故障的协调层。

## 学习要点

1. **先定义不变量，再挑组件。** 同聊天避免回合交错、已沉淀边界不重复追加、外部发送未知不能当作未发送，这些约束比“用 Redis/Bull”更能解释设计。
2. **互斥、幂等、原子性和恢复是不同能力。** 锁约束谁执行，幂等约束重试效果，事务约束一起提交什么，补建任务约束失败后谁再触发；它们相互配合，不能互相替代。
3. **区分安全性与活性。** owner 校验防止误操作别人的锁；TTL 与重检让崩溃后有机会继续。两者都需要，并且都有成立条件。
4. **外部副作用存在结果不明窗口。** 状态机显式保留 unknown，比把所有超时当作失败重试更贴近真实故障模型。
5. **描述能力要带证据边界。** 可以说已有分布式协调设计；“已多副本部署”“可无条件水平扩展”“不丢不重”需要部署观测和故障验证支持。
