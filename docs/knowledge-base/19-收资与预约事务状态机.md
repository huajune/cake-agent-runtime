# 收资与预约事务状态机

**最后更新**：2026-09-11

## 解决什么问题

报名不是一组可随意拼进 prompt 的事实，而是一笔“候选人 × 岗位”的有状态业务办理。系统必须知道当前在替谁报名、使用哪一版岗位契约、哪些值有候选人出处、资料和时间是否获准提交，以及外部工单是否已经存在。

收资表单是这条链路的事务底稿和唯一报名写入权威。记忆保存对人的持续认知，不能替代表单的岗位契约、槽位状态、复述授权或工单终态。

## 实体、作用域与存储

`BookingCollectionForm` 按 `{corpId, userId, botUserId, candidateRef, jobId}` 隔离，并以整实体 JSON 快照保存在 Redis：

- `candidateRef`：手机号未知时为 `session`，取得候选人本人 11 位手机号后 rebind；
- `candidateScope`：同一会话代朋友或家人报名时标为 `additional`；
- `contractSnapshot.fields`：本张表单用于校验和提交的完整岗位契约，包括字段、选项及顺序；
- `slots[labelId]`：`empty | filled | disqualified`，filled 值带规范值、出处和 producer；
- `scheduleDraft`：独立保存候选人选择的日期或精确面试时间，不伪装成收资字段；
- `workOrderId / escalatedReason / lastRecap`：保存不能由槽位重新推导的办理事实；
- `verdictOf()`：从实体即时推导 `collecting | disqualified | ready | escalated | submitted`，不重复落盘总评。

表单 key 为 `collection-form:{corpId}:{userId}:{botUserId}:{candidateRef}:{jobId}`，TTL 7 天。整实体覆盖写依赖同一 chat 的 90 秒心跳租约维持单写者，不使用 CAS。契约快照、槽位、时间草稿与授权记录必须在同一快照内保持一致。

## 主候选人与追加候选人

系统为每个会话和岗位维护两个定位指针：

- `collection-form-primary:*` 指向当前聊天联系人的主表单；
- `collection-form-current:*` 指向最近一次通过 precheck 推进、供 booking 消费的活动表单。

追加候选人可以短暂成为活动表单，但不能覆盖主表单指针。`candidatePhone` 只有在本轮候选人原话中可回查时才参与路由；多人办理必须逐人完成 `precheck → booking`，不能并行推进多张表。

`additional` 表单可以独立提交外部报名，但不得把其姓名、手机号、年龄等写入当前联系人的 session facts、长期画像或 active booking。这样朋友或家人的资料不会污染聊天联系人的身份与预约状态。

## 主流程

```text
候选人消息
  |
  +-- 本轮没有报名答案 -> precheck(mode=query)
  |                         取实时契约与时段、刷新 contractSnapshot
  |                         不消费候选人文本或字段提案
  |
  +-- 本轮已有答案/确认 -> precheck(mode=validate)
                            首次办理：同次建立 contractSnapshot
                            契约漂移：contract_changed -> query 刷新后重投有出处答案
                            公证提案 -> 写 slots / scheduleDraft
                                      |
                                      v
                              持久化表单并派生动作
                                |-- 表单已 submitted -> already_submitted
                                |-- 在途同岗工单命中 -> already_booked
                                |-- empty 槽仍存在 -> collect_fields
                                |-- 硬筛选命中 -> screening_rejected
                                |-- 熔断/配置异常 -> handoff
                                |-- 年龄位于弹性带 -> age_boundary_handoff
                                |-- ready 且需确认 -> confirm_collection
                                |-- 已授权但时间未定 -> select_interview_time
                                +-- 资料和时间均授权 -> ready_to_book
                                                           |
                                                           v
                                     booking 再查 active booking
                                       |-- 命中 -> already_booked
                                       +-- 未命中 -> 调外部报名接口
                                             |-- 成功 -> submitted + workOrderId
                                             +-- errorList -> 精确重开对应槽位
```

## Query 与 Validate 协议

`duliday_interview_precheck` 必须显式传 `mode`：

- `query` 用于查询或刷新岗位报名表和可约时段。它可带 `candidatePhone`、`requestedDate`，但不能带 `fieldValueProposals` 或 `recapConfirmation`，也不把当前聊天文本送入字段 intake。
- `validate` 用于校验本轮报名资料，必须携带非空 `fieldValueProposals` 或 `recapConfirmation=true`。新表单在同一次调用中建立实时契约快照并立即校验，不要求预先空跑 query。

validate 始终消费持久化快照。实时契约与快照不完全相等时返回 `contract_changed`；随后 query 按新契约对齐槽位：新增槽位建立为空，删除槽位移除，同 `labelId` 定义发生变化时重开该槽，未变化槽位保留，同时作废旧 recap。候选人已经给出的答案，只能在新契约仍支持且原话仍可回查时重投。

## 先筛后收与证据边界

所有候选人答案都经统一提案、公证和槽位写入链路。`labelTitle` 只定位实时契约已有槽位，`quote/sourceText` 必须能在可信候选人消息中回查，规范值还要通过身份形态、契约词表和确定性冲突检查。

档案预填只填空槽，并先经过当前岗位的词表和值域筛选。无法适配本岗的历史值保持槽位为空，由候选人重新回答；历史档案不能直接把候选人判为不合格。预填成功的值标记 `producer=archive`，并在提交前向候选人复述求证。

筛选结果遵循两档边界：

- 命中 `rejectedOptions` 或硬越界时，只有本轮候选人证据可以把槽位置为 `disqualified`；
- 年龄落入允许人工裁量、但外部报名接口按硬区间必拒的弹性带时，表单保留已收资料并返回 `age_boundary_handoff`，禁止调用 booking。

确定性代码只校验封闭词表、数值范围和出处，不用开放正则猜社保等长尾语义。模型负责提出契约规范值，notary 负责证明该值有候选人依据。

## Recap 与提交授权

`needsRecap()` 只在 ready 表单含 `archive / system / manual` 外部预填值时成立。候选人原话、规则或模型提案只要已经过公证，不额外制造复述环节。

需要 recap 时，系统从当前槽位渲染 `lastRecap`。任一槽位纠正、清除、契约变化或外部 `errorList` 重开都会使旧 recap 失效。候选人明确确认后，模型以 `recapConfirmation=true` 调用 validate；notary 自动绑定最新候选人回复与此前真实送达的官方复述，模型不复制确认原话。

授权分两层：

1. `isCollectionAuthorized()` 要求表单为 ready，且外部预填不存在或当前 recap 已确认。
2. `isSubmissionAuthorized()` 在资料授权之上，再要求 wait-notice 岗位无需具体时间，或非 wait-notice 岗位的持久草稿与本轮实时可约时段一致。

只有 precheck 返回 `ready_to_book`，booking 才能继续。候选人资料未齐、recap 未确认或精确时段未获授权时，都不能以模型文字承诺代替状态机凭据。

## Already Booked 的双闸

active booking 是当前聊天候选人级状态，作用域为 `(corpId, userId)`，可跨托管账号发现同一候选人的近期工单。precheck 与 booking 共用 `findRecentSameJobBooking()`：

- 查重窗口为 30 分钟；
- `job_id` 与当前岗位相同即命中；active booking 条目没有 `job_id` 时也按命中处理，先核对真实工单；
- `additional` 表单不读取当前联系人的 active booking；
- 表单自己的 `submitted` 终态优先，因为它持有精确 `workOrderId`。

precheck 在派生后续动作前做第一道查重，命中后返回 `duplicateBookingGuard`，停止重复收资、选时间和 booking。booking 在通过资料与时间授权后、调用外部接口前再次执行同一判据，覆盖两个步骤之间另一账号刚创建工单的竞态窗口。

`already_booked` 的业务语义是“预约已经存在，本次没有重复提交”。回执应提供已有 `workOrderId`，有登记时间时同时提供 `interview_time`；Agent 必须如实告知已约上，不能描述为系统失败或承诺稍后重试。改时间和取消分别使用对应工单工具。

两道应用侧闸门减少重复提交并改善用户体验，但不构成跨 Redis、数据库与外部报名接口的全局事务；外部系统的幂等与查重仍是最终事实边界。

## 提交闭环

booking payload 只由已公证表单生成：`{ jobId, interviewTime?, labelList[{labelId, optionCodes|value}] }`。模型不能旁路传入姓名、手机号或补充字段。

外部提交成功并返回 `workOrderId` 后，表单进入 submitted；主候选人分别写 active booking、session facts 和长期身份档案，其中 active booking 保留 `job_id` 与 `interview_time`。这些后置写入不与外部报名构成全局事务，单项失败会记录而不会否认已经存在的外部工单。成功但缺少 `workOrderId` 时，booking 先把表单标记为 escalated 以阻止重复提交；后续 precheck 返回 handoff 并要求调用 `request_handoff`。接口返回 `errorList` 时优先按 `labelId`、缺失时按唯一 `labelTitle` 精确重开对应槽位；无法映射错误字段时同样标记 escalated，由后续 precheck 收敛到 handoff，不让表单静默卡在 ready。

## 关键不变量

- 一张表只代表一个候选人、一个岗位、一个托管账号；手机号到达后 rebind，不复制进度。
- 校验和提交只消费同一份持久化契约快照；契约漂移必须显式刷新。
- filled 值必须有可信出处；历史档案可预填求证，不能直接筛退。
- `verdict`、资料授权和提交授权均由当前实体派生，不另存容易漂移的布尔标记。
- 追加候选人的资料、画像和 active booking 与当前联系人隔离。
- precheck 提供早期查重回执，booking 守住外部副作用前的最终应用闸门。
- `submitted` 与 `workOrderId` 是办结事实；`already_booked` 是已有预约，不是失败。
- 表单 key 丢失会导致重复询问，属于业务事故，不按普通缓存 miss 处理。
