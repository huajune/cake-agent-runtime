# 多模型三层容错架构（Registry → Reliable → Router）

## 解决什么问题

生产 Agent 依赖多家 LLM 厂商（Anthropic/OpenAI/OpenRouter 等），任何单一厂商都会出现限流、超时、宕机。不能让一次 API 抖动直接变成候选人收不到回复。同时不同任务对模型的"智力/成本/延迟"要求不同，不该所有场景都用最贵的模型。

## 三层设计

```
Layer 1: RegistryService   — 注册（Vercel AI SDK createProviderRegistry 统一多厂商）
Layer 2: ReliableService   — 容错（错误分类 + 指数退避重试 + fallback 降级链）
Layer 3: RouterService     — 路由（按"角色"而非按"模型"编程）
```

### Layer 2 容错的具体算法（`src/providers/reliable.service.ts`）

三类错误分类（`classifyError`）：
- **non_retryable**：401/403/404/400、invalid api key、model not found、余额不足 → 立即放弃，直接走 fallback
- **rate_limited**：429 → 优先解析响应里的 `Retry-After` 头（cap 30s），没有才用指数退避
- **retryable**：5xx / timeout / 网络错误 → 指数退避重试

默认参数（`types.ts` DEFAULT_RELIABLE_CONFIG）：`maxRetries: 3`，退避 `100ms * 2^(attempt-1)`，上限 `10s`。

重试打光后按 **fallback 链**逐个换模型再试（配置在环境变量里，如 `AGENT_CHAT_MODEL_FALLBACKS`）。

### Layer 3 角色路由（`src/providers/router.service.ts`）

业务代码永远不写死模型 ID，而是声明"我要一个 **chat / extract / vision / evaluate / review** 角色的模型"。实际模型优先取 Dashboard 运行时角色覆盖，未覆盖才取 `AGENT_{ROLE}_MODEL`；`resolveRoute` 另支持仅供基础设施/诊断使用的精确 override 和显式 fallback 覆盖。

角色划分的依据是任务特征：
- `chat`：主对话，要最强模型
- `extract`：会话事实、沉淀摘要、历史摘要压缩和简历字段共用的提取角色
- `evaluate` / `review`：评估与守卫审查，独立配置避免"用同一个模型自证"
- `vision`：图片消息识别

### 结构化输出兼容经验：DeepSeek 与简历抽取（2026-08-17）

`@ai-sdk/deepseek` 出现“JSON Schema 兼容模式”警告，不代表调用参数写错，也与是否开启 thinking 无关。根因是 DeepSeek 原生 Chat API 只提供 `json_object`，没有原生 `json_schema` 约束；AI SDK 因而把 schema 注入提示词、请求 JSON object，并在客户端对结果做 schema 校验。模型只要漏字段、字段类型偏离或输出空对象，就会在客户端变成 `No object generated: response did not match schema`。关闭 thinking 能避免思考 token 挤占输出，但不能把兼容模式升级为原生 schema。

同一批 5 份匿名化生产形态简历、复用同一份 Vision 转写文本、关闭 thinking 与 provider fallback 的等条件回放结果：

- Qwen3.7 Plus：结构化成功 5/5；字段 precision 95.24%、recall 97.56%；耗时中位数 7.616s。
- DeepSeek V4 Pro：结构化成功 4/5；按全部样本计 precision 96.67%、recall 70.73%；复杂样本连续 3 次均 schema mismatch；成功请求耗时中位数 4.467s。

因此等条件回放支持把共享 `extract` 角色配置为 Qwen3.7 Plus。该角色共有 4 个 LLM 调用点：会话事实提取、会话摘要、历史摘要压缩、简历字段抽取；运营只在 Dashboard 修改 `extractModelId`，清空后退回 `AGENT_EXTRACT_MODEL`。`resume-extract.util.ts` 只能声明 `ModelRole.Extract`，不得携带 `modelId`；A/B 临时脚本若需固定模型，必须显式标注为诊断 override，不能复制进生产业务代码。

## 设计权衡（学习要点）

- **为什么不直接 try/catch 换模型？** 错误分类是关键——401 重试三次纯属浪费且拖慢降级；429 带 Retry-After 时盲目指数退避会过早或过晚。分类 + 差异化策略是从"能跑"到"生产级"的分界线。
- **为什么按角色路由？** 换模型是运维动作不是代码动作。常规切换直接在 Dashboard 完成，部署默认才使用环境变量，无需为了换模型改业务代码或重新发版。这也是成本治理的抓手：提取类任务从大模型切小模型只动配置。
