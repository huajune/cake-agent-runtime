# 复聊（Reengagement）独立生成链路

## 解决什么问题

候选人聊到一半消失是招聘漏斗最大的流失点。需要**主动**二次触达：面试提醒、报名信息没填完的跟进、面试后回访。这与"被动应答"是完全不同的问题——没有用户消息作为触发器，出错时也没有用户纠错的机会。

## 链路结构

```
anchor.service        — 锚点：对话中的可跟进事件（约面成功/报名未完成…）注册锚
follow-up-scheduler   — 调度：按场景规则算触达时点，注册 Bull 延迟任务
follow-up.processor   — 到点执行：先做核验（防陈旧任务）再生成
reengagement.agent    — 生成：一次性结构化 LLM 调用 + 确定性兜底
reengagement-delivery — 投递
touch-ledger          — 全生命周期落 reengagement_touch_records
```

## 核心裁定：不复用主 Generator

主 generator 是"带全套工具的多步 Agent"，用它生成一句"明天面试记得带身份证哦"是**杀鸡用牛刀且不可控**（可能自由发挥调工具、产生新副作用）。复聊用专用的 `ReengagementAgent`（`reengagement.agent.ts`），**单轨设计**——所有场景统一走同一条生成路径：

- **一次性结构化 LLM 调用**（`generateStructured`，无工具、无多步），prompt 由场景注册表（scenario-registry）的 objective + generationPolicy 拼成；模型按 schema 输出 `reason / blockReason / decision / message`
- **blockReason fail-closed**：显式 `blockReason` 优先于 `decision`——模型即使误写 `decision=send`，命中任一停止原因仍不发送
- **确定性兜底**（代码层，不靠模型自觉）：复读检测（文案与近期已发 assistant 消息重合即弃）、姓名检测（文案含候选人姓名/昵称即弃）、面试钟点确定性校正

LLM 生成失败、输出不合契约或任一兜底不过，**放弃本次触达**——主动消息宁可不发，不能发错。

## 收资跟进的两个子态

`booking_incomplete` 共用一个场景 code，但锚点明确区分进度：

- precheck 返回 `collect_fields` 或仍有 `missingFields`，排
  `collection_started` 锚点；生成时只提醒继续补充，不猜缺少哪些字段；
- precheck 成功且 `nextAction` 为 `confirm_collection` 或 `select_interview_time`，排
  `collection_awaiting_confirmation` 锚点，并在任务中携带
  `collectionAwaitingConfirmation=true`。此时资料已经收齐，话术只请候选人回复“没问题”、指出要改
  哪一项，或继续选择面试时间；不得再说“还缺资料”，也不得重发整份资料。

两个锚点都受候选人已回复、报名成功等通用停止条件收敛。是否仍需跟进不能再用“字段是否齐全”
一项直接判断。

## 防陈旧：到点核验

延迟任务注册后世界会变：面试可能已被取消/改期。processor 到点执行时**重新核验锚点事实**（查当前真实状态），不符则放弃。早期漏了取消/改期核验，出现过"面试已取消还发提醒"的 badcase。

教训：**延迟任务的决策依据必须在执行时刻重新获取**，注册时刻的快照不可信。

## 全生命周期追溯

每次触达从调度、生成（含跳过原因 validationReason）、投递到结果全部落 `reengagement_touch_records`，Dashboard 有候选人视角页面。主动触达没有用户反馈兜底，**观测是唯一的质量抓手**。

复聊不经过主 Runner，所以 `FollowUpProcessor.runProactiveTurn()` 在调用 Agent 前显式进入
`RequestContextService`：`traceId` 使用主动回合的 `messageId/batchId`，同时写入 chat、user、corp、
scenario，并标记 `callerKind=REENGAGEMENT`。这样 `llm_execution` 与主动回合流水可以按同一 trace
关联，而不是依赖入站链路替它传递上下文。

## 入职跟进的人工告警边界

`post_interview_onboarding` 到点后先查实时工单：`面试成功`才生成候选人触达，`上岗成功`静默停止，
`上岗失败/已离职`直接写人工介入底账并告警；真实消息发送成功后安排的 +48 小时复核若仍未上岗，
同样只查工单并告警，不再发送候选人消息。

告警使用 processor 已解析的渠道身份，其中包含从 `chat_messages` 回填的信息；候选人昵称仍缺时再
从最近聊天记录补齐，并把品牌、门店、岗位和工单状态写入诊断字段。该出口调用
`HandoffRecorderService + GeneralHandoffNotifierService`，不调用会暂停托管的
`InterventionService`，所以告警后 AI 仍可应答。

## 学习要点

- "被动应答 vs 主动触达"的风险剖面完全不同：被动场景用户会纠错，主动场景一条错误消息就是打扰甚至事故——所以生成策略反而要**更保守**（停止条件优先、生成失败即放弃）。
- 结构化输出 + 确定性兜底是控制幻觉的**架构手段而非 prompt 手段**：blockReason fail-closed、复读/姓名检测都在代码层拦截，不依赖模型自觉。
