# Agent 工具层设计与幻觉防御

## 工具体系

`src/tools/` + `ToolRegistryService` 提供岗位查询、约面/改约/取消、拉群、转人工、召回历史等工具；
`src/mcp/` 支持 MCP 动态扩展。**可用工具集合**由场景 registry 与 Generator 的 `activeTools`
收紧逻辑管理；Guardrail 侧的 `tool-guardrail.catalog.ts` 只登记动作门禁，不拥有工具目录。

## 关键设计经验

### 1. 工具 description 是一等 prompt 资产

与工具语义强绑定的业务约束**写进工具 description**，而不是堆在 system prompt（分层放置原则，见 [[05-Prompt-Section动态组装体系]]）。例如"报名 name 必须真实姓名，微信昵称不算"就属于 booking 工具的 description。

排障时不能拿当前 description 猜历史行为。每次 LLM 调用会把当时实际下发的工具名称、description
与完整 input schema 保存进调用快照；旧档案没有快照时明确标成不可还原，不用新定义补造旧现场。
Provider 动态工具只记录可确认的名称，不复制一份可能漂移的参数定义。

### 2. 确定性兜底优于 prompt 祈祷

多个实测案例证明纯 prompt 约束不可靠：

- 企微备注里有品牌名时应优先推该品牌——preparation 用代码解析并确权备注品牌，写入 `contactBrandAliases` 和 `TurnLedger.mentionedBrands`，再通过 Prompt 证据约束模型；job-list 仍按模型参数或 `sessionBrandState` fallback 形成查询计划，不由 preparation 直接篡改工具参数
- 品类词（"咖啡"）应展开为品牌集合走品牌召回，而不是让模型自己发挥成"咖啡师"岗位名
- 模型显式传入的标准品牌还要经过 `TurnLedger.mentionedBrands` 对账；候选人语料、可信图片、记忆、当前岗位或真实工具结果都没提过的品牌，在发外部查询前返回 `job_list.brand_no_provenance`
- 候选人明确要求包住时，工具解除通勤距离上限、改做全城召回并按住宿福利过滤；候选人的具体可上班窗口则进入结构化班次包含关系判断，而不是只靠"早班/晚班"关键词
- 拉群工具保留本轮 booking 明确失败、区县误传、实时在群、城市来源和同城市重复邀请等结构化闸门；`invite-timing-gate` 本身只拒绝同城市重复邀请。候选人是否已同意、是否已完成岗位推荐或正在推进报名属于对话语义，由主 Agent 基于完整上下文判断，工具层不再用正则二次否决

模式：**能用代码在工具入参层面固化的规则，不要指望模型每次都遵守**。

### 3. 外部 API 语义要在工具层抹平

- `storeNameList` 是精确匹配（备注里的门店名经常对不上），`searchJobName` 才是模糊匹配——工具层做了 0 结果时的本地子串兜底
- "windows 为空 = 等通知岗位"：precheck 不能判 date_unavailable，booking 可不带 interviewTime——外部系统的隐式语义必须在工具层显式建模，否则 LLM 会按字面理解出错
- `bookableSlots` 是工具按完整日期时间与报名截止时间计算后的权威集合；"最近可约"只能取按日期时间重排后的 `nearestBookableSlot`，不能让模型再解释"当天/提前一天"等相对文案
- `booking.already_booked` 表示同岗位预约已经存在、本轮没有重复提交，不是系统失败。回执带出可确认的旧工单号；已有登记时间时再带面试时间，并禁止承诺稍后重提

### 4. 收资与预约是一条事务协议

`duliday_interview_precheck` 的 `mode` 必须显式二分：`query` 只读查询或刷新实时契约，
`validate` 才提交有候选人原话依据的字段提案或复述确认。首次 `validate` 可以在同一次调用里建立
契约快照并校验，不能为了先查表而丢掉本轮答案。

表单按候选人与岗位隔离；多人代报时主候选人与当前办理人使用不同指针并严格串行。precheck 在收资前
检查候选人级在途预约，booking 在真正调用外部接口前用同一判据再检查一次，分别覆盖较好的交互体验
和两个并发回合之间的最终竞态。完整状态与提交边界见 [[19-收资与预约事务状态机]]。

### 5. 幻觉防御纵深

- 入口：空召回闸门（会话没召回过岗位就禁报名链路）
- 参数口：jobId 必须来自本会话真实召回；模型显式品牌必须出现在可信提及集合
- 动作口：precheck 的契约快照、字段公证、授权状态与 booking 的最终查重共同保护外部副作用，详见 [[08-守卫假阳治理与业务裁定]] 和 [[19-收资与预约事务状态机]]
- 文本出口：Output 守卫只校验 catalog 中有确定性证据基的形态，包括“零查询却声称查过”、无出处的量化岗位事实、预约回执与可约时段；它不是通用的所有薪资、地点与岗位文案事实核验器

## 学习要点

工具设计的核心命题：**LLM 是不可信的调用方**。传统 API 设计假设调用方读文档、传对参数；给 LLM 用的工具要假设调用方会编造参数、误解语义、忽略约束——所以要入参校验、来源审计、状态机授权、语义抹平与出站对账。工具定义快照还要保证故障发生后能还原“调用方当时读到的契约”。
