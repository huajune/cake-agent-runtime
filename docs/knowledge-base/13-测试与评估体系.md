# LLM 应用的测试与评估体系

> 最后更新：2026-09-11。依据当前实现与评估口径页核对。

## 问题：传统测试金字塔对 LLM 失效

单测能覆盖确定性代码（合并原语、守卫规则、分段器），但"Agent 回复质量"不是断言能表达的——同输入不同输出、"好"是模糊的多维标准。

## 本项目的分层方案

| 层 | 手段 | 覆盖什么 |
|---|---|---|
| 单测 | Jest（tests/ 镜像 src/ 结构） | 确定性逻辑：facts 合并、守卫规则、消息切分 |
| 回归测试集 | test-suite 域 + Dashboard 页面 | 历史 badcase 固化为用例，修复后批量重放 |
| 校准判官 | test-suite Claude 评审 + 复聊 blockReason，周频标定（docs/todo/judge-calibration.md） | 机器判不了的语义，判官精确率不达标即降级 |
| 生产抽样 | badcase 分析 skill（人机协作 SOP） | 抽生产对话 → 归因 → 修复 → 生成针对性测试集验证 |
| 影子运行 / 观察命中 | 具备 shadow 开关的独立链路，或确定性规则的 observe 结果 | 记录判例后人工核对；不表示出站运行 LLM reviewer 或 semantic shadow |

## 关键经验

1. **badcase 是最宝贵的测试资产**：生产判例带完整上下文（prompt、工具返回、守卫裁决同 traceId 可查），比手造用例真实得多。闭环是：运营标注 badcase → 归因（prompt 问题/工具问题/守卫误拦）→ 修复 → 判例入回归集。
2. **单轮重放有局限**：重放单条消息无法复现多轮状态（记忆、阶段），跨轮问题要靠完整会话级别复现。
3. **评审自动化的坑**：曾发现 turn 评审因 comment 过长"假成功"——评估管道自身也需要被观测。
4. **LLM 评分不能当唯一真相**：相似度评分器已于 2026-09-02 删除（拿真人历史回复当标准答案、看不见上游工具错、加权过线三条硬伤）；判官只在锁定 rubric 并按周标定后才有裁决权。口径页：docs/architecture/agent-quality-evaluation.md。

## 从生产档案到周报：分母与样本先讲清楚

- **守卫档案行数不等于审查量**：`guardrail_review_records` 是单写入者稀疏表，无命中的放行回合不写行；`first_decision=pass` 的行仍可能来自仅观察命中。应分别报告命中、修复和最终处置，不能把落档行数称为“审查回复数”。
- **反馈量要带业务分母**：用相同时间窗的回合数计算每千回合反馈量，再做周环比；单看 BadCase 条数会把业务量变化误当质量变化。
- **转人工原因按稳定码聚合**：使用 `payload.reason_code`，不把可能含候选人姓名、电话的自由文本 reason 写入周报。
- **小样本不展示看似精确的准确率**：系统监控提取质量卡对高置信样本少于 30 的字段显示“样本不足”。这是该卡片的展示门槛，不能替代判官校准口径，也不能推出其他指标样本已经充分。

周报工作流先整理并存档运行数据，再调用 [send-weekly-card.js](../../scripts/weekly-ops-report/send-weekly-card.js) 渲染飞书卡片；脚本支持 dry-run、签名、10 秒请求超时与飞书响应码检查。卡片只带运行数据，改动明细留在文档中。脚本由工作流触发，应用没有对应的 NestJS 定时任务。完整口径见 [weekly-ops-report](../../src/skills/weekly-ops-report/SKILL.md)。

## 学习要点

"LLM 应用怎么测试"几乎是必问题。答案框架：**确定性部分传统测试、概率性部分评估集 + 影子运行 + 生产观测闭环**——重点讲 badcase 从发现到固化为回归用例的完整闭环，这是大多数团队缺失的。
