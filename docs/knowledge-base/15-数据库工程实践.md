# 数据库工程实践（Supabase/Postgres）

> 最后更新：2026-09-11。依据仓库代码与迁移文件核对，不据此推定迁移已在生产执行。

## 迁移纪律

- 测试/生产双库隔离（`db:push:test` / `db:push:prod`），**先测试后生产**
- SQL 幂等：新建用 `IF NOT EXISTS` / `ON CONFLICT`；但**修改既有定义**（索引/函数）必须 `DROP IF EXISTS + CREATE`——IF NOT EXISTS 只查名字不查定义，会静默跳过（吃过 0 行事故，见 [[14-生产事故复盘集]] 案例 3）
- **迁移与代码发版必须同步**：只发代码不推迁移（或反之）是反复发生过的事故源
- 上线新表后用一条真实写入验证落库，不能只看部署成功

## Schema 设计裁定

- **按维度分表而非宽表**：回合流水 / 执行事件 / 守卫档案 / 复聊触达 / 业务漏斗各自独立表，同 trace_id join——写入方、生命周期、查询模式不同的数据不同居
- **JSONB 存档案、真实列存指标**：大 JSONB（完整 prompt 达 43KB）走 TOAST，高频读取字段必须提列（ttft 事故）
- 字段自带元数据模式：`semantic_profile` jsonb 里每个事实带 `{value, confidence, source, evidence}`——比"值一张表、元数据一张表"简单得多，查询也总是一起用
- 大表前瞻：`ops_events` 日增 50 万行时再上分区，不提前过度设计

## 转化分析：聚合下沉，失败路径不改走裸扫

主漏斗、趋势和账号对比由三个 `STABLE` RPC 提供聚合结果，去重与成员匹配在数据库内完成：

| RPC | 所有权与口径 |
| --- | --- |
| `conversion_period_stats` | 窗口内各阶段独立去重，一次返回 total/day/bot 三种粒度；总量跨 bot 按人去重，不能用逐 bot 行简单相加替代 |
| `conversion_cohort_stats` | 新增好友入列批次追踪；最早入列确定归属，先 userId、后 chatId 匹配下游事件，事件不得早于入列。破冰 ⊇ 报名 ⊇ 面试通过，加群是破冰侧支；返回入列日 × bot 汇总 |
| `conversion_handoff_reasons` | 转人工事件按 payload.reason_code 分组计数，空值归 other |

`ConversionAnalyticsService` 按参数缓存聚合查询 Promise 10 秒，同条件并发请求共享加载；底层 `rpcAllPaged` 可继续分页读取聚合结果，因此不能承诺任意规模都只有一次网络往返。首屏 RPC 缺失、超时或熔断时按空数组/空统计降级；后续分页失败时会保留此前已经取得的部分聚合结果。两类失败都由数据库访问层记日志，不回退到拉明细或 Node 全量聚合，消费端也不能把降级结果误当成完整统计。代码目前不能据此证明该查询失败一定触发独立告警。

booking cohort、取消/改约计数等小体量侧支仍使用明细查询；“主路径聚合下沉”不等于全系统禁止读取明细。实现：[OpsEventsAnalyticsRepository](../../src/biz/conversion-analytics/repositories/ops-events-analytics.repository.ts)、[RPC 迁移](../../supabase/migrations/20260910025705_conversion_analytics_rpcs.sql)。

## 长期记忆：数据形态由约束守住

摘要列 `episodic_session_summaries` 使用数组并有数组形态 CHECK，沉淀水位归独立 `consolidation_watermarks`，事实 source 使用标准词汇。运行时读边界只消费规范形态，目标库必须完成配套的一次性数据归一迁移，不能依靠读时兼容覆盖长期无人访问的行。

迁移的验收条件是摘要数组及顺序正确、水位独立且已有独立值优先、source 规范化、数组约束生效，读时 CAS 懒迁移 RPC 不再属于接口契约。迁移文件存在不等于任何目标库已经执行；上线应核对迁移状态、结果形态和约束，再验证读写。具体脚本见 [长期记忆形态归一迁移](../../supabase/migrations/20260911120000_flatten_legacy_long_term_shapes.sql)，记忆语义见 [[03-两层记忆系统]]。

## Redis 与 Postgres 的分工

判定标准不是"快不快"，而是**丢了算不算事故**：

- 丢了算事故且无 DB 备份的业务状态（facts / stage / group-task、debounce pending、collection form 及其定位指针）——pending 丢失会静默吞掉候选人输入，表单丢失会丢报名进度，这些都是架构风险清单上的显式条目
- 可重建热缓存可从权威存储恢复；锁、去重标记等协调 key 不承载业务事实，但丢失仍可能造成并发执行或重复动作，不能笼统称为“可自愈”

有价值的易失数据靠**沉淀**投影到 Postgres（session facts → `semantic_profile` / `semantic_job_intent`，求职段原文 → episodic summary）。

## 连接池

Supabase `max_conns=60` 被 Dashboard 轮询 + 重试风暴打满过全线 522（见 [[14-生产事故复盘集]] 案例 1）；Dashboard 定时预热 + JSONB 裸扫又造成过 Postgres 连续重启（案例 7）。RPC 轮询要有节流，应用重试要有熔断，后台统计必须有固定成本上限。

## 查询与后台任务红线

以下任一项不满足即阻断合入：

1. **降级成本单调下降**：RPC 超时、缺失、熔断或返回异常时，只能读旧缓存、返回空统计并告警；禁止改走全表扫描、分页拉全量或在 Node 重新聚合。主查询因过重失败后再发更重查询，等同自我 DDoS。
2. **定时任务不碰无界明细**：`all`/全历史及 30～90 天长窗口不得进入分钟级预热。长范围必须读小时/日投影；确需明细时由用户按需触发，设置明确起点、statement timeout 和缓存。
3. **每轮有互斥和预算**：cron 必须防 tick 重叠，并限制单轮时间窗、bucket 数、行数和总执行时间。多实例任务使用数据库 advisory lock/分布式锁，不能只靠进程内布尔值。
4. **断更只补洞**：聚合任务按已存在的 bucket 键找缺口，只补缺失小时/日期；无数据的 bucket 也写零值水位，避免每轮重复判断为缺失。禁止因“最新水位过旧”重算整个窗口。
5. **JSONB/TOAST 不做高频统计源**：频繁过滤、排序、分组或展开的字段提升为真实列或预聚合；不得在轮询、预热和 cron 中对大 JSONB 使用 `jsonb_array_elements*`。
6. **重试与熔断按操作隔离**：瞬时错误只允许有上限的指数退避 + 抖动；熔断计数按 RPC/表操作区分，其他健康查询成功不能清零当前失败操作。

### 合入前证据

- 在生产量级、相同索引和数据分布下记录 `EXPLAIN (ANALYZE, BUFFERS)`；确认索引、扫描行数、临时文件和执行时间有硬上界。
- 对 cron/轮询做持续运行验证，核对单位时间调用次数、连接数、累计 DB 时间和任务重叠次数；单次接口延迟改善不能替代持续负载验证。
- 人工演练 RPC 超时、聚合断更和熔断 OPEN，证明失败路径不会发起更重查询。
- 发布后重点观察 `pg_stat_statements`、连接池、CPU/IO、异常重启和聚合水位；异常时先停预热/断载，再考虑扩容。

## 学习要点

前端转后端最容易被考的就是数据库。这套实践的叙事线：**幂等迁移 → 双环境纪律 → 观测验证落库 → 读写路径分离设计 → 查询成本有界且失败成本递减**，每一条都有真实事故背书，比背书本的"三范式"有说服力得多。
