# 可观测性体系（ALS 上下文 + Tracer + Observer 落库）

> 更新于 2026-11-25。本文描述当前代码的读写口径。

## 解决什么问题

LLM Agent 的排障比传统服务难一个量级：同一输入不同输出、失败发生在"模型理解"层面而非异常层面。没有"当时模型看到了什么、决定了什么"的完整档案，badcase 无法归因。

## 架构

```
请求入口 → RequestContextService（AsyncLocalStorage 挂 traceId 等上下文）
        → AgentTracer 埋事件（回合开始/工具调用/守卫裁决/…）
        → CompositeObserver 分发
            ├─ LoggerObserver     → 结构化日志
            └─ PersistingObserver → 落 Supabase agent_execution_events
```

- **AsyncLocalStorage**（`context/request-context.service.ts`）让 traceId 贯穿整个异步调用链而不用层层传参——Node.js 侧等价于 Java 的 ThreadLocal + MDC。这对 Agent 尤其重要：一个回合跨越队列消费、多次 LLM 调用、多个工具的 IO。
- **Observer 模式解耦**：埋点方只调 tracer，落到哪里（日志/DB/未来的 OTLP）由 observer 决定，新增消费端不动业务代码。
- 处理流水用 `message_id` 定位，执行事件和守卫档案用对应的 `trace_id` 查找。复聊触达、渠道消息与运营事件有各自的业务记录。

## 一条消息如何留档

| 想查的问题 | 表与粒度 | 写入和读取 |
| --- | --- | --- |
| 这次处理结果如何，工具实际返回了什么？ | `message_processing_records`，每个处理 ID 一行。包括状态、输入和回复预览、阶段耗时、token 数、步骤、守卫摘要及记忆快照。`tool_calls` 按顺序保存本次生成报告的工具调用，含参数、返回值和可用的执行数据。 | 渠道跟踪处理进度，收尾时写工具明细。列表读轻量投影，工具统计读主流水。运行中断、尚未收尾时，清单可能不完整。 |
| Cake 为这轮回复准备了什么，最后如何投递？ | `message_processing_turn_snapshots`，每轮至多一行。 | 收尾时写回合上下文、SDK 消息及渠道投递结果。历史回合继续用处理 ID 查询。 |
| 供应商在第几次请求收到了什么，原样返回了什么？ | `message_processing_invocations`，每次模型 HTTP 请求一行。一轮可有零次或多次。 | 总部在「调试载荷 → 模型调用原文」先取调用清单，选中一次后读取这一次的完整收发正文。 |
| 哪些过程值得拿来复盘 bad case？ | `agent_execution_events`，一个 trace 可有多行。记录可解释执行过程的事实，包括正常收尾、成功的外部操作、质量线索和异常。 | 事件发生时独立异步写入。消息详情按 trace 取时间线，一次最多取 200 条。有线索需要结合输入、输出和业务回执判断。没有事件也可能是未命中留存条件、超出可读范围或写入缺失。 |

拆分的原因是写入时机和读取频率不同。消息刚进入队列时就需要跟踪，处理中断也需要留下状态。提示词、历史消息和回复体只有运行到相应阶段才产生，体积也大。独立存放以后，列表和状态更新只处理主流水，复盘单条请求时才读取快照。

### 一轮回复可以有三次模型调用

例如，第一次模型响应要求查岗位。Cake 执行工具后，将岗位结果发给模型，第二次请求收到 HTTP 503。Cake 切换供应商，第三次请求得到回复。这轮处理会留下三条模型调用。第二条的响应是 503 正文，第三条请求里能看到实际转发的工具结果。工具的执行耗时、结果和渠道投递结局分别在流水和回合快照中查询。

采集点在 Qwen 和 DeepSeek 共用的 HTTP 入口，位于 SDK 转换请求之后、解析供应商响应之前。每条记录有处理 ID、调用 ID、开始时间、供应商、HTTP 状态、正文完整标记和两份正文。数据库按字节保存，JSON 保留原有字段和空白，流式响应保留按接收顺序拼接的 SSE 内容。无响应头时用空状态标识；响应中断时可查看已读部分。HTTP 状态与正文完整性可以独立判断，例如 HTTP 503 也可有一份完整错误正文。[采集实现](../../src/observability/context/model-invocations.ts) · [供应商接入](../../src/providers/registry.service.ts)

一次回合的收尾事务批量写入这些调用，保存重试沿用原调用 ID。流式片段在进程内收集，默认保留期为 90 天。进程在提交前退出时，这轮未提交的原文会丢失。升级前的历史只含 Cake 或 SDK 的回合现场，无法补出供应商原文。

### 回合快照实际存了什么

下表以企微被动消息为例。主动复聊另有触达指令及发送时序，测试流可含传输请求与流式指标。标记为 `testing` 的调试流跳过生产处理流水及快照写入。

| 快照位置 | 值 |
| --- | --- |
| `request` | 处理 ID、会话和账号、场景、当轮输入、图片数、调度方式；合并消息时还可含来源消息 ID 和到达时间。 |
| `request.agentRequest` | 捕获到的生成请求。包括首选和候补模型、当时的 instructions 或 system、消息序列，以及适用的工具名、定义、输出上限与 provider 选项。字段随入口与执行阶段而异。未走到模型时可缺失。 |
| `response` | 处理状态、错误、回复正文、可用的 reasoning 与 token usage、SDK 响应消息、投递或兜底回执，以及各阶段时间点和耗时。新企微记录的 `agentSteps`、`memorySnapshot` 在主表独立列。 |
| 主流水 `is_fallback` | 本次处理是否走了兜底，供列表、详情和统计读取。 |

快照的业务字段为 `message_id`、`created_at`、`request` 和 `response`。它与主流水按 `message_id` 关联。执行事件按 `agent_execution_events.trace_id = message_processing_records.message_id` 查询。企微聚合处理使用批次 ID 作为本次处理 ID，单条直达消息使用渠道消息 ID。快照和事件默认保留 90 天。[流程入口](../../src/channels/wecom/message/application/reply-workflow.service.ts) · [保留期](../../src/biz/monitoring/services/cleanup/data-cleanup.service.ts)

工具名称、入参、状态和结果集中在主流水的 `tool_calls`。有步骤归属的调用用 `stepPosition` 对应 `agent_steps` 中从零开始的位置，重试时重复的 SDK 步号也能区分。步骤只保存自身的文本、用量、耗时等信息。回合响应的 `messages` 由 SDK 整理，可能含工具消息。供应商自己返回的工具指令随原始响应完整存放。主流水内容被更正时，当前快照随之清除，写入新现场时在同一事务内替换。标量状态更新保留已捕获的现场。[原子写入](../../supabase/migrations/20261125080100_processing_snapshot_storage.sql) · [列表与详情读取](../../src/biz/message/repositories/message-processing.repository.ts)

### 模型当时的输入

工具定义包含当时的 `description` 和输入 JSON schema。`snapshotToolDefinitions()` 使用 SDK 同源 schema 解析，支持动态描述和异步 schema。工具执行函数与工具内部上下文留在程序中。解析失败时标记缺失，模型可继续执行。

Dashboard 最终提示词面板只展示历史快照中的 Instructions 全文（兼容旧记录的 system）与 Messages 消息序列。工具名称、description 和输入 JSON schema 在「Agent 请求」面板查看；旧记录缺失的工具定义不使用当前工具目录补齐。入口：[tool-definition-snapshot.ts](../../src/llm/tool-definition-snapshot.ts)、[调试载荷展示](../../web/src/view/message-processing/list/components/MessageProcessingDetailDrawer/utils.ts)。

## 异步边界必须显式接续 Trace

ALS 只随已进入上下文的异步调用传播，不能自动覆盖所有旁路：

| 边界 | 当前接续方式 |
| --- | --- |
| 投递后记忆收尾 | Runner 的 `bindTurnEndContext()` 捕获当前上下文，后续 `runTurnEnd` 执行时重新进入原 trace |
| 独立复聊生成 | `FollowUpProcessor.runProactiveTurn()` 以 batch/messageId 建立 trace，补 chat/user/corp/scenario，callerKind 为 `REENGAGEMENT` |
| 异步图片描述 | `ImageDescriptionService.inTraceContext()` 以图片 messageId 建立 trace，可回查 `chat_messages`；收尾补写已有回合 trace 时沿用外层 |

`AgentTracer.emit()` 先剔除事件中值为 `undefined` 的字段，再与上下文合并，避免把已有身份字段覆盖为空。图片事件的 trace 可能属于原始图片消息，不能假定每条旁路事件都直接对应主回合流水。

## 按排障价值持久化

`PersistingObserver` 对终态、异常、LLM 执行、品牌状态变化、收资审计和守卫修复等关键事件直接落库；普通工具调用只在副作用、错误、空结果、窄召回或耗时至少 3 秒时保留。装配事件另有条件门槛：

| 事件 | 持久化条件（任一满足） |
| --- | --- |
| `turn_data_sources` | 失败、总耗时 ≥15 秒、任一数据源 degraded/failed |
| `turn_preparation` | 失败、总耗时 ≥20 秒、Prompt ≥50,000 字符 |

| 其余事件 | 何时能在时间线看到 |
| --- | --- |
| 回合与模型 | `agent_end`、`agent_error`、`llm_execution`、`model_fallback` 发出时均留存。一次正常模型调用也有观测价值，重试与退避见对应事件的 `attempts`。 |
| 工具 | `tool_error` 在工具抛异常时留存。`tool_call` 命中外部动作、返回错误、空结果、窄召回或耗时 ≥3 秒时留存。外部动作标记来自工具契约，业务是否真正生效要读该次回执。 |
| 决策、记忆与安全 | 候选人进度判定分歧、品牌迁移或歧义、会话字段校验丢弃、班次抽取与核验分歧、提示词注入命中，在各自事件发出时留存。 |
| 收资与守卫 | 收资表单裁定、身份标签错配、空收资契约、出站修复、入站转人工，在各自事件发出时留存。守卫的最终处置取 `finalOutcome`。 |
| 仅应用日志 | `agent_start`、`model_call`、`agent_stream_timing`、`booking_snapshot`、`oob_reconcile_scan`。 |

当前 24 种事件共用一份规则。其中 16 种在发出时直接进入持久化，3 种按条件留存，5 种仅写日志。详情用同一规则解释可见的字段。工具内部发出的观测事件沿用该次 SDK 调用 ID。模型、回合和带外事件可按各自 trace 查看。工具执行信息取自包装器的一次实测。被选中的工具事件保留工具名、状态和实测耗时等短摘要，即使整轮没能收尾，仍能独立回查。流水中的 `decisions` 只记录实际走过且有埋点的分支，独立于返回给模型的结果。页面只在同一 trace、调用 ID 唯一且相符时关联，历史数据按已有字段展示。[全部留存条件](../../src/observability/execution-event-policy.ts) · [工具执行包装](../../src/agent/generator/preparation/tool-context.builder.ts) · [时间线查询](../../src/biz/monitoring/repositories/agent-execution-event.repository.ts)

例如查岗返回零个结果，可以据事件定位该次查询，再去「工具执行」看参数与过滤条件。预约预检遇到岗位未配置的收资字段，会留下 `collection_form_audit`，其中 `proposal_rejected` 与 `label_title_not_found` 记录了这次为何拒收。工具详情按调用 ID 链接到这条既有证据。邀请工具改试下一群后成功发出邀请卡，整次调用可为 `ok`。前一群被拒绝属于内部判断，最终是否入群仍要看成员事实。单凭事件数量无法计算失败率。

主账本也必须监控自身：`MessageTrackingService` 在终态无法还原或重试后仍写入失败时发送 `message_processing_terminal_persist_failed`，分别按 `terminal_unrecoverable`、`db_write_failed` 去重，避免流水永远显示 processing 却只有日志可查。

## 系统监控读数的边界

| 页面指标 | 当前来源与限制 |
| --- | --- |
| 在途请求 | DB 中 received_at 近 24 小时、status=processing 的行数，head-only count；每次读取后校准 Redis，发现 Redis 高于 DB 时峰值一并归位。查询失败返回 0，因此它不是无条件准确的全局实时并发数 |
| P95 总耗时 | 北京时间今日成功回合，按 received_at 倒序最多取 1000 条，再对有效正数 total_duration 算分位数；保留超过 60 秒的真实慢回合，不代表当天全部样本 |
| 今日告警 / 告警趋势 / 分布 | 飞书告警持久化记录，含基础设施、定时任务和守卫等子系统，不等于消息处理错误数；今日趋势从本地 0 点按小时补零 |

超时回收将 processing 翻为 timeout 后同步扣减 Redis 在途计数。排队耗时扣除 debounce 主动等待的计算见 [[02-消息debounce聚合与租约锁]]；高置信提取小样本与周报分母见 [[13-测试与评估体系]]。入口：[AnalyticsQueryService](../../src/biz/monitoring/services/dashboard/analytics-query.service.ts)、[消息流水查询](../../src/biz/message/repositories/message-processing.repository.ts)。

## 关键经验

1. 历史提示词从配对快照的 `request.agentRequest` 读取。事后用今天的记忆、配置或岗位数据重新装配，可能得到不同输入。
2. **代价**：大 JSONB 有性能陷阱——列表页只需要 ttft 一个数字，却因为它埋在 43KB 的 JSONB 里导致逐行 detoast，月度统计 RPC 慢到 52.6s；修法是把高频读取字段提升为真实列。教训：**JSONB 存档案、真实列存指标**，读写路径分开设计。
3. **观测不能只打日志**：shadow 判例、降级、守卫命中必须落库或推飞书告警。日志是辅助——没人主动看日志，"打了日志"不等于"有观测"。
4. **观测 schema 按维度分表**：回合流程、评估、反馈、守卫、复聊各自独立表，不塞一张宽表——写入方、生命周期、查询模式都不同。

## 学习要点

- 这套是"买不到才自建"：当时 LangSmith 等托管方案与自有栈（NestJS + Supabase）集成弱，且要与业务表 join 归因（守卫档案 ↔ 转化漏斗），自建事件表反而是最短路径。
- ALS 是 Node 后端进阶知识点，前端转后端的学习中主动讲清楚"为什么不能用全局变量、为什么不想层层传参"很加分。
