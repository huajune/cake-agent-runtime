# 可观测性体系（ALS 上下文 + Tracer + Observer 落库）

> 最后更新：2026-09-11。描述仓库实现，不代表已核验线上部署状态。

## 解决什么问题

LLM Agent 的排障比传统服务难一个量级：同一输入不同输出、失败发生在"模型理解"层面而非异常层面。没有"当时模型看到了什么、决定了什么"的完整档案，badcase 无法归因。

## 架构

```
请求入口 → RequestContextService（AsyncLocalStorage 挂 traceId 等上下文）
        → AgentTracer 埋事件（回合开始/工具调用/守卫裁决/…）
        → CompositeObserver 分发
            ├─ LoggerObserver     → 结构化日志
            └─ PersistingObserver → 落 Supabase agent_execution_events
```

- **AsyncLocalStorage**（`context/request-context.service.ts`）让 traceId 贯穿整个异步调用链而不用层层传参——Node.js 侧等价于 Java 的 ThreadLocal + MDC。这对 Agent 尤其重要：一个回合跨越队列消费、多次 LLM 调用、多个工具的 IO。
- **Observer 模式解耦**：埋点方只调 tracer，落到哪里（日志/DB/未来的 OTLP）由 observer 决定，新增消费端不动业务代码。
- **同 traceId 五表可 join**：`message_processing_records`（回合流水，含完整 prompt）、`agent_execution_events`（执行事件）、`guardrail_review_records`（守卫档案）、`reengagement_touch_records`（复聊触达）、`ops_events`（业务漏斗事件）。排障动线：Dashboard 看流水 → 按 traceId 下钻。

## 保留执行现场，而不是用当前配置重建历史

LLM 请求档案除 system/messages、工具名称外，还保存调用时的工具 `description` 和完整输入 JSON schema。`snapshotToolDefinitions()` 使用 SDK 同源 schema 解析，兼容动态描述和异步 schema；只保留模型可见定义，不保存执行函数、工具 context 或 provider 参数。快照解析失败会记录缺失字段，不中断模型调用。

Dashboard 最终提示词面板只读取这份历史快照。记录只有工具名时明确提示无法还原定义，不能拿当前工具目录补成当年的现场。入口：[tool-definition-snapshot.ts](../../src/llm/tool-definition-snapshot.ts)、[工具快照展示](../../web/src/view/message-processing/list/components/MessageProcessingDetailDrawer/tool-definition-prompt.ts)。

## 异步边界必须显式接续 Trace

ALS 只随已进入上下文的异步调用传播，不能自动覆盖所有旁路：

| 边界 | 当前接续方式 |
| --- | --- |
| 投递后记忆收尾 | Runner 的 `bindTurnEndContext()` 捕获当前上下文，后续 `runTurnEnd` 执行时重新进入原 trace |
| 独立复聊生成 | `FollowUpProcessor.runProactiveTurn()` 以 batch/messageId 建立 trace，补 chat/user/corp/scenario，callerKind 为 `REENGAGEMENT` |
| 异步图片描述 | `ImageDescriptionService.inTraceContext()` 以图片 messageId 建立 trace，可回查 `chat_messages`；收尾补写已有回合 trace 时沿用外层 |

`AgentTracer.emit()` 先剔除事件中值为 `undefined` 的字段，再与上下文合并，避免把已有身份字段覆盖为空。图片事件的 trace 可能属于原始图片消息，不能假定每条旁路事件都直接对应主回合流水。

## 按排障价值持久化

`PersistingObserver` 对终态、异常、LLM 执行、品牌状态变化、收资审计和守卫修复等关键事件直接落库；普通工具调用只在副作用、错误、空结果、窄召回或耗时至少 3 秒时保留。装配事件另有条件门槛：

| 事件 | 持久化条件（任一满足） |
| --- | --- |
| `turn_data_sources` | 失败、总耗时 ≥15 秒、任一数据源 degraded/failed |
| `turn_preparation` | 失败、总耗时 ≥20 秒、Prompt ≥50,000 字符 |

这是条件持久化，不是全量事件审计；阈值应结合实际基线，避免采样事实上退化成全量。守卫修复事件用 `finalOutcome: reply / handoff / skipped` 表达最终处置，入站风险意图记为 `inbound_guardrail_handoff`，单次审查动作与最终处置不能混为一个指标。代码入口：[PersistingObserver](../../src/observability/persisting-observer.ts)。

主账本也必须监控自身：`MessageTrackingService` 在终态无法还原或重试后仍写入失败时发送 `message_processing_terminal_persist_failed`，分别按 `terminal_unrecoverable`、`db_write_failed` 去重，避免流水永远显示 processing 却只有日志可查。

## 系统监控读数的边界

| 页面指标 | 当前来源与限制 |
| --- | --- |
| 在途请求 | DB 中 received_at 近 24 小时、status=processing 的行数，head-only count；每次读取后校准 Redis，发现 Redis 高于 DB 时峰值一并归位。查询失败返回 0，因此它不是无条件准确的全局实时并发数 |
| P95 总耗时 | 北京时间今日成功回合，按 received_at 倒序最多取 1000 条，再对有效正数 total_duration 算分位数；保留超过 60 秒的真实慢回合，不代表当天全部样本 |
| 今日告警 / 告警趋势 / 分布 | 飞书告警持久化记录，含基础设施、定时任务和守卫等子系统，不等于消息处理错误数；今日趋势从本地 0 点按小时补零 |

超时回收将 processing 翻为 timeout 后同步扣减 Redis 在途计数。排队耗时扣除 debounce 主动等待的计算见 [[02-消息debounce聚合与租约锁]]；高置信提取小样本与周报分母见 [[13-测试与评估体系]]。入口：[AnalyticsQueryService](../../src/biz/monitoring/services/dashboard/analytics-query.service.ts)、[消息流水查询](../../src/biz/message/repositories/message-processing.repository.ts)。

## 关键经验

1. **完整 prompt 必须落库**。`agent_invocation.request.agentRequest` 存全量请求——"模型当时看到什么"是不可再现的（记忆/配置/岗位数据都在变），不存就永远失去归因能力。
2. **代价**：大 JSONB 有性能陷阱——列表页只需要 ttft 一个数字，却因为它埋在 43KB 的 JSONB 里导致逐行 detoast，月度统计 RPC 慢到 52.6s；修法是把高频读取字段提升为真实列。教训：**JSONB 存档案、真实列存指标**，读写路径分开设计。
3. **观测不能只打日志**：shadow 判例、降级、守卫命中必须落库或推飞书告警。日志是辅助——没人主动看日志，"打了日志"不等于"有观测"。
4. **观测 schema 按维度分表**：回合流程、评估、反馈、守卫、复聊各自独立表，不塞一张宽表——写入方、生命周期、查询模式都不同。

## 学习要点

- 这套是"买不到才自建"：当时 LangSmith 等托管方案与自有栈（NestJS + Supabase）集成弱，且要与业务表 join 归因（守卫档案 ↔ 转化漏斗），自建事件表反而是最短路径。
- ALS 是 Node 后端进阶知识点，前端转后端的学习中主动讲清楚"为什么不能用全局变量、为什么不想层层传参"很加分。
