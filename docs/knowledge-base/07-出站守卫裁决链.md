# 出站守卫裁决链（规则 → 语义 reviewer → 有界收敛）

## 先讲清边界

本文只讲 **Output 守卫内部**。全系统有 Input / Prompt / Tool / Output 四个防线作用位：

- Input 在生成前短路高危入站或识别注入；
- Prompt 用 system sections 和 final-check 降低首版违规率；
- Tool 用真实业务信号拒绝错误动作；
- Output 审查最终候选回复，本文从这里开始。

因此“Output 内有几段”不能用来回答“全系统有几层防线”。总览见
[安全护栏说明](../architecture/security-guardrails.md)。

## 当前链路

```text
候选回复
  → ① Hard Rules：32 个确定性 ruleId
  → ② Semantic Reviewer：按开关与触发条件 enforce / shadow
  → 聚合：pass | observe | revise | block
      ├─ pass / observe → 继续
      └─ revise / block → 确定性最小修复或 ReplyRepairAgent（最多一次）
                          → 二审 → repair regression gate → 收敛
  → OutboundReplySanitizer
  → TurnOutcome：reply | guardrail_blocked | handoff | skipped
```

### ① Hard Rules

`output/rules/output-rule-catalog.ts` 是唯一权威，当前 32 个 ruleId：

| action    | 数量 | 语义                             |
| --------- | ---: | -------------------------------- |
| `observe` |   11 | 记录证据，当前文本仍可发送       |
| `revise`  |   15 | 首版不可发，进入一次有界修复     |
| `block`   |    6 | 高风险首版不可发；自救失败后硬拦 |

规则读取回复文本、本轮工具结果、短期会话文本和记忆快照等已存在证据。规则必须对齐 ground truth
或封闭词形；用正则猜开放语义的规则应留在 observe 或退役。

### ② Semantic Reviewer

`SemanticReviewerService` 只在高风险或 semantic contract 命中时运行，消费裁剪后的
`GuardrailReviewPacket`。enforce / shadow 由托管配置控制；低置信 veto 会降为 observe，
review 模型缺配时语义档降为未开启并告警。

Reviewer 只产出 finding，不改文案。判断“没有证据”前必须先核查证据包是否遗漏或截断字段。

### ③ 有界修复与收敛

`OutputGuardrailService` 只读；真正的文本修复由 Runner 编排：

1. 优先做确定性剥围栏、剥推理残文或拆 JSON 信封；
2. 其余交给无工具的 `ReplyRepairAgent`；
3. hard cap 为一次，修复后再审；
4. regression gate 防止结构坍缩、事实/极性/承诺状态被改坏；
5. 不可恢复问题失败时收敛为 `guardrail_blocked/outbound`，可恢复低风险残留按既定规则 fail-open。

`replan` 已退役。修复不能重进 Generator、重调工具或重复副作用。

## 观测与治理

- `guardrail_review_records`：有信号回合的首版、修复版、两次裁决与 semantic verdict；
- `message_processing_records.guardrail_output`：流水紧凑摘要；
- `agent_execution_events`：semantic review 的运行与 finding 统计；
- 最终质量审计必须看 `reply_preview`，不能只审首版；
- 新规则默认 observe，生产精确率达标后才能升 revise / block；
- 规则增删与 Prompt 教侧配对必须同步 [Prompt 规则台账](../prompt-rule-ledger.md)。

## 学习要点

- Prompt 预防、Tool 守动作、Output 验收，三者不是重复实现同一条规则。
- 守卫检测可以广，修改权必须窄；任何 LLM 修 LLM 回路都要有确定性 hard cap。
- shadow 是灰度和取证机制，不等于线上 veto。
- 机器判例不会自动变成 BadCase；离线复核结果必须经人审、PR、测试和灰度才能影响热路径。
