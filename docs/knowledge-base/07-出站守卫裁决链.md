# 出站守卫裁决链（确定性规则 → 有界收敛）

Output 是 Input / Prompt / Tool / Output 四个作用位中的最终出站验收。它不再调用第二个模型
复审主 Agent，只处理可复算信号。

```text
候选回复
  → 精确长段落去重
  → Hard Rules：24 个 ruleId（19 执行档 + 5 observe 哨兵）
  → pass | observe | repair | replan
      ├─ pass / observe → 继续
      └─ Runner 按 repairMode 执行一次修复
          ├─ replan → 无已提交副作用时，同参数重进 Generator
          └─ rewrite → 机械最小修复或无工具 ReplyRepairAgent
          两路 → 同一规则二审 → 适用的修复回归检查 → 收敛
  → OutboundReplySanitizer
  → Runner resolution：reply | handoff | skipped
```

## 规则边界

当前规则只含：

- 模型格式异常、内部实现泄漏、元叙述旁白；
- 身份/经历造假教唆、歧视性筛选、籍贯探问、名额承诺等封闭高风险词形；
- booking/改约/线上面试位置、明确 no-match 门店状态、高置信品牌回指等工具回执对账。
- 零查询轮的查询完成宣称、无来源的岗位数字，以及报名/取消/改期的完成态对账。

开放的岗位语义、承诺质量、重复语义和候选人不满意程度由主 Agent 理解，不用正则或第二模型
评分。精确重复由 sanitizer 机械删除；handoff 承诺由 TurnOutcome 与实际副作用对账。
仅有 observe 命中时，Output 保留 `ruleIds` 并返回 `pass`，不启动修复。
旧 revise / block 都映射为 repair；原严格规则保留 `allowFailOpen: false`，旧记录按原值兼容读取，
`recoverability` 退出运行时。Input 审查为 pass / handoff；风险命中时不进入 Agent，Runner 以 handoff 和 guardrail.phase=inbound/source=input_guardrail 表达结果，保留既有 conversation_risk 意图。

## 规则定义与目录

Catalog 仅管理可独立识别与治理的规则。Input、Tool、Output 各持一份子目录，
`guardrail/catalog.ts` 只聚合这三份目录；Input 与 Output 执行器直接引用规则定义，Tool 目录
用于审计登记，门禁仍在工具域执行。阅读 Output 时先看
`output/output-rule-catalog.ts` 的默认 action、修复属性、证据来源和 `source/entrypoint`，
再沿入口看检测函数，最后回到 `HardRulesService` 看调用顺序。

检测函数用 `createOutputRuleFinding` 引用已登记 ID，不再各写一份默认 action；未登记会报错。
只有显式声明 `per_hit` 的规则可提供场景化修复反馈。源码审计测试同时检查规则登记与实际调度，
能发现“写了规则没登记”以及“登记了却没接入执行”。

修复回归直接看 `reply-repair/repair-regression.util.ts`，恢复分支看
`runner/agent-runner.service.ts`，清洗看 `output/sanitizer/outbound-reply-sanitizer.ts`，
并结合各自行为测试理解。回归结果、恢复理由码和判据、清洗步骤留在所属实现中，不另设登记目录。

## 有界修复

1. Runner 根据守卫派生的 `repairMode` 选择路径，hard cap 一次；
2. rewrite 优先剥围栏、推理残文或 JSON 信封，其余交给无工具的 `ReplyRepairAgent` 局部修改；
3. 重生成若由真实工具明确短路为 `handoff/skipped`，优先保留工具终态，不伪造二审；纯无工具空产物仍按修复失败处理。其余产物再过相同确定性规则，rewrite 复用首版工具轨迹，replan 使用重生成版工具轨迹；
4. regression gate 防结构、极性、日期和既成 booking 状态退化；机械剥离/拆封跳过比较，
   replan 首版的违规岗位内容豁免结构与极性比较；
5. rewrite 高风险或 `allowFailOpen: false` 的违规仍失败则转人工，允许放行的低风险残留按既有规则留档 fail-open。

replan 档（当前只有 `job_query_claim_without_query` / `job_fact_without_provenance`）
用完全相同参数重进 Generator 一次，不注入反馈、不裁工具集；
重生成结果走二审与 regression gate，首版永不回退、不 fail-open，仍不过则 `replan_exhausted`
转人工。首版已有已提交副作用时，Runner 禁止重进 Generator、降级 rewrite 并告警。
2026-07 的旧 replan 带反馈重进 Generator 并裁工具，07-27 删除，不得复活。

真实首审/二审与最终处置分开：Runner 返回 `resolution: { outcome: reply | handoff | skipped, reasonCode? }`，
Trace 使用 `finalOutcome`；advisory 不产生最终处置。仅元叙述旁白时 skipped，保留已有工具意图且
不新增介入；纯推理/工具残文直接 handoff。空修复和悬空产物不伪造二审，按既有资格回退或转人工。

## 目录与证据所有权

- `guardrail/output/`：审查门面、规则公共类型与 `output-rule-catalog.ts`；`rules/` 包含具体规则、
  调度和岗位事实信号工具；`sanitizer/` 负责确定性清洗。
- `reply-repair/`：修复模型、修复上下文、修复证据包和回归闸。
  `RepairEvidenceBuilder.build(BuildRepairEvidenceInput)` 产出 `RepairEvidencePacket`，
  供 `ReplyRepairAgent` 拼装修复输入；它由 `AgentModule` 注册，GuardrailModule 不再导出。
- `runner/`：选择并执行一次修复、组织二审与回归检查、收敛 outcome。Replay 定局后由
  `TurnOutcomeInterventionService.commit()` 独立提交人工介入，`TurnFinalizer` 只收尾记忆。

证据包保留既有数据形状，迁移不改变规则与 Prompt。Output 自己读取规则所需输入做确定性
对账，不消费修复证据包，也不因曾有 `output/llm/` 目录而获得模型审查职责。
