# 外部动作记录与恢复

本实现对应六阶段方案的阶段三，以 2026-10-21 评审补充为准。执行记录负责同一意图的执行纪律，不承诺跨外部平台与本地数据库的全局“恰好一次”。业务查重继续由业务服务负责；手机号＋岗位不是永久动作 ID。

## 部署与开关

分阶段部署约束：本 PR（C）只允许 `observe` 验收。生产工具的 `logicalTurnId` / `inputOccurredAt` 由后续回复持久化 PR（D）接线；必须在 D 已部署且完成身份链路验收后，才能启用 `execute`。单独启用 C 的执行档会拒绝缺少持久身份的动作，这是故意保留的安全门，禁止用临时 UUID 或当前时间伪造稳定身份来放行。

执行档若海绵接受报名但未返回工单号，动作保持 unknown，阻止同资源新意图重提并进入核实；观察档仍保留原有表单转人工防重提逻辑。


先在测试库单独执行 `20261021090000_agent_action_records.sql`、`20261021093000_action_ops_event_projection.sql` 与 `20261021130000_version_booking_projections.sql`，核对权限、RPC 和索引，再部署应用。事件迁移依赖原有 `ops_events`，投影迁移依赖原有长期记忆表；观察档部署也需要这些 RPC。回复计划的扩展表另见回复执行模块的迁移。不要连带执行仓库中历史待迁移文件。生产迁移、生产发布及切执行档均需单独确认。

| 配置 | 默认值 | 行为 |
| --- | --- | --- |
| `ACTION_EXECUTION_MODE` | `observe` | 记录及 would-block 观测；不依据观察记录跳过原有外部调用 |
| `ACTION_EXECUTION_CUTOVER_AT` | 空 | 执行档必填；只接纳边界之后、已持久化身份的输入 |

执行档回退至 `observe` 或 `off` 时必须保留切换边界；已有执行档的成功、未知及在途义务继续受保护，不能借回退绕开。观察记录不能直接升级为执行凭据。存储故障在从未启用执行档时只降低观察覆盖；执行档或已有切换边界时停止新派发。配置不合法启动即失败。

动作记录观察档与阶段四的已完成动作保护是不同开关范围：原有业务门禁、最新输入检查和经批准的重放安全修复仍生效。七套在途工单窗口由阶段五单独管理，保持旧口径。

## 状态及恢复入口

动作身份包括企业、执行账号、原始意图版本、动作种类与目标；另校验聊天、逻辑回合与参数摘要。原始输入时间不能替换为重试时间。登记后使用数据库资源锁和行锁领取执行权；实际发送前再次检查权限与领取归属。

首次登记在同一企业和 resource 的事务锁内，将最近已登记动作保存为 `previous_action_id`；同键重放不重写关联，正文清理后仍保留该审计链。关联范围与资源冲突域一致，不按账号或动作类型额外拆分，各动作仍保留自己的执行账号。取消与改约共享工单资源；取消后重新报名通过原手机号＋岗位的 booking 资源关联前次报名，而不是跨资源猜测最近一次取消。可用原报名结果的工单号查阅对应取消链，但不新增查重或放行规则。该字段只表示登记先后，不证明前次成功、新意图合法或当前目标已满足；未决阻挡和业务校验保持原样。

| 状态 | 恢复行为 |
| --- | --- |
| registered | 尚未调用外部，可取消或领取；不会由扫描器擅自开始业务动作 |
| executing / unknown | 查询或接受可靠回调；租约过期只授予核实权，不能再次派发 |
| succeeded / pending | 外部已成功，只补本地状态；不能把补账失败展示为业务失败 |
| succeeded / complete | 读取原结果，不再派发 |
| failed | 必须有“本次请求未生效且已终止”的证据；只有显式可重试的失败才能重新领取 |
| cancelled | 只允许取消未派发动作，不得复活 |

成功与 `local_sync=pending` 同次事务保存。原外部结果写入最多尝试两次；仍失败时提交只负责结算/补账的修复队列。数据库和队列同时失败时，预先保存的 executing 行仍在，扫描器会发现它。进程内已知成功保留为真实成功；崩溃后没有保存的成功证据不能凭空恢复，只能核实或交人工。

核实每分钟最多领取 25 条、整轮预算 30 秒、单次只读查询最多等 5 秒，最多 6 次自动尝试，原输入起 24 小时为默认自动核实截止。具体外部能力未验证前不使用其“幂等”注释自动重送。晚到的可靠终态证据在截止之后仍能进入结算；原始派发尝试 ID 与核实任务 owner 分开保存，旧尝试证据不混入后来尝试。相互冲突的证据交人工。

延迟提醒允许使用持久回复计划中首次冻结的 `recoveryWindowStartedAt` 作为这 24 小时的起点，避免数日前的报名时间让到期提醒一开始就过期。该时间不得早于原输入或晚于当前时间一分钟，并纳入参数指纹；重试不得推进时间窗，结果未知的旧动作不能借此重开。切换执行档和 90 天保留限制仍检查原始 `occurredAt`，不以提醒时间替代。

工单当前投影由 `apply_active_booking_projection` 在候选人共享行上持锁比较原事件版本，所有 set/clear 入口共用此 RPC。取消成功先留下版本墓碑，即使供应商列表暂未收敛，旧报名也不能复活指针；较老改约不得替换较新约面时间。不同聊天对同候选人写入不同工单时，事务内合并保留两者。相同版本重试不改投影。取消全量指针还保留候选人级水位，阻止此前未落本地的旧工单迟到插入。JSON 公共指针形态、排序、最多 10 笔和七套业务窗口保持原样；独立 `active_booking_versions` 列记录版本与墓碑，在仍有旧动作可恢复时不得清理。

严格补账的数据库读取、投影与画像 RPC 请求均显式限时 5 秒；画像字段在行锁内按原 updatedAt 拒绝旧事实。Redis 租约与数据库不构成跨系统事务：请求超时或调用方失锁不证明远端写入已撤回，工单/画像的数据库版本条件才是旧结果不覆盖新结果的最终保护。部署必须先加迁移，再滚动切换全部投影写入者；回滚到旧的直接覆盖写实现时不具备这个保证。

后台本地补账与 live worker 共用 `conversationProcessingLeaseKey(chatId)`；取不到会话锁就等待下次。补写前复核归属，失去租约不标完成。工单补账读取当前供应商投影；旧报名不恢复已取消工单，旧改约读取当前约面时间但不得越过较新本地版本；取消后的查询仍显示有效时保留待补账，取消墓碑已落地。收资表单按摘要 CAS，身份事实按原发生时间保留较新信息。没有可靠当前状态时保留 pending。

收资办结身份与邀请记录的 Redis 合并写使用字段原始字节和 hash generation 的 Lua CAS。读取只为已存在 hash 补代际标识，不续期；写时同时校验字段与代际，避免同字段并发丢更新以及过期重建后的 ABA。身份按 extractedAt 保留较新字段，邀请按 invitedAt 保留较新同群记录；CAS 冲突不原地盲重试，抛错保留待补账。后台补账要求会话 hash 已存在，不复活已过期状态；正常首次写仍可在原快照确认为缺失、且尚无其他写入者创建 hash 时初始化。

扫描器只处理 execute 记录，观察记录不会产生后台业务补账或人工核实告警。修复队列用尽、执行档结算未确认和需要人工核实均有可去重告警。

## 已接入边界与能力限制

报名、取消、改约在供应商实际写请求处登记；拉候选人入群、补拉接客 bot 和兼容性后续邀请分别登记。发门店位置、预约地址及报名/取消通知各有独立动作。普通回复、回执、降级回复和群发按不可变内容分段登记，见回复/群任务实现。

Sponge 请求的未知结果目前没有经过验证的按请求号终态查询，查询到“当前有工单”不代表原请求已经终止。群成员已存在也不能证明某次超时请求终止。因此这些未知结果保留证据并转人工，不自动重发。通知 webhook 的受理成功仅代表该通知接口已受理，不表示运营已阅读；邀请卡受理不表示候选人已进群。

仅返回介入意图的工具不视为外部成功。尚未迁入新账本的安全暂停、群满/拒邀告警保持原有保障，不能宣称受本动作账防重保护。

## 人工核实

通过受控运维数据库连接读取待处理动作；仅 `service_role` 可调用人工核实 RPC，不新增公开 HTTP 重试接口。查询始终按企业、状态、小批次及时间索引限制范围。首次 unknown 即可查询，超过预算后 `review_required=true`，状态仍保持 unknown。

人工使用 `review_agent_action(jsonb)` 必须提供：

- `corpId`、`actionId`、冻结的 `accountId`、`payloadHash`、原 `dispatchAttemptId`。
- 实际操作者 `operator`、可追溯的证据出处 `basis`（工单/回调/供应商核实编号，避免复制个人信息）。
- `conclusion`：`succeeded`、`failed`、`leave_unknown` 或 `retry_local_sync`。
- 终态结论须附 `completion`，明确 `requestTerminated=true`；失败还须 `kind=definitive_no_effect`；成功须给出可补账结果。

RPC 在同一事务保留不可修改的审计记录并结算。失败结论不自动授权重试，成功结论不能被人工降级。`retry_local_sync` 仅重开成功动作的本地补账预算，不执行任何外部请求。不能确定时使用 `leave_unknown`。如确需承担重复风险发起新动作，应另行获得用户明确决定并关联原动作；本实现不提供自动换号绕过未知的路径。

## 保留、回滚与验证

每 10 分钟按索引分批清理超过 90 天的正文和结果；每批最多 100 条，每轮最多 10000 条、30 秒预算，下一批开始前续租并检查预算，到限后留待下一轮。动作与回复计划各自使用分布式互斥。off/observe 档不承担执行恢复义务，可清理非终态正文而不改写状态；execute 档仅清理已完成且补账完成的记录，未决动作及待补账记录受保护。保留动作身份墓碑，RPC 返回处理的动作行数而非关联证据行数。输入超过 90 天不得自动生成新操作。审计保留操作者、依据编号和结论，普通完成记录的审计结果正文同步清理。

数据库扩展不删除旧字段或表，旧应用继续可运行。回滚应用不能删除新表，也不能移除切换边界；已经派发的 execute 动作需要保留恢复能力。执行档启用之前应先验收观察样本、回复回调路由、凭证解析与具体供应商能力。

可复验资产：`tests/biz/action-execution/*.spec.ts`、`action-records.postgres.sql`、`action-review.postgres.sql` 与 `action-records-concurrency.py`。SQL 只针对隔离数据库运行；并发脚本拒绝非 `cake-runtime-pg-*` 容器名。真实外部幂等能力与生产 Agent 业务回归必须另有外部证据，不能由这些单测替代。

清理修复迁移：`20261023060000_runtime_retention_batches.sql` 在原运行时迁移之后执行；先迁移再部署应用，兼容旧单批调用。回滚应用不恢复已清理正文，身份墓碑不受影响。
