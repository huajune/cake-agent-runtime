# 消息存储迁移

适用于 `20261125075900`、`20261125080100` 和 `20261125081000`。先在测试环境演练，按相同顺序排入生产发布窗口。已有渠道消息与处理流水的标识保持原值。

## 发布顺序

1. 保存数据库可恢复备份和对应的应用版本。先执行[停写旧格式的准备迁移](../../supabase/migrations/20261125075900_prepare_storage_cutover.sql)。旧版本会用完整正文继续读写。
2. 使用已确认的目标数据库连接执行 `psql -X -v ON_ERROR_STOP=1 -f scripts/backfill-runtime-bodies.sql`。脚本按渠道消息、测试执行和动作主键每批提交至多 250 行。它还原渠道原始载荷和测试响应，从动作实际采信的回执取出当前结果和证据。中断后可重跑。以旧标记仍非空的行数核对进度，动作回执或归属不匹配会中止当批。[分批脚本](../../scripts/backfill-runtime-bodies.sql)
3. 暂停旧应用、后台写入者和旧导出，等待在途写入结束。执行仓库的正常数据库迁移命令。准备迁移可重复执行。流水迁移转换步骤及工具归属，将历史请求、响应迁入快照的两列。被替代和无可读内容的历史快照会退出详情，主流水仍在。原始步骤无法确认归属时保留可确认的工具清单。正文迁移处理剩余行，删除旧列、触发器和配置。任一失败事务可安全重跑。[流水迁移](../../supabase/migrations/20261125080100_processing_snapshot_storage.sql) · [正文迁移](../../supabase/migrations/20261125081000_retire_body_storage_markers.sql)
4. 全部迁移成功后切换应用并恢复流量。验证新流水和快照按 `message_id` 查询，事件按 `trace_id` 匹配。用一条升级前的流水核对回合上下文与原保存时间，用带工具的升级后流水在「模型调用原文」逐次核对 HTTP 状态、请求体和响应体。原文只对总部开放，列表与普通详情按原有投影加载。抽查一条带媒体字段的聊天和一条有多个回执的预约，核对渠道原文、测试正文、已采信工单和动作恢复状态。生产验收后回写数据库现状文档。

## 回滚

切换前恢复旧应用可继续读取分批还原的正文。开始删列后需要同时恢复数据库备份和匹配的旧应用，回滚点应涵盖切换前最后一笔外部动作。若已经恢复流量，先停止派发并核对切换后的企微受理与回执，避免重放外部动作。
