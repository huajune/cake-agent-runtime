# 普通回复分段投递的 200 倍峰值压测

2026 年 11 月 26 日，把生产普通回复峰值放大 200 倍后，隔离数据库连续三分钟处理完 70,200 个分段与结算请求。按回合实际开始时点回放时，20 个并发处理槽出现排队，95% 的回合在入队后 127.5 秒内等到首段被模拟企微受理。用预先生成的回复完成了这组实测，真实模型的时间另行估算。

PR #1589 将每段发送前的两次数据库访问合为一次。在一个事务里核对回合、登记动作并取得发送权。企微受理后用一次事务保存该段回执和动作结果。两段成功发送共四次分段请求，整轮结算另一次。在隔离库里，两个进程争同一段时只有一个能取得发送权。[分段事务](../../supabase/migrations/20261125100000_ordinary_reply_segment_io.sql) · [宕机与受理回执回归](../../tests/channels/wecom/message/delivery/reply-chain.integration.spec.ts)

## 首条多久能发出，队列会积压多少

首条计时从向 Redis 提交任务开始，到模拟企微受理第一段结束。两次独立实验都固定 20 个并发处理槽，完整跑到最后一轮确认输入。各轮使用不同的聊天，回复文本已经生成。P95 表示 95% 的回合在该时间内等到首段受理。

| 一分钟输入 | 从入队到首段 P50 / P95 | 从 worker 接手到首段 P95 | 等候队列最高值 | 第 60 秒仍等候 | 第 60 秒后多久清空 |
| --- | --- | --- | ---: | ---: | ---: |
| 实际回合开始节奏，3,600 轮、7,600 段 | 64.9 秒 / 127.5 秒 | 447 毫秒 | 2,389 轮 | 2,369 轮 | 137 秒 |
| 按高峰结算节奏构造，4,200 轮、9,600 段 | 109.2 秒 / 189.8 秒 | 450 毫秒 | 3,557 轮 | 3,240 轮 | 182 秒 |

两组的时间都主要花在等 worker，第一组排队的 P95 为 127.0 秒，第二组为 189.3 秒。第一组 7,600 段、第二组 9,600 段均按发送尝试 ID 和回执摘要逐条核对。每个模拟企微请求恰好受理一次，每个动作都能找到对应回执，全部回合最终确认了输入。两组分别执行 36,800 和 44,400 次数据库请求，包括建回合、存分段、开始投递、逐段领取和写回执、整轮结算、本地收尾标记及确认输入。[队列与受理计时](../../tests/biz/reply-execution/load/queue.cjs) · [逐段核对 SQL](../../tests/biz/reply-execution/load/verify-receipts.sql) · [原始分位数与回执核对](ordinary-reply-peak-load-results.json)

## 数据库能承受多少请求

独立向真实 PostgREST 和 PostgreSQL 注入分段领取、分段回执和整轮结算请求。无论先前请求是否返回，都按原定时刻继续注入。每分钟 23,400 次，平均每秒 390 次，最忙一秒送入 2,400 次。这里测得的 RPC 耗时包括连接池排队和数据库处理。

| 回放时间 | 完成 / 请求数 | RPC P95 / P99 | 最忙一秒完成 | 同时在途最高 | 分段回执 | 错误 / 死锁 |
| --- | ---: | --- | ---: | ---: | ---: | --- |
| 1 个峰值分钟 | 23,400 / 23,400 | 186 / 517 毫秒 | 1,645 | 758 | 9,600 | 0 / 0 |
| 连续 3 个峰值分钟 | 70,200 / 70,200 | 257 / 775 毫秒 | 1,667 | 1,167 | 28,800 | 0 / 0 |

数据库配额为 2 vCPU、2 GiB 内存，PostgREST 连接池为 24。两个 CPU 核在最忙的采样间隔接近用满，部分请求排到了下一秒。连续三分钟时，单次 RPC 最长 1.67 秒，数据库内存峰值约 1.0 GiB。第 180 秒还有 159 个请求进行中，到 180.1 秒全部完成。队列实验和数据库实验分开执行，前者测首段受理等待，后者测数据库能否独立接住这三类请求。生产中的监控报表、其他业务写入、外部限流和故障重试会占用额外容量。[数据库回放与统计](../../tests/biz/reply-execution/load/database.cjs) · [原始统计](ordinary-reply-peak-load-results.json)

## 流量和时间的口径

- 观测期为北京时间 11 月 19 日 10:45 至 11 月 26 日 10:45。11 月 23 日 13:15:17 起的 60 秒内，已受理过分段的普通回复共有 18 轮开始，合计 38 段。第一组按每一轮的实际开始时点和段数复制 200 份。开始时间取自 `agent_reply_turns.created_at`，企微进入回调或 Redis 队列可能更早。[回合开始时点与段数](../../tests/biz/reply-execution/load/peak-turn-starts.json)
- 11 月 25 日 15:44:35 起的 60 秒内有 48 个分段动作登记、48 份受理凭证、21 个结束回合。按秒乘以 200 作为数据库的输入曲线。第二组队列使用同一分钟的回合结束节奏构造等量到达，按 3,000 个两段、1,200 个三段匹配总量。三个数字分别来自成功动作创建、匹配回执写入和结束回合的最后更新时间。[逐秒计数，依次为登记、回执、结束回合](../../tests/biz/reply-execution/load/peak-minute.json)
- 队列使用真实 Redis、Bull、回复投递服务和数据库。每次 RPC 加入 91 毫秒往返网络时延，模拟企微在 35 毫秒后受理。模型生成、工具调用、打字间隔和真实企微网络均未计时。生产候选人的实际等待还会包含这些时间，接口受理后到达手机也有额外延迟。
- 为估计模型与工具占用 worker 的影响，另取同期 1,089 个已完成的两段或三段回合。从回合创建分别量到首份和末份受理回执，按段数分组，再按总耗时分为 20 档。把两段、三段的历史耗时按各档样本数抽入第二组 4,200 轮，固定 20 个处理槽，末段受理时释放槽位，峰值分钟后停止注入。100 次模拟的首段等待 P50 中位数为 **1.82 小时**，P95 中位数为 **3.32 小时**，各次 P95 为 3.24 至 3.39 小时。这是按历史耗时推算，线上 200 倍流量的实测值仍未知。[历史分组数据](../../tests/biz/reply-execution/load/service-time.json) · [排队模型](../../tests/biz/reply-execution/load/queue_estimate.py)

## 复现

本机需要 Docker、Node.js、pnpm 和 Python 3。从已安装项目依赖的工作树执行以下命令。

```sh
pnpm run build
bash tests/biz/reply-execution/load/run.sh
```

脚本创建仅有回环网络的 PostgreSQL 16、PostgREST 和 Redis 容器，加载迁移、启用动作正文压缩，预置 50,000 条历史动作、50,000 份回执和 8,000 个历史回合。容器在结束后清理，结果 JSON 保存在脚本打印的临时目录。[运行脚本](../../tests/biz/reply-execution/load/run.sh) · [本次结果](ordinary-reply-peak-load-results.json)
