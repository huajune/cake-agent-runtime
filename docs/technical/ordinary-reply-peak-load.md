# 普通回复分段投递的 200 倍峰值压测

2026 年 11 月 26 日，在 #1588 和 #1589 的五份迁移全部执行后回放生产峰值。按真实回合开始时点放大 200 倍，20 个处理槽下，从入队到首段获模拟企微受理的 P95 为 **129.6 秒**，从处理槽接手到首段受理的 P95 为 **457 毫秒**。数据库单独连续回放三个峰值分钟，完成全部 70,200 个请求。[联合迁移顺序](runtime-storage-batch.md#发布顺序) · [原始数据、环境和脚本指纹](ordinary-reply-peak-load-results.json)

PR #1589 将每段发送前的两次数据库访问合为一次。在同一事务里核对回合、登记动作并领取发送权。企微受理后用一次事务保存该段回执和动作结果。两段成功发送共四次分段请求，整轮结算另一次。两个进程争同一段时只有一个能取得发送权。[分段事务](../../supabase/migrations/20261125100000_ordinary_reply_segment_io.sql) · [宕机与受理回执回归](../../tests/channels/wecom/message/delivery/reply-chain.integration.spec.ts)

下文的排队时间按当次实验的 20 个固定处理槽计量。本批应用支持后台设置 1 至 100 槽，生产首次部署后设置 50。发布后的首段时延和队列等待量须按生产新档位观测。[实际注册数与生产首档](../workflows/deploy-guide.md#主聊并发首档)

## 首条多久能发出，队列会积压多少

首条从向 Redis 提交任务计时，到模拟企微受理第一段结束。两组分别运行到所有输入确认。每轮属于不同聊天，回复文本预先生成。P95 表示 95% 的回合在该时间内等到首段受理。

| 一分钟输入 | 从入队到首段 P50 / P95 | 从 worker 接手到首段 P95 | 等候队列最高值 | 第 60 秒仍等候 | 第 60 秒后多久清空 |
| --- | --- | --- | ---: | ---: | ---: |
| 实际回合开始节奏，3,600 轮、7,600 段 | 65.6 秒 / 129.6 秒 | 457 毫秒 | 2,379 轮 | 2,359 轮 | 138.8 秒 |
| 按高峰结算节奏构造，4,200 轮、9,600 段 | 108.4 秒 / 187.5 秒 | 445 毫秒 | 3,547 轮 | 3,240 轮 | 179.8 秒 |

第一组等处理槽的 P95 为 129.2 秒，第二组为 187.0 秒。两组模拟企微分别受理 7,600 和 9,600 段，每个请求恰好一次。按原派发尝试逐条匹配动作状态、结果及证据，重新计算新回执内容的 SHA-256，全部通过。所有回合最终确认输入。两组分别执行 36,800 和 44,400 次数据库请求，包括建回合、存分段、开始投递、逐段领取与写回执、整轮结算、本地收尾及确认输入。[队列计时](../../tests/biz/reply-execution/load/queue.cjs) · [逐段核对 SQL](../../tests/biz/reply-execution/load/verify-receipts.sql)

## 数据库能承受多少请求

独立向 PostgREST 和 PostgreSQL 注入分段领取、分段回执及整轮结算三种请求，按预定时刻送入。每分钟 23,400 次，平均每秒 390 次，最忙一秒计划送入 2,400 次。RPC 耗时从实际发起请求算起，包括连接池排队和数据库处理。

| 回放时间 | 完成 / 请求数 | RPC P95 / P99 | 最忙一秒完成 | 同时在途最高 | 分段回执 | 错误 / 死锁 |
| --- | ---: | --- | ---: | ---: | ---: | --- |
| 1 个峰值分钟 | 23,400 / 23,400 | 52.8 / 143.9 毫秒 | 2,106 | 314 | 9,600 | 0 / 0 |
| 连续 3 个峰值分钟 | 70,200 / 70,200 | 34.4 / 245.1 毫秒 | 2,384 | 773 | 28,800 | 0 / 0 |

数据库配额为 2 vCPU、2 GiB 内存，PostgREST 连接池为 24。连续三分钟回放时，数据库 CPU 在最忙采样间隔使用两核配额的 95.6%，内存峰值为 1138 MiB。单次 RPC 最长 461.2 毫秒，按原定注入时点计至返回的 P95 为 42.4 毫秒。第 180 秒采样时还有 2 个请求在途，随后全部完成。队列实验另行运行。生产中的其他读写、真实网络及供应商限流都会影响容量。[数据库回放与统计](../../tests/biz/reply-execution/load/database.cjs) · [原始分位数](ordinary-reply-peak-load-results.json)

## 流量和时间的口径

- 观测期为北京时间 11 月 19 日 10:45 至 11 月 26 日 10:45。11 月 23 日 13:15:17 起的 60 秒内，已受理过分段的普通回复共有 18 轮开始，合计 38 段。第一组按每一轮的实际开始时点和段数复制 200 份。开始时间取自 `agent_reply_turns.created_at`，企微进入回调或 Redis 队列可能更早。[回合开始时点与段数](../../tests/biz/reply-execution/load/peak-turn-starts.json)
- 11 月 25 日 15:44:35 起的 60 秒内有 48 个分段动作登记、48 份受理凭证、21 个结束回合。按秒乘以 200 作为数据库的输入曲线。第二组队列使用同一分钟的回合结束节奏构造等量到达，按 3,000 个两段、1,200 个三段匹配总量。三个数字分别来自成功动作创建、匹配回执写入和结束回合的最后更新时间。[逐秒计数，依次为登记、回执、结束回合](../../tests/biz/reply-execution/load/peak-minute.json)
- 队列使用真实 Redis、Bull、回复投递服务和数据库。每次 RPC 加入 91 毫秒往返网络时延，模拟企微在 35 毫秒后受理。模型生成、工具调用、打字间隔和真实企微网络均未计时。生产候选人的实际等待还会包含这些时间，接口受理后到达手机也有额外延迟。
- 为估计模型与工具占用 worker 的影响，另取同期 1,089 个已完成的两段或三段回合。从回合创建分别量到首份和末份受理回执，按段数分组，再按总耗时分为 20 档。把两段、三段的历史耗时按各档样本数抽入第二组 4,200 轮，固定 20 个处理槽，末段受理时释放槽位，峰值分钟后停止注入。100 次模拟的首段等待 P50 中位数为 **1.82 小时**，P95 中位数为 **3.32 小时**，各次 P95 为 3.24 至 3.39 小时。这是按历史耗时推算，线上 200 倍流量的实测值仍未知。[历史分组数据](../../tests/biz/reply-execution/load/service-time.json) · [排队模型](../../tests/biz/reply-execution/load/queue_estimate.py)

## 复现

本机需要 Docker、Node.js、pnpm 和 Python 3。从已安装项目依赖的工作树执行以下命令。

```sh
pnpm run build
bash tests/biz/reply-execution/load/run.sh
```

脚本创建仅有回环网络的 PostgreSQL 16、PostgREST 和 Redis 容器，按版本顺序应用全部五份迁移，在删列后的结构上预置 50,000 条历史动作、50,000 份回执和 8,000 个历史回合。容器在结束后清理，结果 JSON 保存在脚本打印的临时目录。[运行脚本](../../tests/biz/reply-execution/load/run.sh) · [本次结果](ordinary-reply-peak-load-results.json)
