## 生产证据与处置

生产基线为 v11.14.2、默认 observe、切换边界为空。调查锚点为北京时间 2026-10-27 13:00–14:00；群任务追踪延伸至原任务最终完成。数据库查询使用时间索引或已知主键，5 秒超时，最多 100 行；Redis 仅访问已确认的会话与任务键。未扫描全部历史。

### 三条入群 pending

三条动作时间分别为 13:08:34、13:25:55、13:55:41，均为 `wecom.group_add_member / observe / succeeded / pending`，供应商 code=0、请求已终止。该结果证明邀请被受理，不证明候选人已加入群。

根因是 Redis Lua 的空值兼容性：生产返回的快照省略 `raw` 空字段。代码仅判断 `raw === null`，将缺失字段错误地编码为“字段存在且为空字符串”，首次写 invitedGroups 的 CAS 必然失败。三个会话仍存在且均无 invitedGroups，符合该路径。只读生产 Lua 复核返回 `generation` 而无 `raw`。

修复：读取快照时把省略的 raw/generation 归一为 null，继续保留原始字节与 hash 代际比较，不削弱并发、过期重建和后台禁止复活保护。

已针对这三条记录进行限定补账：复核当前主键记录仍为 observe 成功，采用修复后的 RedisStore CAS，只合并邀请记忆，保留原邀请时间和较新同群记录，不延长 TTL、不重建过期会话；成功后按原 owner/fence 标记同步完成。三条均读回 `local_sync=complete` 且邀请记忆存在，外部邀请请求为零。没有将 observe 记录升级为 execute。

主回合回复核对：前两条回复表述为“邀请已发送”；第三条回复表述为“已拉进群”，比供应商受理证据更强。该口径问题不应拿来证明入群已完成，亦不作为恢复验收通过依据。

### 六次回调拒绝

13:45:35–13:45:36 的六次事件均为企业级 `messageType=10001`、source=0、带 imRoomId 的企微系统消息，缺少 contactType。它们不是纳管发送成功回执；此前只看错误日志不能推断发送回执匹配失败。

修复仅针对带房间身份的该类系统事件，将缺失 contactType 归为 UNKNOWN，交给现有过滤规则处理，不触发候选人回复。普通消息、邀请卡和发送回执仍须满足原校验，不推断个人联系人或发送成功身份。

### 两条群发送失败

同一原任务两条 send job 在获取同 bot 发送锁期间超时，未派发外部请求。后续原任务重试成功，结果缓存分别记录北京时间 14:12:20、15:00:18 为 sent。无需补发，也没有证据支持修改串行锁或放宽发送间隔。

补回归断言：获取锁失败时无发送、无成功幂等键；原任务随后获得锁仅发送一次。现有同 bot 并发串行测试继续通过。
