# 群任务与复聊的独立执行边界

群任务和复聊不接入主聊动作运行时。`ACTION_EXECUTION_MODE` / `ACTION_EXECUTION_CUTOVER_AT` 只控制主聊；独立任务不创建 `agent_action_records`、`agent_reply_turns` 或 `agent_reply_inputs`，也不依赖其恢复 worker 和逐段回调。

## 群任务

沿用 Cron → Bull plan/prepare/send/summarize、共享消息缓存、bot 发送锁和间隔、同群当日场次去重、品牌轮转、结果快照，以及既有飞书预览/汇总/失败通知。抢单群仍在发送前刷新标签，摘标后不发。主文本、小程序卡片和跟随文本走 `NotificationSenderService` 原渠道接口，不再冻结动作计划或等待动作账本确认。

发送前失败仍可按 Bull 原预算退避重试。实际派发前只在原 Bull job 保存 `sendAttempted`，用于阻止进程中断、部分成功或未知结果后重复发送整批；发送不完整时结果标为待核对，通过既有汇总通知处理。它不改变主聊模式，不生成新任务、不自动补发余段，也不把未知误算成成功。

存量 job 若带原 `dispatchPlan`，只保留一个退役保护分支：已有当日成功标记则跳过；否则保留待核对，拒绝把旧计划当成尚未发送的普通任务重跑。此字段不再由新代码写入；现存旧 job 已核实或过了队列保留期后可以删除该分支。既有用户决定的漏发结案和未知隔离不因代码简化而撤销。

## 复聊

沿用 `FollowUpSchedulerService`、独立 `ReengagementAgent`、`TouchLedgerService` 的 Redis 触达槽/频控，以及 `reengagement_touch_records` 和 Dashboard。场景、当前工单、候选人最新消息、托管权限和冷却条件仍在原链路判断；旧锚点不会仅因早于主聊 cutover 被拒绝。

`ReengagementDeliveryService` 仅复用渠道分段发送和当前主动许可；不打开主聊回复回合，不保存整段计划，不做 SQL 回复恢复扫描。接口明确 `errcode=0` 即受理成功，无需自发回调。未知结果停止本轮，原在途/未知触达槽不重新生成或发送；部分发送不计作完整触达。外部成功后的记账错误保留为本地异常，不能据此再次派发。

升级拉群仍由复聊既有流程在成功触达后触发，使用主动许可；不借主聊动作模式决定是否执行。主聊工具调用同一邀请服务时继续使用主聊动作账本。邀请结果未知时两条路径都停止，不换群盲发。

## 历史与发布

本次退出接入不新增数据库迁移，不删除历史记录、修改生产任务或重发消息。`group_task.message` 历史动作值、已部署 SQL 的旧任务字段/函数保留可读，现行调用方已移除。主聊原输入确认、报名/取消/改约防重复、本地补账和旧主聊 execute 恢复不受此改动影响。

发布前仍需核实实际部署期间有没有产生旧的 **execute** 群任务或复聊义务；若有，须先按原请求与结果处理，不能以移除代码将它们静默结案。这是旧实现退出的一次性数据核对，不是给所有未来定时任务增加主聊跨边界承接。纯 observe 历史不是新的发送授权，未知记录继续隔离。

验证覆盖独立任务在主聊 off/observe/execute 下运行、主聊存储不可用、当前权限关闭、未知停止、旧计划不重放、群标签和限速，以及原调度/通知和主聊回归。所有渠道调用采用替身，不触达真实候选人或群。
