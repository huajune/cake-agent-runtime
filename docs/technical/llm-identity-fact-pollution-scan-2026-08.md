# LLM 轨身份字段污染面扫描（A2，2026-08）

> 执行时间：2026-08-11 18:31–18:40（Asia/Shanghai）  
> 性质：生产只读扫描；未修改 PostgreSQL、Redis、生产数据、环境开关或运行时配置。  
> 口径提示：本文把“无候选人出处”定义为按 A1-B 的逐字/轻归一探针无法复算；它表示事实**不可证实、应进入污染候选集**，不等于已证明字段值必然错误。

## 1. 技术摘要

- **严格 `source=llm/model` 的身份事实中，5/57（8.8%）无可复算候选人摘录，涉及 2/50（4.0%）个会话。**其余 52/57（91.2%）均在同会话近 7 天候选人原文中命中。
- **1 个受影响会话已经进入收资链路。**该会话的 `experience` 在 2 个 `duliday_interview_precheck` trace 的回合入口记忆中可见，其中 1 个 trace 同时调用了 `duliday_interview_booking`；即 1/5 个不可证实字段、1/2 个受影响会话进入过 precheck/booking。
- **当前 50 会话没有仍存储的标量扇出值。**因此本批“不可证实身份事实 ∪ 存量标量扇出”的精确去重并集为 2/50（4.0%）。另有 2 个不同会话发生过标量扇出尝试，但已被 admission gate 拦截，若把“被拦截尝试”也作为风险面，并集为 4/50（8.0%）。
- **08-10 的 drop 增长不是流量或 extract 模型切换造成，主要是姓名门观测扩面。**08-10 相比 08-07，处理 turn 下降 2.2%（1,107 vs 1,132），drop 字段增加 293（826 vs 533）；其中 288 条来自 `auto_greeting_nickname/honorific_suffix`。剔除姓名门后仅增加 54 条（538 vs 484）。
- **无法完成真实 per-model 质量比较。**08-03 以来 3,816 条 `extraction_field_dropped` 事件全部缺 `trace_id` 和 `modelId`；生产 extract 主模型自 07-02 起一直配置为 `deepseek/deepseek-v4-flash`。08-11 出现 11 次 DeepSeek→Qwen fallback，但 fallback 事件同样没有 trace/chat 标识，无法把具体 drop 归到实际 fallback 模型。
- **长期档案严格 `llm/model` 口径为 0，但存在 307 条旧 `source=extraction` 身份事实。**旧链路把运输来源写成 `extraction`，抹掉了原始 producer；这些事实不能诚实归到模型或规则，也不能并入本次严格分母。它们是下一轮数据清理前必须先解决的血缘盲区。

结论：当前有明确依据先隔离复核 2 个会话、优先核对已进 booking 的 1 个会话；没有依据批量清空长期档案或仅凭 drop 总量切换模型。

08-10 相比 08-07：

- 流量：1,107 vs 1,132 turn，**-2.2%**，排除“流量翻倍”。
- 总 drop：826 vs 533，增加 293。
- 姓名门：288 vs 49，增加 239；08-10 的 288 条占当天 drop 34.9%。若以“08-07 全量→08-10 全量”的净增量看，姓名门解释 81.6%；若用 08-07 当日已有的 49 条作为基线，剔除姓名门后仅从 484 增至 538（+11.2%）。

全表只读聚合显示，长期档案六字段中的实际 source 分布为：

| 字段                   | source     |  事实数 |
| ---------------------- | ---------- | ------: |
| age                    | booking    |   1,010 |
| gender                 | booking    |   1,009 |
| age                    | extraction |      84 |
| gender                 | extraction |      67 |
| education              | extraction |     156 |
| **旧 extraction 合计** |            | **307** |

- 严格 `source=llm/model`：0 条。
- `height/weight/experience` 不在当前长期 `profile_facts` schema，长期层天然为 0。
- 旧 `source=extraction` 只记录“经沉淀运输”，不记录原事实来自模型、规则还是候选人摘录；把 307 条全部算成模型事实会夸大，把它们全部排除又会低估潜在模型污染。

本报告因此不对这 307 条给出“无出处率”。在生产清理前，应先用 origin session + evidence 做单独血缘复算；缺 origin 的记录只能进入人工复核池，不能自动删除。

## 6. 范围、数据与度量定义

### 6.1 样本

- 从近 7 天 `message_processing_records` 取最新 50 个有效 `(corp_id,user_id,session_id)`；样本实际覆盖 2026-08-11 16:18–18:38 CST，属于高流量热路径快照，不代表 7 天分层总体。
- Redis 命中 49/50 个 `production:factsv2:*` key；严格串行 HGETALL，只访问这 50 个唯一 key，未使用 SCAN、pipeline 或写命令。
- 长期档案按样本 `(corp_id,user_id)` 索引 join；另对全表只做 source/字段计数聚合，不拉候选人值。

### 6.2 原文复算

1. 从 evidence 中提取成对引号内的候选人摘录；若 evidence 明确内含字段标量值，也允许剥出该值。
2. 仅删除空白与标点并转小写，不做语义相似、同义词或常识推断。
3. 在相同 `chat_id`、近 7 天、`role='user'` 的 `chat_messages.content` 中做 `EXISTS`；数据库只返回 probe id 与命中布尔值，候选人原文未导出。
4. evidence 拿不出确定性摘录，或 7 天原文不命中，均进入“不可证实”候选集；两种状态分开记录。本批 5 条全部属于前者。

### 6.3 生产安全

- 每条 PostgreSQL 查询都在 `BEGIN TRANSACTION READ ONLY` 内执行，并在同一事务设置 `SET LOCAL statement_timeout='8s'`；查询严格串行，无超时。
- 未读取整列 `agent_invocation`，只使用 indexed 时间窗、紧凑观测列与聚合结果。
- 报告不包含候选人姓名、电话、消息原文、字段值或 Redis 凭据。

定量趋势只有少量自然日且 08-07/08-11 都是不完整对照窗口，因此正文使用精确审计表而非趋势图，避免视觉上暗示连续时间序列或因果关系。

## 7. 限制与稳健性判断

1. **最新 50 会话偏向当前热路径。**不可把 8.8% 字段率或 4.0% 会话率外推为全生产总体；发版后应按天分层抽样。
2. **“无摘录”不是“值错误”。**它足以阻止自动信任和触发复核，但不支持直接删除事实。
3. **7 天文本窗会漏掉更早的真实出处。**本批严格事实都来自活跃 session；长期 `extraction` 记录未进入严格分母，避免把历史窗外事实误判为污染。
4. **drop 事件缺 trace/model 血缘。**配置归因只排除了“08-10 主模型切换”，不能产出模型间幻觉率或 fallback 质量差。
5. **drop 字段数不是污染会话数。**姓名/扇出一次可能产生多个字段事件，同一值也可能跨轮重复；诊断同时报告 turn、字段和去重会话。
