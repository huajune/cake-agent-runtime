# 蛋糕的租户、成员和业务账号

总部、河南自招、上海自招各自是一个蛋糕租户，每家外部供应商也有自己的租户。上海智能体组归总部，既孵化产品，也用自己的托管号做招聘业务、收集运营反馈。总部员工有跨租户查看业务的权限，数据始终归实际承接业务的租户。

## 业务范围

| 谁在用蛋糕 | 自己的业务记在哪里 | 能看哪些业务数据 |
| --- | --- | --- |
| 总部员工，包括上海智能体组 | 总部租户 | 全部租户的聊天、托管和运营数据，托管页按组织分组 |
| 河南自招员工、组负责人 | 河南自招租户 | 整个河南自招，包括其他同事负责的小组 |
| 上海自招员工、组负责人 | 上海自招租户 | 整个上海自招 |
| 某家供应商的员工、组负责人 | 该供应商租户 | 本供应商的全部小组 |

只有专用管理员 `cakeadmin` 可以开通、重置、停用后台账号，管理权限，以及操作平台 AI 回复总开关。总部员工用个人手机号登录即可查看各租户业务。对于托管小组开关、代办工单等业务修改，首版设计按本租户已有操作权限执行。总部在查看其他租户时使用只读视图。

例如，上海智能体组的 Bot 接到咨询，会话和后续报名都归总部。总部同事在后台查看一条河南会话以排查回复质量，页面标明「河南自招」，该会话、后续工单和统计仍然归河南。

## 租户、人员和小组怎样关联

| 对象 | 身份和归属 | 生命周期 |
| --- | --- | --- |
| 蛋糕租户 | 为每个租户建立稳定的 `tenant_id`，显示名称可以调整 | 新供应商登记为新租户。多个租户可以接入同一家托管服务。 |
| 蛋糕成员和后台登录 | 成员档案保存稳定的成员 ID、所属租户、租户角色、姓名、登录手机号和启停状态。开通后关联 Supabase Auth 用户 ID | 收到手机号前可先建档。手机号用于登录。服务端按当前有效成员归属和权限处理每个业务请求。 |
| 托管小组和 Bot | 一个组织有多个小组，每人负责一个小组，组内可有多个企微号。每个企微号固定属于一个组织 | 同事在 Stride 扫码归组，管理员在蛋糕绑定小组。组内新增企微号随目录同步，同组织换负责人或调整小组时，业务数据仍归该组织。 |
| 外部业务账号和通知 | 按租户登记实际启用的外部服务。海绵业务账号有稳定本地 ID 并绑定承办成员。飞书按用途绑定应用、群、任务清单及需要的人员授权 | 同一租户内，多个 Bot 可引用已确认的同一业务账号。供应商可按实际业务接入其他服务。 |

后台统一显示「所属组织」。数据库的 `tenants` 是这份组织名单，`id` 是稳定主键，`name` 是显示名称，`created_at` 记录创建时间。现有三个组织沿用已有 ID。员工档案的 `organization` 外键和聊天记录的 `tenant_id` 外键都指向 `tenants.id`。接入新供应商时，`cakeadmin` 在「账号管理 → 登记组织」填写名称。蛋糕生成稳定 ID，新组织随即进入开户、调岗与小组绑定的选择范围。组织改名只改显示名称。

### 租户管理员与组长的查看范围

开户时，`cakeadmin` 在「租户角色」选择「组长」或「租户管理员」，提交后可在账号名单核对。现有员工和未指定角色的新成员默认是组长。租户管理员调入其他组织时，在新组织的角色为组长。

本版两种角色都按上表的租户范围查看数据，河南的组长和租户管理员都能看整个河南中心。将来启用组级查看时，租户管理员查看本租户全部业务，组长查看本人负责的小组内所有 Bot 的业务。总部跨租户查看和 `cakeadmin` 的平台管理权限各自独立。

业务明细应能追溯到业务发生时的租户和托管小组。有原始小组 ID 时保留它，也可以用渠道连接、Bot ID 和业务发生时间查当时的入组记录。派生流水可沿原始业务记录追溯。将来的组长视图先按租户和负责小组筛选明细，再展示详情或计算报表。能确认租户、暂时无法确认小组的记录留在租户级视图。

## 一条消息的归属与权限

以下是产品的完整流程。蛋糕已完成组织登记、业务数据隔离和现有飞书通知路由的开发与测试。海绵业务账号的租户级凭据管理、历史工单迁移和新供应商渠道仍按后文的上线范围推进。

1. **消息进入。** 蛋糕核对渠道连接和 Bot 身份，用消息发生时有效的小组绑定确定业务租户。外部企微企业 ID、Stride 小组备注都可以协助核对。归属缺失或冲突时，暂存待核对，确认后再处理。
2. **记录和处理。** 聊天、收资表、预约、消息处理流水和复聊都记在托管号所属组织。定时扫描和恢复托管时，蛋糕用企微号找到组织，读取该组织的候选人资料和预约，再排提醒。重试沿用原业务归属。
3. **调用外部服务。** 报名按业务租户、承办账号取海绵凭据。通知按该租户启用的飞书应用、群或任务清单发送，需要个人委派时使用对应用户的授权。租户尚未接入的能力显示「未接入」，本次外部调用跳过。
4. **员工查看。** Supabase Auth 校验手机号和密码，蛋糕用 Auth 用户 ID 找到有效成员和读取范围。河南、上海自招和供应商按本租户查询，总部可在全部租户汇总和单个租户详情之间切换。列表、详情、报表、订阅和已开放的导出遵循同一范围。
5. **员工操作。** 服务端分别校验操作权限与目标资源的租户。查看河南数据时，总部员工的个人账号仍属于总部。后台记录实际操作人、目标租户和操作对象。

## 海绵与飞书的授权

- **首次绑定**。租户启用海绵时，在该租户登记对应的业务账号，迁移已有配置或录入 token。暂缺上游账号 ID 时也可建立本地绑定。成员、小组和海绵账号可以先就位，Bot 接通后补关联。
- **凭据更新**。同一业务账号换 token，只更新该业务账号的服务端凭据。所有引用它的 Bot 共用更新后的授权，后台密码和原有工单归属继续有效。账号名称、手机号相似或 token 相同都不足以自动合并两个账号。海绵接口接受 token 只能证明凭据可用，归属以经确认的成员绑定或上游账号身份为准。
- **更换承办账号**。同组织内更换海绵承办账号时，新业务使用新绑定。新建工单应记录当时的业务账号 ID，后续查询、改约、取消沿原归属处理。历史工单缺少可靠依据时列为待核对。
- **缺失或过期**。成员仍可用自己的手机号登录后台。已启用的外部能力缺少授权时，停止该项调用并提示更新。共享目录类服务需显式授权给使用它的租户。飞书应用凭据与办理委派的用户授权分别保管，个人授权可独立续期或撤销。
- **凭据可见范围**。服务端保管可更新的海绵凭据。成员列表与详情只返回业务账号标识和授权状态，操作日志只记录操作人、绑定和变更类型。密码由 Supabase Auth 管理。

## 开通与绑定 SOP

总部管理员和中心负责人办理开户、托管绑定或新组织接入时，可查看[飞书操作手册](https://gingjqcjzc.feishu.cn/wiki/QR75wvbBIiIy2ekdNH1csJrfn1g)。

以下流程在租户隔离版正式发布后执行。员工可以先开通后台。托管号、海绵和飞书分别按租户的实际需要办理。

### 已有租户新增同事

负责人提供姓名、登录手机号、所属租户、负责小组和准备托管的账号。已有名册可直接核对。小组还没有 Bot 时也可先建档。

| 步骤 | 谁来办 | 怎么办 | 完成标志 |
| --- | --- | --- | --- |
| 1. 核对成员档案 | 总部管理员 | 在目标租户按手机号和负责小组核对。已有档案沿用原记录。发现手机号或小组与其他租户冲突时，请负责人核对是否涉及调岗。 | 成员、租户和负责小组一致，缺手机号时标为待开通。 |
| 2. 开后台登录 | 总部管理员、同事本人 | 管理员用 `cakeadmin` 在「账号管理」开通账号，选择所属组织和租户角色，为每人设置独立随机初始密码，单独交给本人。 | 同事用个人手机号和密码登录，核对上表规定的范围。 |
| 3. 在 Stride 扫码归组 | 同事本人、Stride 管理员 | 同事在 Stride 扫码归组。cakeadmin 在「账号管理」同步 Stride，在开户弹窗选择「负责小组」，或在已有成员行点「绑定托管小组」。核对组织和组内昵称后确认。空组也可绑定。 | 在蛋糕能查到该组、负责人和各 Bot 的归属。 |
| 4. 办理已启用的外部服务 | 业务负责人、运维 | 使用海绵的租户核对承办账号并绑定授权。使用飞书的租户核对应用、接收群、清单及接收人，按需完成委派授权。 | 已启用的业务只使用本租户确认的账号和目的地。 |
| 5. 验收并启用 | 租户负责人 | 用测试联系人发一条消息，在所属租户查到该会话。已启用报名或派单时，用测试工单核对承办账号和实际接收方。 | 归属与操作范围正确后开放正式流量。使用已有小组时，注意小组开关影响整组。 |

已在 Stride 正常托管的账号，直接核对现有渠道、小组和 Bot 绑定即可。缺少海绵或飞书的供应商可以独立办理开户和托管。

### 新租户接入

| 步骤 | 谁来办 | 怎么办与验收 |
| --- | --- | --- |
| 1. 登记租户 | 总部管理员、租户负责人 | 确认名称、负责人和实际需要的渠道及外部服务，用 `cakeadmin` 打开「账号管理 → 登记组织」，输入组织名称。蛋糕生成租户 ID，开户时直接选择这个组织。 |
| 2. 登记渠道和小组 | 渠道管理员、运维 | 使用 Stride 时，在平铺列表找到或创建小组，登记渠道连接、小组 ID 与租户的对应关系。使用独立 Stride 企业时，另行接通目录和消息回调。 |
| 3. 跑通首位成员 | 总部管理员、租户负责人 | 选一位同事和一个托管号，走完上面的开户、收消息流程。只验证该租户启用的外部服务。 |
| 4. 核对权限后扩开 | 总部运营、新旧租户负责人 | 用两个普通租户账号验证各自能看本租户全部小组、聊天和统计，只能操作有权管理的本租户小组。再用总部个人账号验证两个租户的业务均可查看且标明来源，跨租户视图只读。 |

小组和组内企微号属于同一组织。同步目录时按渠道、小组 ID 和企微号核对。同组织调组自动同步。已登记企微号与目标小组的组织不一致时，同步提示核对 Stride 配置。

## 实现与上线边界

截至 2026 年 11 月 23 日，测试库已登记 17 个小组、12 个在用 Bot。正式环境的绑定登记和开户安排在发布窗口。

| 场景 | 实现口径 |
| --- | --- |
| 组织与账号 | 开户、名单导入、登录、调岗和托管小组共用 `tenants`。显示名取自组织表，归属用稳定 ID。新组织登记后即可选择。同名小组或过期备注不会改变归属。 |
| 聊天、流水与复聊 | 聊天和主动复聊按所属组织保存。主动复聊分别记录触发时间和处理时间，调用快照、执行事件与审查记录继承流水的组织。成员可以查看本组织的列表、详情和趋势。 |
| 用户活动、运营事件和报表 | 活动按业务时间入账，日报按组织和托管号汇总。旧事件重试沿用首次记录，避免重复计数。 |
| 记忆和预约 | 候选人的长期档案、收资表、预约指针与快照按组织读取。后台补写预约、定时排提醒、恢复托管以及飞书介入任务都使用托管号所属组织。 |
| 外部服务 | 组织可以单独办理后台开户和托管归属登记。现用飞书通知按登记的路由选择，新组织默认没有飞书目的地。现有海绵集成仍有使用平台默认 token 的路径。供应商正式办理海绵业务前须完成独立凭据及工单归属验收。独立渠道和跨渠道消息去重另行接入。 |

在隔离环境用真实 Supabase 密码会话验过从「登记组织」到供应商员工登录的完整流程。两位河南员工都能看整个河南中心，模拟供应商只能看本组织，总部员工可跨组织查看。账号管理和 AI 总开关仅对 `cakeadmin` 开放。

测试库用河南和供应商各自的托管号验收。两边的聊天、流水与统计归入各自组织，事件重放只记一次。同组织内更换小组或负责人，已记录的业务仍可查看。[数据库验收用例](../../tests/supabase/business-tenant-ownership.sql)

正式发布前，按发布当天的 Stride 目录核对绑定、生效时间和总部及各中心的登录范围。正式迁移、私下交付初始密码、历史回填分别留存验收结果。[发布与回填待办](../todo/business-data-tenant-id.md)

## 现有配置如何迁入

当前分支的账号表设计为 `dashboard_accounts`，托管配置 `hosting_member_config` 按 `botImId` 查找现有海绵与飞书绑定。迁移时把两者接到同一份租户及成员档案。

1. 登记三个内部租户。核对全部在用同事、渠道连接、Stride 小组 ID、负责人与已知手机号。每人一个档案和一个负责小组，组内可以有多个 Bot。手机号待补的同事先建档，身份有冲突的交负责人确认。
2. 为新业务记录写入租户。历史记录按下表分批处理，同时核对外部账号的绑定时间。迁移前后逐租户对账聊天、工单和报表数量，检查重试中的任务。
3. 现有海绵与飞书配置按已确认的租户、业务账号和人员身份迁入。飞书个人接收人跟随该租户的成员绑定，企微对外昵称和人设跟随 Bot。切换前核对报名、预约、工单轮询和通知的实际目的地。
4. 随正式发布为全部已核实手机号开户，按人私下交付独立随机密码。重复办理保留原密码和停用状态。后续接入海绵租户凭据时，另验多人换班、token 更新和既有工单的操作范围。

### 只有 Bot ID 或小组 ID 的历史数据

蛋糕登记小组的组织、Bot 所在的小组和首次核实时间。当前目录用于识别在用号，历史回填按已核实的渠道、Bot 或小组标识办理。

2026 年 11 月 20 日，Stride 目录快照与开户名册中的 17 个小组逐一匹配。总部 4 组、5 个 Bot，河南自招 10 组、4 个 Bot，上海自招 3 组、3 个 Bot。12 个已绑定 Bot 都只出现在一个小组，6 个空组也可以先登记租户。这份快照证明采集时的归属，历史起始时间需要另行核实。

同日核对正式库历史聊天，共有 17 个不同的非空 Bot 标识。11 月 23 日复核后，12 个与在用托管目录匹配，4 个业务 Bot 已退役，1 个是评测工具的测试标识。本次开户覆盖名册中全部 17 个小组的负责人，空组也可开户。历史租户回填只核对 12 个在用 Bot 的有效时段。其余 5 个标识的聊天保留原记录，归属未核实的记录仅总部可见。另有 Bot ID 为空的聊天记录，可回填条数待逐时段试算。

| 一条历史记录留下了什么 | 怎样确定这条记录的业务租户 |
| --- | --- |
| 当时的托管小组 ID | 用渠道连接、小组 ID 和业务发生时间查唯一有效的租户绑定。同时有 Bot 证据时核对两者一致。 |
| 只有 Bot ID 和时间 | 按该 Bot 当时的归组记录查租户。对长期在同一租户的在用号，由负责人一次确认有效时段，该时段内的消息可整批补齐。 |
| 缺标识或有多种可能 | 可利用同一业务事件的已核实记录补证。旧配置、日报或运营事件中的组名供核对。证据仍有冲突时进入总部的「归属待核对」清单，普通租户查询及分租户报表排除这些记录。 |

当前聊天写入保存 Bot ID 和消息时间，小组级回调的原始消息缺少小组 ID。先让新写入固化租户，再对旧记录只读试算，按租户、时间段输出可回填和待核对数量。核对后仅回填租户为空的记录，可从上批进度继续。权限通过验收后，可以先开放归属已核实的数据，剩余历史按 Bot 和时段处理。

首次切换在旧服务运行时登记已核对的 Stride 目录，待旧服务处理完登记前的待回复消息后再切换。新服务按原回调核对组织，预约、改约和取消重试也使用原业务资料。之后新号随目录每五分钟同步，也可从「系统 → 账号管理」立即同步。历史聊天可用 `backfill_chat_tenants` 按消息 ID 试算并回填，每批最多 500 条。

登录实现和环境初始化参考见[后台账号说明](../../src/biz/center-dashboard/README.md#后台账号)。
