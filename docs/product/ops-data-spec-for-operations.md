> ## ✅ 口径速览（与早期版本不同处，以下述为准）
>
> 1. **不统计「入职」**：系统只追踪到「面试通过」。「整体转化率」= **面试通过数 / 加好友数**。
> 2. **加群率 = 进群数 / 破冰数**（分母是破冰，不是报名）；进群不在漏斗主链里，是破冰后的运营侧支。
> 3. **Handoff 原因现在是 15 类**（清单见 Block 4 一节）。
> 4. **漏斗主链 4 级**：加好友 → 破冰 → 报名 → 面试通过；报名 cohort 2 级：报名 → 通过。
> 5. **候选人可自助取消/改约面试**：Agent 有了自助取消工单、自助修改面试时间两个能力，账号对比表新增对应两列。
> 6. **转化分析页支持两种数据口径**：「同期发生量」和「成熟同批追踪」，页面顶部 Tab 切换（默认后者）。

## 一、我们要解决什么问题

运营每天要回答几个问题：

- **"今天每个号的招聘数据怎么样？"** —— 没有汇总，只能逐个对话翻
- **"我们的转化漏斗在哪个环节流失最严重？"** —— 没有完整漏斗视图
- **"为什么这个候选人转人工了？什么原因最多？"** —— 飞书告警有，但没有汇总分析
- **"加好友后，多少候选人真的回复了？"** —— 没追踪过僵尸好友比例

这套数据体系把这些答案**结构化、自动化**地提供给运营。目前全部功能已上线。

## 三、运营能拿到的三个数据出口

### 出口 1：飞书运营日报（每天晚上 9 点自动更新）

**地址**：飞书多维表格 [运营日报](https://gingjqcjzc.feishu.cn/wiki/JA9wwoysQiUzBJkFJmnchl9XnJg)

**用途**：每天看当天的成绩单，按号查看每个招聘账号的产出。

**表头**（7 列）：


| 列名    | 含义                  | 怎么算                         |
| ----- | ------------------- | --------------------------- |
| 日期    | 报告日期                | 自动                          |
| 小组    | 账号所属小组（琪琪/宇航/南瓜/小祝/盼盼） | 自动                          |
| 添加好友数 | 当天新增了多少个企微好友        | 平台「新增客户」回调为主（真实加好友即计数，含没开口的），消息兜底        |
| 破冰数   | 当天有多少新好友真的开口聊了     | 候选人首条**真实**消息时计数（排除"我是xx""请求添加你为朋友"等加好友招呼语；"破冰"=不再是僵尸好友） |
| 成功报名数 | 当天预约面试成功的人数         | Agent 调海绵接口预约成功时计数          |
| 邀请进群数 | 当天邀请候选人进招聘群的成功次数    | invite_to_group 工具成功时计数     |
| 通过数   | 当天面试通过的人数           | 海绵工单中"面试成功"且通过时间是今天的工单数     |


**每行 = 某天某个号的全部数据**。同一小组多个号会有多行。

#### 飞书日报使用场景

- **晚上 9 点后**：打开飞书表，看当天的成绩单
- **周报/月报**：复制日报数据做周/月汇总
- **复盘问题号**：哪个号破冰率特别低？哪个号预约数为零？

### 出口 2：Web 转化分析页（实时）

**地址**：Dashboard 菜单下方 → "**转化分析**"

**用途**：看 KPI 与趋势、转化漏斗、各账号横向对比、Handoff 原因分布。

#### 先认识两种数据口径（页面顶部 Tab 切换）

页面顶部有「数据口径」Tab，所有卡片、趋势图、漏斗、账号表随之同步切换：

| Tab | 回答的问题 | 怎么算 | 什么时候用 |
| --- | --------- | ------ | -------- |
| **同期发生量** | "这段时间各阶段各发生了多少？" | 同一时间窗内，各阶段分别按候选人去重后相除。今天通过的人可能是几天前加的好友 | 日常盯量、和飞书日报核对 |
| **成熟同批追踪**（默认） | "这批新加的好友最终转化得怎么样？" | 从同一批新增好友出发追踪其后续转化，逐级分子属于上一级分母；**带 7 天成熟期**——太新的好友"还没来得及转化"，不计入，避免比率被压低 | 周复盘、评估获客质量与漏斗真实转化 |

> 两种口径数字不同是正常的，不是数据错了。对外汇报时注明用的是哪个口径。

#### Block 1：5 个转化率 KPI（一排）

每张卡显示一个百分比 + 同环比变化 + 分子/分母：


| KPI       | 公式         | 衡量什么               |
| --------- | ---------- | ------------------ |
| **破冰率**   | 破冰数 / 加好友数 | 开场白质量 + 僵尸好友比例     |
| **报名转化率** | 报名数 / 破冰数  | Agent 收资料和约面的能力    |
| **加群率**   | 进群数 / **破冰数** | 引导进群的能力（分母是破冰，进群是破冰后的运营侧支）|
| **面试通过率** | 通过数 / 报名数  | 候选人匹配岗位准确度         |
| **整体转化率** | **通过数 / 加好友数** | **端到端漏斗效率（最关键指标，收口到面试通过、不含入职）** |

#### Block 1.5：KPI 趋势图

5 个转化率的**逐日趋势曲线**，口径跟随顶部 Tab。用法：

- 看某个率是缓慢恶化还是突然掉——突然掉通常是配置/系统问题，缓慢恶化多是流量或话术问题
- 曲线出现**断点**（不是掉到 0）表示当天分母为 0（没有对应数据），属正常展示，不是丢数
- 调整开场白/策略后，用趋势图对照调整日前后变化

#### Block 2：Cohort 漏斗（同一批人追踪）

**Cohort 维度切换**：

- **加好友 cohort**：选某时间段加好友的候选人，跟踪他们后续走到哪一步
  - **主链 4 级**：加好友 → 破冰 → 报名 → 面试通过
  - **加群是侧支**：不在主链里单列一级，作为"破冰之后有多少人进了群"单独展示（分母=破冰）
  - 示例："5/21-5/27 加好友的 500 人里，最终 60 个面试通过"
- **报名 cohort**：选某时间段报名的候选人，跟踪他们后续走到哪一步
  - **2 级**：报名 → 通过
  - 示例："5/21-5/27 报名的 80 人里，最终 35 个面试通过"

漏斗图直观看出**哪个环节流失最严重**。

#### Block 3：账号维度对比表

每行一个 bot 账号，便于横向对比：


| 账号      | 所属小组 | 新加好友 | 破冰  | 报名  | 进群  | 通过  | 自助取消 | 自助改约 | 整体转化率 | 状态  |
| ------- | ---- | ---- | --- | --- | --- | --- | ---- | ---- | ----- | --- |
| gaoyaqi | 琪琪组  | 120  | 85  | 25  | 20  | 18  | 2    | 3    | 15.0% | 🟢  |
| ZhuDS   | 小祝组  | 110  | 80  | 20  | 15  | 12  | 1    | 0    | 10.9% | 🟡  |
| ...     | ...  | ...  | ... | ... | ... | ... | ...  | ...  | ...   | ... |


- **自助取消 / 自助改约**是新增两列：候选人明确要取消或改面试时间时，Agent 现在可以直接调海绵办理，不必转人工。这两列是**运营侧支计数**，不参与转化率计算；自助取消/改约多，说明候选人时间波动大或约面时段设置不合理，可针对性复盘
- 状态指示：🟢 ≥10% / 🟡 5-10% / 🔴 <5%
- 点击表头可排序，可按"小组"筛选
- **换号合并说明**：招聘账号换号（微信号轮换）后，新旧号会被合并成同一行展示（计数相加），不会裂成两行。如发现某账号换号后仍显示两行，联系研发在系统配置里登记别名映射即可，运营侧无需操作

> 🚧 **来源渠道维度（规划中，待数据接入）**：后续会支持按"候选人来源渠道"（扫码/活码/投放等）筛选和对比——看哪个渠道不只是量大、而是获客质量高（破冰率/报名率/通过率）。前提是上游能透传渠道信息；接入前此维度不展示。

#### Block 4：Handoff 原因分布

**Handoff = 转人工**。当 Agent 无法处理某些场景时，会暂停托管 + 飞书告警，让招聘经理介入。

**15 类原因**（会随产品形态调整——增删原因不影响饼图，运营无需配合改动）：


| 原因                          | 含义          |
| --------------------------- | ----------- |
| cannot_find_store           | 候选人找不到门店    |
| no_reception                | 到店无人接待      |
| booking_conflict            | 预约信息冲突      |
| onboarding_paperwork        | 入职办理问题      |
| interview_result_inquiry    | 追问面试结果      |
| modify_appointment          | 改期/取消已预约面试（Agent 自助改约/取消失败后的兜底）  |
| self_recruited_or_completed | 候选人已被自招/已面试通过/已入职 |
| no_match_or_group_full      | 无匹配岗位 / 群满需维护 |
| system_blocked              | 工具/系统卡死无法自助 |
| booking_capacity_full       | 岗位报名人数已满，无法在线报名，需人工确认名额或另荐岗位 |
| group_invite_failed         | 拉群操作失败（如邀请发不出去），需人工把候选人拉进群 |
| salary_admin_inquiry        | 薪资明细/考勤/工作证明类咨询，岗位数据里没有答案；告警会带上缺口信息，方便运营补录岗位资料 |
| interview_slot_coordination | 候选人只能特定时段（如只有周末有空），系统可约场次都覆盖不了，需人工与门店协调特殊时段（区别于改期：这是**还没约上**时的协调）|
| identity_age_exception      | 候选人身份/年龄在岗位硬要求边界（如 17 岁、学生想上社会岗），需人工裁量能否破例 |
| other                       | 其他          |


饼图 + 列表展示，可以看出**哪种问题最高发**，从而优化 Agent 或流程。

> 💡 这些分类会随产品稳定增删（比如细分某类、合并低频类）。届时饼图会自动反映新分类，运营侧不用做任何配置；如对某类原因的命名/含义有建议，欢迎反馈。

#### Web 转化分析页使用场景

- **每周复盘**：切「成熟同批追踪」看本周漏斗各环节转化率变化
- **日常盯量**：切「同期发生量」看今天/本周各阶段发生数，与飞书日报对得上
- **小组对比**：看哪个小组转化率最高，复制最佳实践
- **服务质量分析**：Handoff 原因分布反映 Agent 哪些场景处理不好；自助取消/改约两列反映约面时段合理性
- **产品迭代决策**：哪个环节流失多，就优先优化哪个环节

## 六、运营常见疑问 Q&A

### Q1：为什么"通过数"今天显示 10，而昨天报名只有 5 个？

**A**：因为"通过数"是**当天发生通过事件的数量**，不是"今天报名的人有几个通过了"。今天通过的人可能是 3 天前、5 天前报名的。两个指标不是同一批人。

如果想看"今天报名的最终多少通过"，要看 Web 转化分析页的 **报名 cohort**，或把数据口径切到「成熟同批追踪」。

### Q2：为什么"加好友"的人没回复消息，破冰率上不去？

**A**：可能原因：

- Agent 开场白不够吸引人
- 候选人加好友只是好奇，没真实求职意向
- 候选人忘了

可以从 Web 转化分析页看出：

- 破冰率：本期实际破冰比例
- KPI 趋势图：破冰率是缓慢恶化还是突然掉
- 同环比：和上周对比有没有恶化

### Q3：为什么同一个小组里两个号差距这么大？

**A**：可能原因：

- 两个号面向的候选人画像不同（地域/品牌偏好）
- 两个号的开场白质量不同
- 两个号被分配的岗位池差异

可以用 Web 转化分析页的**账号维度对比表**直接看到每个号的漏斗各阶段表现，定位问题环节。

### Q4：Handoff 一直很多怎么办？

**A**：去 Web 转化分析页看 **Handoff 原因分布**。如果某种原因占比特别大：

- `cannot_find_store` 多 → Agent 的门店定位能力需要优化
- `modify_appointment` 多 → 看是不是预约时段选得不合理（注意：候选人改期/取消现在优先由 Agent 自助办理，这一类只剩自助失败的兜底）
- `interview_result_inquiry` 多 → 候选人面试后追问太多，可能要主动同步面试结果
- `salary_admin_inquiry` 多 → 岗位资料缺口大，按告警里带的缺口信息补录岗位数据
- `interview_slot_coordination` 多 → 面试场次覆盖不了候选人的空闲时段，考虑加开周末/晚间场次

### Q5：飞书日报里"邀请进群数"和"成功报名数"的关系？

**A**：两者**不是顺序关系**，是**两个独立动作**。

- 一个候选人可能：报名了但不进群、进群了但不报名、又报名又进群
- 在 Web 转化分析页的 Cohort 漏斗里，漏斗**主链是 4 级**：加好友 → 破冰 → 报名 → 面试通过；"邀请进群"**不在主链里**，是**破冰之后的运营侧支**（分母=破冰人数），单独展示

### Q8：仪表盘上"活跃用户"和"托管用户数"有什么区别？

**A**：两者衡量的是**不同的东西**，不要直接对比：


| 指标        | 含义                             | 统计窗口                    | 数据来源                                       |
| --------- | ------------------------------ | ----------------------- | ------------------------------------------ |
| **活跃用户**  | **最近 1 小时**内有消息往来的去重用户（实时在线脉搏） | 固定近 1 小时，**不随顶部时间范围变化** | 消息处理流水                                     |
| **托管用户数** | 所选时间范围内有托管活动的去重用户（累计盘子）        | 跟随顶部时间范围                | 本日=消息流水；更长范围=托管活跃表 user_activity（保留 365 天） |


- **活跃用户 = "此刻有多少人在聊"**：无论顶部选今天还是近 180 天，它始终只看最近 1 小时，卡片上带「近1h」标记。用来判断当前是否有人在实时对话。
- **托管用户数 = "这段时间一共服务了多少人"**：跟随时间范围累计，范围越长数字越大。
- 所以两个数**通常不相等、也不该相等**——一个是瞬时快照，一个是区间累计。

### Q9：两种数据口径的数字对不上，哪个是对的？

**A**：都对，回答的问题不同。「同期发生量」数的是**这段时间发生了多少**（和飞书日报同源可核对）；「成熟同批追踪」数的是**这批人最终走到了哪**（带 7 天成熟期，刚加的好友不计入）。对外汇报注明口径即可，不要混用两个口径的数字互相印证。
