# 蛋糕记忆系统现状与健康报告

> 同事同步版｜核查日期：2026-10-23｜生产数据快照：18:39:20（北京时间）
> 代码基线：已发布 v11.14.1；PR #1456 保留待人工批准，未合并、未发布。本文不包含候选人个人信息。

## 1. 现在可以怎样理解蛋糕的记忆

蛋糕保存的是“当前会话认知”和“候选人与某个托管账号的长期关系档”。它既不是全量聊天记录的无限上下文，也不是招聘业务系统的替代品。原始聊天提供证据，记忆帮助延续对话，收资表单控制报名，海绵工单提供真实招聘进度。

当前结论是：**结构化数据约束已经落地，本轮确认的脏值已清理；长期信息仍有缺失，运行效果需要继续按生产窗口观察。** 不能把健康证闭集外为零理解成健康证信息完整，不能把流水线成功理解成每一次语义提取正确。

最重要的业务边界：

- 身份档案、求职意向按候选人 × 托管账号隔离，不跨账号偷偷预填。
- 候选人级工单可以跨账号核查；这不等于允许跨账号复制个人档案或共享聊天接管权限。
- 历史档案可以帮助提问、检索和预填，但不能绕过本岗位表单的筛选、确认与提交授权。
- `message_metadata` 保留，承担未来跨系统身份关联；当前不进入 Prompt 不是退役理由。

## 3. 存什么、存哪里、谁消费

| 对象 | 存储与寿命 | 消费与价值 |
| --- | --- | --- |
| 聊天原文 | Supabase `chat_messages`；Redis 消息热缓存默认 7 天 | 对话上下文、证据回查、沉淀原料；消息缓存可回源 |
| 会话事实 | Redis `factsv2` Hash，默认 7 天 + 12 小时 | 当前身份线索、城市／区域／班次等偏好、品牌状态 |
| 会话工作台 | 同一 Hash，同寿命 | 岗位池、已展示岗位、当前焦点、查询签名，支持指代与防复读 |
| 会话阶段 | 独立 `stage`，实际写入及续期为 7 天 + 12 小时 | 策略选择；缺失返回 null，由上层选择兜底 |
| 长期身份／意向 | Supabase JSONB，持久；Redis 2 小时缓存 | 回访认知；按候选人 × 稳定 bot 身份隔离 |
| 咨询摘要 | 同表裸数组，上限 20 段 | 回访首轮最近一段自动注入（最多 300 码点）；更早由工具读取 |
| 沉淀水位 | 独立 JSONB 列，持久 | 去重和确定下次消息边界；不进入 Prompt |
| 报名表单 | tools 域 Redis 单据及 primary/current 指针，7 天 | 人 × bot × 岗位事务底稿；不能当成可随意清空的缓存 |
| 候选人进度 | 海绵工单 + 本地指针 + 会话状态的只读派生视图 | 当前预约、查重、复聊与提醒；未知不能当作无工单 |
| 当轮账本 | 内存 `TurnLedger`，一轮 | 记录真实工具结果和本轮授权；只有选定结果进入持久工作台 |
| 跨系统关联 | `message_metadata` JSONB，持久 | 外部标识与联系人快照；不替代关系主键或字段证据 |

“7 天”有三个不同含义：消息窗口相对上次候选人开口回看 7 天；会话业务生命周期 7 天；连续闲置 7 天后沉淀。窗口不是“距今 7 天”，首次咨询与连续未获回复消息可能跨度更大，最终受 300 条和默认 24,000 字符限制。

## 4. 变更规则：哪些新信息可以覆盖旧信息

| 类型 | 写入规则 | 业务例子 |
| --- | --- | --- |
| 长期身份 | 逐字段合并，低置信不得覆盖 high；陈旧时间不得覆盖新值 | 报名成功确认的手机号不会被后续低置信抽取覆盖 |
| 长期意向 | 每字段原始时间较新者胜；没提及保留；显式 null 墓碑清除 | 本轮只改班次，原城市不丢；明确不要某区域才清空 |
| 城市依赖 | 城市变更时清除不应继承的旧区域／地点；新同轮字段可重新落入 | 从上海转杭州，不携带旧上海商圈 |
| 时效字段 | available_after 日期早于今天不消费；delayed_intent 的有效 until 优先，否则按事实时间 30 天 | “下周再说”不能几个月后仍约束对话 |
| 摘要 | 求职段追加、最多 20 段；已有条目不交模型反复改写 | 非求职／无实质内容不加摘要，但推进处理水位 |
| 收资槽位 | 已 filled 不接受普通重投；本人显式改口、纠正或后端打回按规则重开 | 模型每轮重复提交全表不会覆盖已确认项 |
| 业务成功 | 外部真实回执确立；版本投影防旧状态复活，行动恢复能力受 observe／execute 档位约束 | 不能凭助手说“已报名”就标记报名成功 |

健康证未知留 null，原话／日期留在证据和消息中。evidence 最多 **200 个 Unicode 码点**，省略号也计入；不是 200 字节，也不是数据库中保存完整聊天原文的替代方案。

## 5. 本轮已经改变了什么

v11.14.1 已上线：四态健康证与约束、evidence 预算、意向字段时间合并与墓碑、时效过滤、摘要三态与首轮召回、沉淀任务复用、岗位池前 10 条完整后 20 条精简、停止持久化 brand_ids，并保留 metadata。

生产清理已执行并逐行备份：首批 51 行／73 字段；超长证据 2,184 个字段；健康证修正 863 行（其中 534 个信息不足值置空）；37 段坏摘要；431 个过期意向字段；54 个学历别名；删除 81 条真正纯空行。**各轮对象有重叠，不能加总为候选人数。** 原报告把 metadata 视作死列、把大量保留行视作可删空壳的判断已撤销。

metadata 初次可靠回填 6,429 行，后续再补 68 行。后续回填结束时空值快照为 2,013；本次新快照为 2,017。生产持续写入且查询时点不同，本次只读统计不能证明这 4 行变化来自哪种写路径，也不能认定新增值都可恢复。

已清理 355 个用户确认废弃的测试 Redis 键。后续验证另清理 125 个本次自建命名空间键，两者是不同批次；没有清空生产命名空间。

## 6. 健康状态与后续重点

**本轮已确认的记忆缺陷已完成修复并上线，数据形态检查通过；仍需治理的是历史关联缺失、候选人进度口径，以及发布后的长期效果验证。** 正常未知、未充分验证和已确认故障分别说明，不能合并成一份故障清单。

| 项目 | 当前结果 | 验证依据 |
| --- | --- | --- |
| 结构化数据质量 | 健康证四态、证据长度及相关字段约束已生效，已确认脏值完成清理 | 18:39 快照 34,916 行，现有 CHECK 违规 0 |
| 记忆更新与消费 | 字段时间合并、显式清除、过期过滤、摘要三态与回访首轮召回已上线 | v11.14.1；发布前 7 条真实 Agent 回归，上线后 5 条四态／旧值回归通过 |

这些结果证明已检查的约束和回归场景通过；不把它们换算为全业务语义准确率。

### 6.2 正常未知：不以填满字段为目标

当前 bot 关系档中，707 行有明确健康证四态，19,286 行未知或尚未采集。大量候选人未进入收资阶段，**未知数量本身不能证明漏采，更不能解释成“没有健康证”**。对已进入应采集阶段却没有留下信息的情况，才需要按业务流程进一步核查；本次未统计这一分母。

信息不足的历史“有／无”等值，继续留空，等候选人确认。不会为了降低空值率而猜测本地有效性或办理意愿。

### 6.3 真实遗留与待评审事项

| 事项 | 已知范围与实际影响 | 后续处理 |
| --- | --- | --- |
| metadata 历史关联缺失 | 2,017 行为空，其中 **2,012 行为 legacy，当前 bot 关系行 5 行**；影响跨系统关联完整性，不等于候选人主键缺失或当前对话大面积失忆 | 仅凭可靠血缘补齐；优先核查当前 bot 关系行的写入来源，不猜填 botId |
| 候选人进度时间窗口 | 规则已集中，但上下文、查重、复聊仍沿用不同 legacy 窗口，可能对同一工单作出不同判断；当前尚未量化实际错误影响 | 优先核查差异事件和业务案例，区分合理的场景差异与真正冲突，再确定是否统一 |

### 6.4 待验证效果：尚无结论不等于已发生故障

发布后的长期耗时和语义效果还缺少足够长的同口径对照。后续用固定 7 天窗口观察抽取耗时与输入量、收尾 failed/interrupted、沉淀到期积压、首轮摘要注入，以及错误回忆、漏记、旧值复活的实际样本；每项保留分母和时间范围。

替换抽取模型、移出会话锁是需要证据支持的优化选项，**不列为必须完成的遗留修复**。应先确认成本与一致性收益，再决定是否改动。
