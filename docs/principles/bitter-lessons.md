# 本库苦涩教训台账（Bitter Lessons）

> 定位：收录**机制级方向性教训**——花了真实成本建、后来被数据证伪"整个思路错了"、拆除/关停才是正确处置的机制。
> 不收 bug（那是修复台账的事）：bug 是实现错了，苦涩教训是**方向错了**。
> 术语：借喻自 Sutton "The Bitter Lesson"（人工结构终被通用方法溶解），本库语义见 [glossary.md](./glossary.md) B 层——比原义宽，指一切交过学费的方向性证伪。
> 收录标准：机制级（非单点 bug）、有证伪数据、已裁定拆除或转向。

## 0. 一句话版本

最贵的错误不是 bug，是"整个思路错了"的机制。把学费单记下来，防止同一个思路换个名字再建一遍——**拆除是正确处置，不是失败；重建才是**。

## 1. 教训台账

### L1 守卫硬规则面铺太广（历史批次 30 → 10 条）

- **建了什么**：出站守卫确定性规则一路加到约 30 条，期望规则面越广拦得越全。
- **怎么证伪**：截至 2026-07-10 的逐档实证复审发现，大量规则拦不到真问题、专产假阳（含语义 markdown 误读误拦簇）；“兜底边界原则”确立后按档核查，20 条无 badcase 支撑。
- **处置裁定**：当时大规模下线 20 条、阶段性只留 10 条在产；后续新增规则仍必须逐条走
  observe 发牌，不能把“当前 catalog 数量”误读成这次历史批次从未发生。
- **元教训**：确定性规则只配拦"完成时态、可确定性判定"的结果形态；每档规则入场必须 badcase 实证（兜底边界原则）。规则面的宽度不是防御力，是假阳产能。

### L2 LLM 语义审查 enforce 从未够格开启

- **建了什么**：出站三档中的 LLM 语义审查层，期望语义理解兜住硬规则拦不住的问题。
- **怎么证伪**：shadow 长跑后 2026-08-05 大清算——命中大簇几乎全假阳；精度从未达到 enforce 门槛（至今 `outputGuardrailLlmEnabled=false`，2026-08-21 生产配置核实）。
- **处置裁定**：enforce 保持关闭；语义层改定位为"形状勘探器"（发现新问题形状供人复盘，不裁决不拦截）。
- **元教训**：LLM 审查 LLM 的精度天花板低于 enforce 门槛。二次模型链一律先 shadow 实证，精度不达标就只配当勘探器。

### L3 repair/rewrite 链路破产

- **建了什么**：守卫拦截后由 repair 模型重写回复再投递，期望"拦下来还能救回来"。
- **怎么证伪**：泄漏类拦截的 rewrite 把问题"洗成"零事实的幻觉投递（含伪造链接）——表面合规、实质更糟；回归闸建了两期（四形态回退）仍治不住；改约失败等工具失败簇约 43.9% 属编排缺陷，重写层无从修复。
- **处置裁定**：~~用户宣告整条链路破产（2026-08，复盘前禁止再提 rewrite 补丁）。~~
  2026-08-26 终态校准：带工具 `replan` 已物理删除；宽泛 rewrite 失去“质量提升机制”定位。
  现存 `ReplyRepairAgent` 只承担一次有界文本修复/P0 自救，并受二审与 regression gate 约束。
- **元教训**：零上下文的模型重写只会制造"更合规外观的更糟输出"。修复必须回到编排层/事实层，不能靠"再叫一次模型"。

### L4 投递路径的 LLM 实时判断

- **建了什么/想建什么**：投递热路径上引入 LLM 实时判断的反馈循环。
- **怎么证伪**：延迟与可靠性均不可接受，实践否决。
- **处置裁定**：禁止新增无证据、无 hard cap 的 LLM 实时判断循环。现存 semantic reviewer 默认关闭、
  可 shadow；enforce 只在显式配置和门控下运行。现存 repair 上限一次，不得重调工具。
- **元教训**：默认快路径必须确定性。确需 inline LLM 时只能显式开关、证据门控、有界运行并
  保留确定性失败收敛，不能把第二个模型当无限责任兜底。

### L5 模型仲裁候选人事实（72.3% 假阳）

- **建了什么**：让模型对候选人字段冲突做裁决。
- **怎么证伪**：候选人事实裁决 72.3% 假阳观测（P11 立宪的直接动因）；语义三分法复盘确认第二档 LLM 的正确角色是"抽取顺风车"而非仲裁器。
- **处置裁定**：P11 裁决权宪法（2026-08-12）：**模型作证、代码公证、本人终审**；裁决权限缩在 resolution 域。
- **元教训**：模型可以作证，不能定案。事实真值的维护是代码（公证）与本人（终审）的职责。

### L6 用提示词承载业务逻辑（precheck 13.5K 描述）

- **建了什么**：precheck 工具描述积至 13,517 字符——40+ 条硬规则实为"用自然语言写的状态机转移表"，每条都是 badcase 换来的、放置也符合当时分层裁定，但架构上是让 LLM 当状态机的执行引擎。
- **怎么证伪**：收资状态机（#1023，2026-08）用代码接管字段契约与流程推进后，描述瘦身至 729 字符且行为更稳——证明烂的不是哪句话，是"提示词承载业务逻辑"这个决定本身。
- **处置裁定**：收资走表单状态机；上下文工程原则 C3（行为逻辑归代码）。
- **元教训**：巨型 description/手册段落的第一问不是"哪句能删"，是"哪些内容应该变成代码或返回值设计"。

### L7 排障信息注入教学通道（张漪 case，27K+）

- **建了什么**：提取 reasoning 全文当作 evidence 随每个字段注入 prompt。
- **怎么证伪**：单轮 system prompt 撑到 27K+ 字符（chat `69a13e919d6d3a463b0a37c6`），靠 badcase 反查才发现——通道无测长无告警。
- **处置裁定**：evidence 定性为排障字段不注入 prompt；quote 渲染截 40 字。
- **元教训**：排障字段与教学字段必须分离；任何无测长、无告警的注入通道必然静默膨胀（→ 膨胀哨兵 F4）。

### L8 复聊复用主 generator（#477）

- **建了什么**：复聊（二次触达）复用主对话 generator 链路。
- **怎么证伪**：复聊场景与主对话差异过大（无来回、事实要求高、话术模板化），复用主链成本与风险高于收益。
- **处置裁定**：独立 ProactiveComposer/ReengagementAgent 取代；删除 #477 是裁定不是回归；复聊无工具裁定（2026-08-20 二期确认：LLM 产文案、代码扣扳机）。
- **元教训**：场景差异大到一定程度，"复用主链"的工程美德变成负债——独立轻链更便宜也更稳。

## 2. 元规律（跨教训蒸馏）

- **M1 二次模型链的精度天花板**（L2/L3/L5 同族）：用模型去审查/修复/仲裁另一次模型输出，不提升真值质量，只提升表面合规。三案三种形态（审查假阳、重写洗白、仲裁误判），同一个根因。
- **M2 确定性边界**（L1/L4/L5）：热路径与真值维护必须确定性；模型的领地是生成与作证。
- **M3 提示词不是逻辑的家**（L6/L7）：业务逻辑住代码，排障信息住观测，提示词只留原则与接口。
- **M4 机制入场须实证、在场须可退**（全部）：每个机制入场要 badcase/数据实证（兜底边界原则），判断替代型机制必须自带退场旋钮（C9 松绑就绪）——L1/L2/L3 的拆除之所以可行，正因有 shadow 档、批次制、回归闸。
- **M5 拆除记账**（本文档存在的理由）：折旧不可耻，但学费必须入账——每次拆除后在本台账立条，防同思路重建。2026-08 业界"松绑 harness"趋势追认了 L1/L2/L3 的处置方向（判断替代型 harness 折旧）。
