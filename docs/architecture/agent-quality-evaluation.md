# Agent 质量评估体系（口径页）

> 本页是"Agent 回复质量怎么评"的唯一口径：三层评估各管什么、指标怎么定义、多久看一次、谁消费结论。
> 判官自身的精确率考核（发牌制）见 [docs/todo/judge-calibration.md](../todo/judge-calibration.md)；精确率数字落 [质量指标台账](../quality-metrics-ledger.md)，样本明细在本地报告 `logs/analysis/judge-calibration-*.md`。
> 2026-09-02 裁定：**评估以周频质量盯盘为主，发版闸门保持轻量**——实践证明直接上生产再快速修复比重闸门更划算。

## 1. 顶层指标：每个阶段的任务目标完成质量

结果指标是**约到面试**，但不单看约面数：每个阶段有自己的任务目标（`strategy_config.stage_goals`，运营可配），
评估看"该阶段的目标完成得好不好"，而不是"回复像不像真人"。

| 阶段（stage_goals.stage）          | 任务目标（摘自配置）                                   | 完成信号（ops_events）                                       | 质量看什么                                                                             |
| ---------------------------------- | ------------------------------------------------------ | ------------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| trust_building 建立信任与初次接触  | 自然开场，一次拿到能查岗的最少信息                     | `agent.opening_sent` → `candidate.engaged`                   | 破冰率；开场后候选人是否回话；有位置线索时是否直接查岗而不是再问一遍                   |
| job_consultation 岗位匹配与释疑    | 基于工具数据给真实岗位信息，打包推荐收敛到可考虑的岗位 | `job.recommended`                                            | 推荐是否基于有效位置与距离阈值；岗位事实是否与工具结果一致；无岗时是否如实收口而非编造 |
| qualify_candidate 关键资格补充确认 | 只补影响推荐/约面的硬条件，不制造被审问感              | `precheck.passed`                                            | 是否只问缺的字段；是否重复索要已给信息；筛选条件是否照抄岗位原文                       |
| interview_scheduling 面试安排      | 对齐面试要求与时间，收资后提交预约并回执               | `booking.succeeded` / `booking.failed`                       | 预约载荷是否正确（时间/门店/字段）；失败时是否如实说明并转人工；有无"已约好"的假回执   |
| onboard_followup 面试及上岗对接    | 解答面试与上岗问题，异常时停止托管转人工               | `interview.passed` / `candidate.hired` / `handoff.triggered` | 转人工精确率（该转的转、不该转的不转）；转人工后真人是否接续；复聊是否在该停时停       |

横切指标（所有阶段共用）：

- **硬错误率**：编造岗位事实、错城市、错时间、假回执、泄露内部信息。目标 0，任何一例进周报置顶。
- **转人工精确率**：`handoff_events` 里 reason_code 与对话事实一致的比例；由 weekly-handoff-analysis 抽样。
- **稳定率**：同一用例重跑 3 次结论一致的比例（pass^3）。模型不确定性是 badcase 的常见来源，只跑一次的"通过"不算通过。目前没有自动生产者（批次重跑 2026-09-02 裁定不做，闸门保持轻量），需要时手工重跑后按台账格式登记。

三层的结论数字统一落 [质量指标台账](../quality-metrics-ledger.md)：一行一个（日期, 任务, 阶段, 指标）；阶段名与指标名以本节为白名单，`pnpm run quality-ledger:validate` 在 CI 里校验。

## 2. 三层评估

| 层                        | 管什么                                                                                                                                                     | 数据与工具                                                                                    | 频率                                            | 结论去哪                                         |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | ----------------------------------------------- | ------------------------------------------------ |
| **L1 确定性轨迹断言**     | 机器能判的行为：调了什么工具、入参对不对（城市/品牌/半径）、有没有不该调的（拉群/booking）、记忆与表单状态（`memorySetup` / `memoryAssertions`）、守卫终态 | test-suite 场景用例 + `tool_calls` / `execution_trace`；checkpoint 需结构化（待办，见 §4）    | 每次修复后重放；周批                            | test_executions；BadCase 状态回写                |
| **L2 校准过的判官**       | 机器判不了的语义：回复是否达成阶段目标、口径是否合规、该不该发复聊                                                                                         | test-suite Claude 评审（锁定 rubric，reviewer_source=claude）；复聊 blockReason；入站词表     | 判官周标定（rubric 与阈值见 judge-calibration） | 质量指标台账（判官精确率）；不达标即降级         |
| **L3 生产抽样与业务结局** | 真实对话里出了什么事，以及阶段完成信号的漏斗                                                                                                               | 定时任务（badcase 扫描、守卫审计、转人工周报、收资日报）+ `ops_events` 漏斗 + 飞书 BadCase 表 | 日/周                                           | 各任务报告；BadCase 表；周报；数字进质量指标台账 |

三层共用 §1 的指标名与阶段名；报告里出现的指标必须能在本页找到定义。

## 3. 发版闸门（轻）

- 必过：`pnpm run ci:check`（lint / typecheck / 单测 / 词表与地理校验）。
- 可选：改 prompt 或换模型前，跑该改动对应类目的场景用例子集（`POST /test-suite/batch` 定向），只看 L1 断言与硬错误，不追求全量通过率。
- 不做：回归验证全量重放、相似度门槛。线上问题走 badcase 快速修复环。

## 4. 已退役与待办

**已退役**

- LLM 相似度评分器（原 `src/evaluation/llm-evaluation.service.ts`，2026-09-02 删除）。三条硬伤：拿真人历史回复当标准答案，岗位库存与状态已变；tool_grounded 模式把工具结果当真相，上游工具错了它看不见；四维加权让流程停滞的回复过线。60 天仅 10 次运行，标定 10 条里 2 条高分实错。
- 出站守卫 LLM 语义审查器（2026-08-28 起生产归零，PR #1045）。

**待办（各自独立立项）**

1. 回归验证整条线下线：对话快照重放、验证集飞书回写、Dashboard 回归页、SOP 里"验证集通过才算已解决"的规则改为只看测试集。
2. checkpoint 结构化：把测试集"期望行为"从自由文本改为可判断言（工具名/入参键值/禁止调用/回复必含与必不含），L1 才能机器化。

**已裁定（2026-09-02）**

- pass^3 批次重跑：不做。发版闸门保持轻量，不给场景用例批次加重跑参数；§1 稳定率保留定义、无自动生产者。
- 统一指标表：不建数据库表、不做接口，定时任务结论落 markdown 台账 [quality-metrics-ledger.md](../quality-metrics-ledger.md)，CI 校验名字白名单。
