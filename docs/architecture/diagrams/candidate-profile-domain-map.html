CANDIDATE PROFILE DOMAIN

一份档案,
谁说了算

招聘 Agent 的核心资产只有一份:候选人档案——姓名、手机号、城市、品牌意向、用工形式……这套重构给档案里的每一条信息安排唯一的负责人:谁解析、谁裁决、谁保管。本文是 candidate-profile-domain-refactor-plan.md 的图解版。

贯穿全文的案例 · 改编自真实 P0(badcase vkikct39)
小张在同一个消息窗口里发来三样东西:一张 BOSS 直聘岗位截图(上面印着招募经理的手机号和「18-40岁」门槛)、一句手打的「我叫张丽鑫,03年的,想找奶茶店的兼职,我在顺义」、一条[引用 高雅琪:望京必胜客急招] 的追问。——在旧链路上,截图里的经理手机号和「18岁」曾被当成候选人自陈提交进真实报名表,AI 面试短信发到了招募经理手机上。
name 张丽鑫 age 03年→23 brand 奶茶店→品类展开 city 顺义→北京 labor_form 兼职 ⚠ 截图手机号 必须拦下 ⚠ 引用名"高雅琪" 必须拦下

小张的三条消息,从进门到写进档案再到被报名工具消费,每一站只做一件事——这就是全部架构。

01/ 09 · 问题定义
candidate profile

全系统只有一份核心资产:候选人档案袋

召回岗位要看城市和品牌意向,报名要姓名和手机号,拉群要城市,守卫要身份。所有业务动作都建立在同一件事上——「关于小张,我们知道什么」。把它想象成一只入职档案袋:每往里放一页纸,都必须回答四个问题。

① 这是什么字段?

「奶茶店」是品牌线索还是工种?「顺义」是区还是城市?把自由文本翻译成标准字段值——这是解析问题。

② 谁说的?

是小张亲口说的,还是岗位截图上印的,还是引用气泡里经理说的?——这是出处问题,vkikct39 那次事故就死在这一问缺席。

③ 有多可信?

手打的真名 vs 微信昵称、白名单精确命中的城市 vs LLM 猜的城市——不是所有信息都够格进报名表。这是置信问题。

④ 冲突了听谁的?

上周说在杭州、今天定位在北京;截图里是必胜客、嘴上说想做奶茶——这是裁决问题。

i
这套架构的全部内容,就是给这四个问题各安排一个唯一的负责人。①归族一解析器,②③④归族二裁决器,保管归 memory。
02/ 09 · 为什么要动
status quo

同一句话,五个部门,五张表格

「候选人档案」从没被立为一等域。每次 badcase 打到某个字段,就围绕那个字段长出一套小系统,各带一份「信封」——值+来源+置信度+冲突规则。现在同一个「小张亲口说的手机号」,在五套结构里有四个名字,而全库没有一个互转函数。

memory/facts/ 已被搬空过两次——geo、brand 各迁走一批,每个文件头都留着迁移记录。剩下的不是「留下来的」,是「没搬完的」。
03/ 09 · 目标架构
target architecture · 全景图

一座法院:鉴定科、证物科、合议庭、档案室

目标形态是一座分工严格的法院。鉴定科(族一)把方言口供翻译成标准语言;证物科(visual)登记封存证物;合议庭(evidence)裁定每条主张采不采信;档案室(memory)只管保管与借阅;办案人员(tools/agent)拿着档案办事。src 根目录数不变,resolution 一词本就双关:entity resolution(实体解析)+ conflict resolution(争议裁决)。

族一的准入测试

「输入自由文本,输出该字段的标准值/极性/意图,零 IO 零 LLM 零状态。」——能拒绝东西:session 编排进不来,输出治理(如 sanitizeBrandName)进不来,任何读档案的代码进不来。

族二的准入测试

「输入多源主张,输出采信/拒绝/冲突+理由码,只准调族一做归一复算。」——能拒绝东西:IO 进不来,存储格式进不来,prompt 拼装进不来。

i
resolution 一词本来就有两义:entity resolution(把「奶茶店」解析成品牌集合)与 conflict resolution(裁决冲突证词)。两族共居一域不是凑合——是词义本身。
04/ 09 · 族一
field parsers · brand / geo / labor-form / candidate

鉴定科:每个翻译官只懂一种方言

小张那句手打的话,在鉴定科被拆给四个翻译官——每人只认自己那种「方言」,只输出标准语言。这正是你那句裁决的落地:品牌、地址、姓名本来就是平级的候选人信息,它们的解析器也平级。brand 和 geo 早就搬进来了,这次把 labor-form 和身份字段族(candidate)也接来,四科并列。

candidate/ 是唯一的新科室

把散在 tools/shared(九个 parse*、isStudent 唯一识别器、真名问答解析)和 memory/facts(逐字段提取器、name-guard 纯函数)的解析器合并成每字段一个。合一即消灭两轨漂移——同一个字段两套正则、守卫各缺一半的时代结束。

合一顺手修掉的真 bug(勘探实锤)

「需要有健康证是吗」疑问句在 tools 轨被判有证直进 booking;「身高165以上能做吗」的复述门槛被当自陈身高;「要招男生吗」被提取成性别。单一解析器取两轨守卫的并集。

i
准入判据能拒绝东西:brand→geo 的同形地名消歧是显式登记的例外(删掉会复活两个 P0);其余解析器之间互不依赖。
05/ 09 · 证物科
resolution/visual

证物科只登记证物,不判案

小张那张岗位截图进门时先到证物科:vision 模型产出描述与结构化 sheet,finalizeVisualFactSheet 做三道登记手续——key 白名单过滤、按 kind 补 ownership 归属、身份证号脱敏。到此为止。这张证物「能不能采信、能写进档案哪一格」,是合议庭的事,不是证物科的事。

曾经的误会

visual 像 brand/geo 一样是解析器

它没有「文本→词表」这件事:值的载体仍是描述文本,真正生效的是 kind 对档案写入的门控。把消费策略也留在 visual,等于让证物科替法官判案。

目标分工

生产归一留 visual,消费策略归 evidence

schema、finalize、模型词表(生产侧)留在证物科;resolveExtractionScope 授权域矩阵(消费侧)迁入合议庭,与文本来源的准入规则合成同一张表。

!
顺手修一个现行漏洞:守卫的 review-packet 目前绕过 finalize 手搓 sheet——白名单/归属/脱敏三道登记手续在评审链路全部失效(Phase 0-5)。
06/ 09 · 族二
resolution/evidence · claim 裁决

合议庭:一条主张要过三道审

任何想写进档案的信息,先变成一条主张(claim):「name=张丽鑫,producer=rule,quote="我叫张丽鑫,03年的"」。合议庭对每条主张过三道审。这套引擎已经存在(收资证据化专项,shadow 运行中)——重构只是给它正名分、迁居所、扩管辖:从 precheck 的旁路视图,升格为全部档案字段的唯一裁决器。

合议庭的新管辖(重构收编)

session.service 里散着的 11 道臆造门(纯数字姓名/引用发言人/第三方号码/话题证据门…)、city 的让位规则(同一条判据曾手写 4 遍)、rule×LLM 合并策略(3 份手抄清单已漏掉 brand_ids)、快照对账语义——全部收进 evidence,写成按字段穷尽的 Record:加字段不表态,编译直接失败。

来源分类学互转表

五套「谁说的」枚举不再各说各话:evidence 持有唯一一张互转表,candidate ↔ user_text ↔ rule ↔ ownership:candidate 的对应关系首次显式化,有损塌缩必须写在表上,禁止再私转。

i
brand 的极性状态机不并入:品牌是「状态」(要/不要/都看看,替换式)不是「标量值」,强套 claim 信封是伪统一。它保留自己的 reducer,只作为档案的一个字段接受统一读模型——这是方案里声明的非目标。
07/ 09 · 亲手试
resolveExtractionScope · 授权域矩阵

拨一拨:这条消息能写进档案的哪几格

整套架构里最容易被误解的一件事:不是所有进来的信息都有资格写档案。每条消息按「来源」领到四扇门的开关组合——身份、手机号、偏好、地理。点下面的来源,看四扇门怎么变。开关逻辑与 visual-fact.policy.ts 的 KIND_EXTRACTION_SCOPE 逐字一致。

📞

💼

i
这张矩阵是 Record<VisualFactKind, MessageExtractionScope> ——加一档新 kind 不表态,编译期直接报错。旧实现是 if 链,新 kind 会静默落进全关兜底,事实被吞掉且无任何信号。
08/ 09 · 档案室
memory after

档案室退回档案室

memory 不可替代的职责一直只有一半:存取、TTL、并发、生命周期、沉淀、召回编排。另一半——「事实怎么算出来」——是历史欠账挤进来的。重构后 extractAndSave 只剩三步:调 LLM 抽取 → 调 evidence 裁决链 → 落盘。

现在

档案室里开着庭

session.service 单文件 1883 行,其中约 520 行是判据:11 道臆造门逐条内联、city 六条写入路径各带一份让位规则、rule×LLM 合并靠三份手抄字段清单(已漏 brand_ids)。改一条规则要在行间注释里考古。

重构后

只管保管与借阅

判据全部住 evidence,以字段为键、Record 穷尽、纯函数可单测。memory 的落盘格式(SessionFactValue/Redis 三态兼容)一字不动——统一发生在「进出档案的裁决通货」层,不动存量数据。

brand_state:留在原 hash,收口 key

品牌状态继续住 factsv2 hash 的单字段,但 BrandStateService 删掉自己抄的那份 buildHashKey,读写走 SessionService 唯一出口——key 格式从此只有一处定义。

precheck 快照:存储归 memory,语义归 evidence

快照是 precheck→booking 的事务握手,不是记忆。水位计算、对账闸、字段映射表全归 evidence;CandidateSnapshotService 只剩 Redis get/set。

09/ 09 · 落地
rollout · 每期独立发版

四期到位,先修 bug 再动家具

仓库每周发版、多会话并发改码,大爆炸不可接受。分期原则:每期独立可发版、独立可回滚、都有可观测的收益;Phase 1 的解析器合一是行为变更(不是纯搬迁),靠「分歧句用例清单」守——每个字段采用哪个口径,在 PR 里逐条可见。

P0
独立修 ×8

三个真 bug(健康证疑问句/身高门槛/brand_ids 丢弃)+ 守卫 packet 走 finalize + [位置分享] 标记收口等。与重构解耦,先发免押。

P1
立域断环

labor-form 平移;candidate/ 立域,两轨解析器合一(行为变更,用例清单守);ESLint 禁 memory→tools。

P2
evidence 立域

claim 引擎迁出 memory;快照闸/字段映射表归位;ESLint 禁 tools→memory/facts。环封死。

P3
策略收口

city 七路收成 producer 清单(试点);11 道门成裁决链;合并策略 Record 穷尽;来源互转表;简历判据合并。

P4
终态归位

授权域并入 evidence;memory/facts 解散;档案读模型收口;claim shadow→enforce(业务裁决 D4)。

需要裁决的三件大事(全部清单见方案 §5,D1–D8)

D1 简历判据两版合并采哪个口径——现行分歧正让健康证截图在 claim 轨被误拒(quote_not_found);D3 LLM 猜的城市要不要从 high 降 medium——直接改变拉群门放行面;D4 claim 引擎 shadow→enforce 的判决条件与时间表。

i
诚实声明:目录树非对称(族一 4 子域 + 族二 2 子域,界线靠文档与 ESLint);brand 信封不统一;落盘格式不迁移。这些是写进方案的接受项,不是遗漏。

一句话,记住整套架构

原始消息 → 剥标记(infra/utils) → 鉴定科解析(族一:brand·geo·labor-form·candidate) → 合议庭裁决(族二:evidence,三道审) → 档案室保管(memory,只存不判) → 办案消费(precheck·booking·拉群·prompt)。

解析的只解析,裁决的只裁决,保管的只保管。四个问题——这是什么字段、谁说的、可信吗、冲突听谁的——各有唯一负责人;小张的真名与城市写进档案,截图上的手机号、门槛年龄和引用前缀里的经理名,在①出处审就出局。
