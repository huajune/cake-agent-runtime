# 出站守卫 repair 链路架构评估（2026-07-27）

> 基于 2026-07-21 / 07-24 / 07-27 三期生产守卫质量审计（`guardrail_review_records` 全量档案 + `message_processing_records` 投递核验）。
> 触发背景：三期审计累计发现 repair 改坏并实际投递的案例后，对"这套 guardrail 是不是架构性错了"做一次分层裁定。
> 结论先行：**检测层是净正资产，问题集中在 repair 的"动手权"——不需要推翻，需要收权。**

---

## 1. 爆炸半径：问题到底多大

以 2026-07-24（完整工作日）为例：

| 层 | 量 | 说明 |
|---|---|---|
| 守卫审查的回合 | 395 | 全部命中+shadow 档案 |
| 语义 shadow（只看不改） | 366 | 再误判也不触达候选人 |
| 硬规则命中 | 29 | 其中 10 条 observe（看而不动） |
| **实际动手 repair** | **19** | 占当日回合 ~5% |
| repair 改好 | ~60% | 07-27 审计全量普查口径 |
| **已投递且实质有害** | **~3 条/天** | 编造政策、结论反转、星期翻错 |

三期变好率：54.5%（07-24，失败加权抽样）→ 60%（07-27，全量普查）。静默误伤连续三期为 0。

**定性**：不是"到处乱改"，是"在有权动手的 ~5% 回合里，良品率只有 ~60%"。范围小，但漏出的每一条都直接伤候选人体验。

## 2. 分层裁定

### 2.1 检测层：净正资产，保留并继续投入

- 硬规则命中精度大多 70%〜100%（`unsupported_store_status_speculation` 三期 100%；`job_detail_lookup_required` 是流程型命中，少硬假阳）。
- 语义 shadow 抓到的漏拦类型——薪资编造、面试形式臆造、"报名系统卡了我人工补报"式无证据叙述、岗位+距离编造——**硬规则和其它任何机制都覆盖不了**，是独有的检测能力。
- 例外：`settlement_cycle_mismatch` 语序假阳连续三期未收敛（07-27 命中 2/2 全假阳），属规则口径工程债，不是架构问题（PR #731 已修后缀否定+愿望复述两类）。

### 2.2 收敛策略（block/fail-open 分级）：已被生产验证是安全的

- `final_decision=block`（整轮静默）连续三期 0 例。
- fail-open 的"二审没过→回退首版"分支在 07-27 窗口实际**救了**一条候选人（`batch_6a62d97b…`：修复版把"有月结岗只是没日结"过度泛化成"什么都没有"，二审未过回退首版，候选人拿到的是更好的那版）。
- **这一档不需要动。**

### 2.3 repair 层：结构性脆弱，是所有已投递伤害的唯一来源

三期全部坏案例塌缩成同一句话：**repair 动了它不该动的东西。**

| 案例（均已投递核验） | 形态 | 根因 |
|---|---|---|
| 报名表压成一句话（07-21 锚定判例） | 结构压扁 | rewrite 自由重写 |
| 4 岗位详情 → "附近没岗位"（`batch_6a606ac5…`） | 结论反转 | replan 看不到首版 + 工具白名单缺地理召回 |
| "建议问店长" → 编造"半小时晚退不扣款"（`batch_6a38e61c…`） | 内容编造 | 纯流程违规（缺工具调用）却放开整段重写 |
| 面试"周二"→"周一" + "已提交"→"稍后回执"（`batch_6a630be4…`） | 已确认事实被改 | **提示层保护已生效仍被击穿**——模型照抄仍翻错 |

结构性病因：**repair = 让第二个 LLM 拿着比首轮更差的上下文（早期看不到首版、工具白名单被砍、反馈是静态常量）去"修一句话"，却拥有重写整段的权力。** 这个组合天然产生"修一处、坏三处"。

最后一行案例是关键证据：`batch_6a630be4…` 发生在 v10.29.0（首版注入 + 双通道"逐字保留"指令）**上线之后**——提示层已经做到天花板，LLM 指令遵循永远到不了 100%。结论：**剩余伤害只能靠确定性机制兜，不能再往提示词里加字。**

## 3. 演进轨迹：三期修复在把 repair 从"自由重写"收敛成"受约束编辑"

| 时间 | 机制 | 性质 |
|---|---|---|
| 07-21 后 | fence-only 命中走确定性剥围栏，跳过 LLM 重写（`fence_stripped`） | 确定性最小修复 ① |
| v10.29.0 (#716) | replan 注入首版草稿 + 双通道逐字保留指令 | 提示层约束 |
| v10.29.0 (#716) | `detectRepairRegression` 一期：结构压扁 / 极性反转 → 回退首版 | 确定性回退闸 ① |
| PR #731 | 回归闸二期：`fact_mutated`（星期翻错）/ `commitment_downgraded`（既成副作用降级） | 确定性回退闸 ② |
| PR #731 | 流程型违规（`image_description_not_saved`）反馈补"原文逐字保留" | 向"补工具不重写"过渡 |

方向已经对了，但都是被 badcase 逐个逼出来的补丁。下一步应把这个方向**升格为架构约定**。

## 4. 目标架构：repair 动作阶梯（按优先级递减）

```
命中规则
  │
  ├─ ① 确定性最小编辑          能剥就剥、能替换就替换（围栏剥离、标记清洗、
  │                            结算词句级替换）。零 LLM，零回归风险。
  ├─ ② 保文补参                纯流程违规（缺工具调用/缺落库）：补执行工具，
  │                            文本逐字保留。LLM 只负责"要不要微调一句话"。
  ├─ ③ 受约束重写              事实性违规才允许 LLM 改文本；必须带首版 +
  │                            违规句定位 + 工具事实包（含 booking 盖章字段）。
  └─ ④ 确定性回退闸（出口必经） 修复版改动了未点名的已确认事实 / 结论极性 /
                               结构块 / 既成副作用宣称 → repair 判失败，
                               回退首版（P1/P2）或 block（P0）。
```

规则目录相应增加一个声明字段（示意）：`repairStyle: 'minimal_edit' | 'preserve_text' | 'rewrite'`，让"该用哪档"成为规则登记时的显式决定，而不是散落在 runner 分支里的隐式行为。

**设计原则**（从三期审计提炼）：

1. **检测可以广，动手必须窄**——LLM 负责发现问题，确定性代码负责改动文本；LLM 改文本是最后手段且必过回退闸。
2. **回退闸只做"比较"不做"判断"**——不判断修复版好不好（那是二审的事），只比较"是否改动了不该动的东西"（日期星期、副作用宣称、结构块、结论极性），纯代码可枚举。
3. **fail-open 优于静默，首版优于坏修复**——生产三期验证：静默 0 伤害容忍、"回退首版"多次救人；危险的从来是"干净通过二审的坏修复"。
4. **每档新增豁免/回退形态必须有已投递的生产 trace 实证**——本文所有机制均可回指 trace，杜绝想象中的防御。

## 5. 残留风险与观测

- 回退闸是枚举式的，未来会出现第五种、第六种回归形态——**接受**，用守卫审计（每 2 天定时任务）持续兜；每次新形态照第 3 节流程补。
- `job_detail_lookup_required` 是命中量最大、repair 失败最集中的规则，其"该查未查"的检测价值与 replan 修复的低良品率是两回事——若阶梯落地后其 replan 档良品率仍 <70%，考虑降为 observe + 语义审查接管。
- 二审对"编造性新增断言"（无中生有的政策/福利）仍无确定性覆盖（`repair_regression` 只挡改动不挡新增）；候选方向是"修复版新增的政策类断言必须在首版或工具结果中有出处"，需要词表工程，暂列 backlog。
- 观测锚点：`guardrail_review_records.reason_code` 的 `repair_regression_reverted:*` 前缀即回退闸命中率；若某形态命中率持续为 0 可考虑下线，持续偏高说明上游 repair 质量退化。

## 6. 结论

| 问题 | 裁定 |
|---|---|
| 这套 guardrail 架构错了吗 | **没有**。检测层、shadow 通道、observe 档、收敛分级都被三期生产数据验证为净正或零伤害 |
| 哪里在漏 | repair 层的"整段重写权"。所有已投递伤害均出自这里 |
| 怎么修 | 不推翻，收权：把"确定性优先、LLM 兜底、出口必过回退闸"的动作阶梯升格为架构约定（第 4 节） |
| 已走到哪 | 阶梯 ①④ 已有两期实现（fence_stripped + 回归闸四形态），② 有第一个试点（image_description），③ 的上下文注入已落地；缺的是 `repairStyle` 显式化与"新增断言溯源"检测 |
