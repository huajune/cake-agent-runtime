# 岗位报名标签配置修正清单（给运营）

> 数据来源：2026-08-18 生产全量扫描——450 品牌 → 468 个在招岗位 → 109 个报名标签。
> 结论：约 **60 个标签是十几个"同一问题"的重复变体**，规范化后全库约 **30 个标签就够**。
> 重复不修的影响：AI 无法跨岗位复用候选人已答信息（同一人换个岗又被问一遍同样的问题）、
> 筛选无法自动执行、数据无法统计。
>
> **修正五原则**：
> ① 一个问题只用一个标签（新建岗位从既有标签选，不新造同义标签）；
> ② 筛选条件配进「拒绝选项」，不写进标题（标题写「是否为学生」+拒绝选项「是」，
>    而不是标题写「不要学生」）；
> ③ 有限答案的问题用单选/多选，不用文本（文本无法自动筛选）；
> ④ 标题是给候选人看的问题，不是给招募经理看的指令或岗位说明；
> ⑤ 涉敏感信息的标签（婚育/籍贯/常住地）先过合规审查再上。

## 零、敏感要求项（业务要求如此，照实执行——2026-08-18 用户裁定）

> 裁定：籍贯筛选、婚育状况收集是**真实业务要求，不要求业务修改**。
> 处置原则改为：**判定层照配置执行，披露层绝不说破**（AI 拒因永不提及籍贯/婚育，
> 走换岗承接话术+因果隔离；对话侧守卫红线继续有效——它管的是 AI 说什么，不管业务筛什么）。

**3 籍贯**（14 岗，其中 6 个果蔬好岗配置了地域排除——接受集抠项形态）
- 照常执行：候选人籍贯不在接受集 → 岗位不合格 → **换岗承接，不提籍贯**；
- 对配置方的唯一请求（为了能执行，不是为了改要求）：提供选项全集
  （契约建议书 8.5 optionUniverse）——没有全集，AI 无法分辨"全集收集"与"子集筛选"，
  等于要求筛却看不见筛选条件。

**754 婚育状况**（瑞族V-ZUG ×1）
- 照常收集；建议（提升可用性，非必须）：改单选给固定选项（已婚已育/已婚未育/未婚），
  否则自由文本下游难统计；
- AI 侧收集话术按低压力表单项处理，披露档 RESTRICTED（若用于筛选，拒因不外泄）。

**751 常住地是否在张家口**（必胜客 ×1）
- 若为通勤考量建议并入 325 通勤时间（可执行的筛选形态）；若为地域要求则同籍贯处置：
  改单选 是/否 使其可机判，AI 执行但不说破。

## 三、类型改造（筛选类 TEXT → 单选+拒绝选项）——为什么必须改 + 逐个改法

**先纠正一个分类前提**：TEXT 的默认语义就是**收集项**（收答案随报名提交给门店看），
这没有问题、也不必改。需要改的只是其中一小类：**标题是"要求句"的 TEXT**
（不要学生及暑假工/需要中餐厅经验/常住地是否在张家口等，约 5-8 个标签）——
它们的筛选目前由 AI 读中文标题做语义判断（软筛，有人把关但依赖模型逐次读对），
改成选项+拒绝配置后升级为机器硬筛（一次配置永久生效，不漏）。
判断一个标签该不该单选化，两问检验：**答案能穷举吗？答案会影响能否报名吗？**
两个"是"→必须单选+把不合格答案配进拒绝选项。

**正确示范（照抄即可）**：性别(771)、有无本地健康证(13)、学历(2)、学信网(703)、
能做多久(387)、通勤时间(325)、可在岗几个月(744)、是否接受厨房工作(692)。

逐个改法（未随 §四 合并覆盖的独立项）：

| labelId | 现状 | 目标配置 |
|---|---|---|
| 500 周末是否在岗(97岗) | TEXT | 单选 能/不能；周末必须在岗的岗拒绝 [不能] |
| 572 是否接受多家餐厅共享(105岗) | TEXT | 单选 接受/不接受；拒绝 [不接受]；"共享"含义写进说明栏 |
| 763 是否在缴纳社保(31岗) | TEXT | 单选 在缴/未缴；**用途先向业务确认**（灵活用工合规通常要求"未缴"，则拒绝 [在缴]），确认后配拒绝并在说明栏写明原因 |
| 670 能否工作半年以上(3岗) | TEXT | 并入 387（拒绝 [3个月内] 或 [3个月内,3-6个月] 按岗配） |
| 738 班次是否都能接受(3岗) / 755 早晚班次都能接受吗(1岗) | TEXT | 并入 741 多选（哪个班次缺人就把缺的班次配为必选/拒绝缺席） |
| 641/668/611/724 周四六日族(34岗) | TEXT | 并入 500 单选（能/不能） |
| 481 是否接受轮岗(1岗) | TEXT | 单选 接受/不接受；拒绝 [不接受] |

**纯收集项保持 TEXT 不动**（答案不可穷举）：姓名/手机号/年龄/身高/体重/住址/
出生日期/工作经历/意向岗位/所学专业。
