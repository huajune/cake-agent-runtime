# 岗位报名标签配置修正清单（给运营）

> 数据来源：2026-08-18 生产全量扫描——450 品牌 → 468 个在招岗位 → 109 个报名标签。
> 结论：约 **60 个标签是十几个"同一问题"的重复变体**，规范化后全库约 **30 个标签就够**。
> 重复不修的影响：AI 无法跨岗位复用候选人已答信息（同一人换个岗又被问一遍同样的问题）、
> 筛选无法自动执行、数据无法统计。
>
> **修正五原则**：
> ① 一个问题只用一个标签（新建岗位从既有标签选，不新造同义标签）；
> ② 筛选条件配进「拒绝选项」，不写进标题（标题写「是否为学生」+拒绝选项「是」，
>    而不是标题写「不要学生」）；
> ③ 有限答案的问题用单选/多选，不用文本（文本无法自动筛选）；
> ④ 标题是给候选人看的问题，不是给招募经理看的指令或岗位说明；
> ⑤ 涉敏感信息的标签（婚育/籍贯/常住地）先过合规审查再上。

## ⚠️ 零、优先处理：合规风险项（含"接口现状→怎么改 AI 才能消费"）

> 说明：标题业务侧可以不改；但**接口目前返回的形态让 AI 无法正确消费**，
> 下面每条写清"现在返回什么 → AI 消费时发生什么 → 最小改法"。

**754 婚育状况**（瑞族V-ZUG ×1）
- 接口现状：TEXT、无选项、无说明（labelInstructions 为空）。
- AI 消费问题：AI 只能照标题**原样开口问候选人婚育情况**（就业歧视高风险问句由 AI 替公司说出）；
  且 TEXT 无筛选信号，答案收了也不知道用途。
- 改法：优先**下线**。业务确须保留则：①改单选并给固定选项；②labelInstructions 写明
  用途与话术边界；③**永不配拒绝选项**（不得作录用筛选——法规红线）。

**751 常住地是否在张家口**（必胜客 ×1）
- 接口现状：TEXT、标题内嵌具体城市、无选项。
- AI 消费问题：筛选意图藏在标题里，AI 与服务端都无法机器执行——候选人答"不在"，
  报名照样提交，白约一场面试。
- 改法：改为中性的通勤类标签（复用 325 通勤时间，单选+拒绝[不符合]）；
  若必须保留原意：改单选 是/否 + 拒绝[否]，筛选才真正生效。

**3 籍贯**（果蔬好×8 必胜客×4 乐高×2）
- 接口现状：SINGLE_OPTION、accepted=29 个省级全集、**无拒绝选项**。
- AI 消费判定：全集接受+零拒绝 = **纯收集项**（不构成筛选），AI 可正常消费，此条现状可用。
- 风险提示：将来若有人给它配拒绝选项=省籍筛选（歧视红线）。建议海绵侧把该标签
  **锁死禁配拒绝选项**；AI 侧已按"禁明说"披露档处理。

## 二、标题病清单——逐条给"接口现状 → AI 消费问题 → 目标配置"

**728 不要学生及暑假工**（肯德基×32）／**735 不要暑假工！**（必胜客×1）
- 现状：TEXT、无选项。这不是问题是**规则**——AI 若照标题向候选人提问会问出
  「你是否'不要学生及暑假工'？」；不问则规则无人执行。
- 目标配置：标题「当前身份」；类型 单选；选项 学生（在读）/暑假工/社会人士；
  该类岗位拒绝选项配 [学生（在读）,暑假工]；说明栏写"本岗位不招在读学生与暑期工"。

**762 需要中餐厅服务员经验**（小吊梨汤×1）
- 现状：TEXT，要求当标题。AI 无法把"需要"翻译成可执行筛选。
- 目标配置：标题「有无中餐厅服务员经验」；单选 有/无；拒绝 [无]。

**730 确认人选接受工作内容**（肯德基×31）
- 现状：TEXT，这是**给招募经理的操作指令**，不是给候选人的问题。

  工作内容要点写进说明栏（AI 会先向候选人念说明再问）。

**650 这个岗位做汉堡的 / 651 这个岗位是做汉堡的**（必胜客，同一句话建了两个标签）

**266 有无健康证；有无分拣**（奥乐齐×6）

## 三、类型改造（筛选类 TEXT → 单选+拒绝选项）——为什么必须改 + 逐个改法

**为什么必须改（关键认知）**：目前 109 个标签里 86% 是 TEXT。TEXT 标签**没有任何
机器可执行的筛选形态**——筛选意图只存在于标题的中文措辞里（"不要/需要/能否"），
AI 和海绵服务端都执行不了。也就是说：**今天所有 TEXT 型筛选实际上无人把关**。
判断一个标签该不该单选化，两问检验：**答案能穷举吗？答案会影响能否报名吗？**
两个"是"→必须单选+把不合格答案配进拒绝选项。

**正确示范（照抄即可）**：性别(771)、有无本地健康证(13)、学历(2)、学信网(703)、
能做多久(387)、通勤时间(325)、可在岗几个月(744)、是否接受厨房工作(692)。

逐个改法（未随 §四 合并覆盖的独立项）：

| labelId | 现状 | 目标配置 |
|---|---|---|
| 500 周末是否在岗(97岗) | TEXT | 单选 能/不能；周末必须在岗的岗拒绝 [不能] |
| 572 是否接受多家餐厅共享(105岗) | TEXT | 单选 接受/不接受；拒绝 [不接受]；"共享"含义写进说明栏 |
| 763 是否在缴纳社保(31岗) | TEXT | 单选 在缴/未缴；**用途先向业务确认**（灵活用工合规通常要求"未缴"，则拒绝 [在缴]），确认后配拒绝并在说明栏写明原因 |
| 670 能否工作半年以上(3岗) | TEXT | 并入 387（拒绝 [3个月内] 或 [3个月内,3-6个月] 按岗配） |
| 738 班次是否都能接受(3岗) / 755 早晚班次都能接受吗(1岗) | TEXT | 并入 741 多选（哪个班次缺人就把缺的班次配为必选/拒绝缺席） |
| 641/668/611/724 周四六日族(34岗) | TEXT | 并入 500 单选（能/不能） |
| 481 是否接受轮岗(1岗) | TEXT | 单选 接受/不接受；拒绝 [不接受] |
| 109 是否需要住宿(1岗,已单选) | 单选无拒绝 | 现状可用（纯收集项，无需拒绝） |

**纯收集项保持 TEXT 不动**（答案不可穷举）：姓名/手机号/年龄/身高/体重/住址/
出生日期/工作经历/意向岗位/所学专业。

## 五、改完之后的核对机制

运营修正完成后通知技术侧，我们重跑同款全量探针（450 品牌→全部在招岗位→标签），
按以下判据自动核对（基线快照已存档 label-baseline-20260818.json.gz）：

1. 上表"替换映射"左侧的全部变体 labelId 在生产标签中**岗位数归零**；
2. 标签总数 109 → 约 35 以内；
3. 标题病清零（无未闭合括号/无指令式标题/无感叹号/无一格两问）；
4. 学生/周末/时长/天数四个筛选族全部为单选，且有筛选需求的岗配有拒绝选项；
5. 754 婚育状况已下线；751/籍贯类已处置。

核对报告会逐条给出通过/未通过与残留岗位清单。
