## 一、结论

1. **方向对，但不能「把政策全抽到后台」一步到位。** 清点出的约 190 条里，纯政策事实只有二十来条，其余七成以上是「政策和行为规则写在同一句里」。能搬的是拆出来的政策那一半；行为那一半（什么时候调哪个工具、不许编造、先查证再转）必须留在代码里。
2. **行业 Skill 只适合装一类东西：平台级的默认口径和标准答法。** 另外三类各有现成的住处，不该再搬：数值阈值（已在策略配置的「业务阈值」里）、复聊的时间参数（已在托管配置里）、岗位事实（在海绵岗位数据里）。合规红线（残障、民族、户籍、婚育不得外显，面试后流程一律真人）不进口径库，留在红线里。
3. **只加口径文本不会生效。** 现行提示词里有三处「工具没返回的业务事实禁止用通识补充」的禁令，运营允许的「泛泛回答」正好撞上它们；还有一条常驻自检明文禁止说「必须本人银行卡」。口径进库的同时必须同批改这些规则。
4. **口径库仍由我们自己维护**【已裁定】：后台只是展示，不开放运营编辑，所以不需要审批、差异预览、独立发布这一套。摸底时发现的后台现状（策略接口免鉴权、保存无校验、变更记录停写）记在 3.4 备查，不作为这件事的前置。
5. **15 条口径里，有 7 条不用等口径库、现在就能按缺陷或提示词修改落地**；日结和健康证两条已裁定，不用再问运营；有 1 条根本不是口径问题（阶梯薪资）。

小结：不用等口径库的 7 条（O1、O2、O3、O5、O8、O11，加 O10、O12 可先改提示词）；进口径库的 8 条（O4、O6、O7、O9、O13、O14、O15，加 O10、O12 的政策句）。

**和现有红线的一处潜在冲突**：生产红线第 3 条是「已约面阶段问『店长会联系吗』，直答『后续由我们跟进』，严禁让候选人自行联系门店或找店长」。O4、O14 的答法是「提前和店长说」「问店长」。两者管的事不同（一个是面试前谁对接，一个是在职期间的请假和离职），但并存会让模型混淆，口径条目要写明适用的问题。

## 三、摸底结果【事实】

### 3.1 行业 Skill 现状

- 数据层管道是现成的：建表时就有这一列，版本化迁移和发布函数都逐列拷贝它，跨环境同步脚本也带它。不需要加列，不需要改发布函数。
- 缺的是五样：类型、写接口、校验、提示词消费点、前端编辑器。前端现在是「功能开发中」的占位组件，没接配置。
- 生产值：正式版第 15 版（06-05 发布）和测试版都是空数组。
- 仓库里没有关于行业 Skill 的任何设计。原则文档对 skill 的定位是「承载做事的步骤、按需拉取」；政策口径是事实不是步骤，名字和内容有点错位；后台维持现状（#18），页签不改名、不做编辑器。

### 3.2 政策内容散在哪

| 位置 | 清点条数 | 构成 |
|---|---|---|
| 提示词各段（主要是咨询手册 37 条、常驻自检 11 条） | 59 | 53 条是政策与行为混写 |
| 工具说明与工具返回指令 | 77 | 44 条混写，18 条纯政策，15 条纯行为 |
| 守卫、复聊、收资、策略种子 | 56 | 48 条混写 |
| 生产红线 | 10 条里至少 4 条是政策 | 健康证宽口径、兼职不缴社保、某品牌目前仅上海在招、预约失败时的衔接话术 |

同一件事多处居住是常态：健康证住五处；发薪与签约主体住渲染代码、手册、常驻自检、类型注释四处。

写死在渲染代码里的口径（搬不搬要分开看）：合作模式推出的发薪与签约结论、月结自动补的「次月发上月」、阶梯薪资按月清零、保险字段的敏感标注、健康证何时办的判定词表、到店话术模板。

台账里有一组到期未处理的临时规则：暑假工两条规则的复查点写的是「约 2026-09」，已到期。

### 3.3 运营口径与现行文本的直接冲突（搬之前必须先解决）

1. 岗位查询工具说明里一条「工具未返回的业务事实禁止用通识补充」：明文禁止「一般日结当天结」这类回答，并把「排班固定还是灵活、试用期」点名为转人工示例。
2. 常驻自检的薪资工时一条：要求结算、工时事实逐字对应工具返回。
3. 常驻自检的银行卡一条：禁止说「必须」。
4. 渲染代码里 RPO 发薪「必须转人工」。
5. 转人工工具场景 12 把「几号发几月工资」列为转人工。

### 3.4 策略配置后台的现状

| 项 | 现状 |
|---|---|
| 鉴权 | 整个策略控制器免 token，是业务模块里唯一一个；保存和发布接口因此没有鉴权。前端其实每个请求都带 token，收回不影响后台使用 |
| 保存校验 | 只检查是不是数组或字符串。没有条数、单条长度、总长度上限，不校验元素类型。写库是整列覆盖，无并发保护，后写者胜 |
| 变更记录 | 变更记录表从 2026-03-30 起没有任何代码写入；前端的变更记录弹窗没有挂载；发布时的版本备注恒为空 |
| 发布粒度 | 整份快照：测试版转正式版，再复制出一条新测试版。运营发布口径会连带研发在测试版里改到一半的红线和阶段目标 |
| 缓存 | 进程内 60 秒；发布后清空。用 SQL 直改库只能等 60 秒 |
| 故障行为 | 缓存过期且读库失败时整轮失败，没有旧缓存兜底 |
| 谁在读 | 只有主生成器。复聊 Agent、无工具改写、出站守卫都不读策略配置 |
| 回归 | 调试对话和对话回归读测试版；test-suite 单条执行在同时带了账号两个 ID 时会切到正式版，用测试版口径跑回归的结果可能失真。test-suite 没有确定性的文本断言 |
| 提示词位置 | 红线和阈值在稳定前缀里（跨轮字节不变，吃得到前缀缓存）。口径库全量静态注入到同一段，缓存行为与红线相同。提示词膨胀告警阈值 6 万字符，正常约 4.3 万 |

### 3.5 现有纪律对这件事的约束

- 台账的「规则该放哪」判定树只分类行为约束，**业务事实没有分支**，要新增一支。
- 台账有一条长效裁定：「策略文本的编辑主体只有我们（你和 AI 会话），后台侧不加额外约束」。口径库沿用这条，不重开。
- 原则文档最强的一条约束：「零审查的居所是最危险的居所。任何新增内容居所必须同时回答谁审、怎么审、多大算超」。
- 三条既有铁律落到这件事上：同一约束只准住一处 → 迁移即回收，搬一条删一条；职责迁移必须回收 → 渲染代码或提示词里的政策句搬走后原处要删；临时规则必须标过期条件 → 口径条目要带复查日期。
- 原则明确反对为口径新增守卫或正则路由。口径的合法形态是「进上下文、由模型判断」的提示便签。

## 四、口径库方案【已裁定 #18、#25】

### 4.1 装什么、不装什么

| 装 | 不装 | 原因 |
|---|---|---|
| 平台级默认口径与标准答法（O4、O6、O7、O9、O10、O12、O13、O14、健康证、兼职不缴社保、中介不收费等） | 数值阈值 | 已在「业务阈值」里，结构化且工具层会读 |
| | 复聊时间参数 | 已在托管配置里，一个数不能住两处 |
| | 岗位事实（发薪日、阶梯、排班） | 在海绵岗位数据里；口径只做字段没写时的兜底 |
| | 合规红线 | 改错的后果是合规事故，留在红线里 |
| | 行为规则 | 归研发 |
| 二期：按合作模式、品牌、城市分叉的口径文案 | | 分叉的判断逻辑留在代码，文案由口径库提供 |

### 4.2 优先级

红线 > 岗位工具字段 > 口径库默认值 > 转人工。一句话：**岗位字段优先，口径兜底**。口径与岗位字段冲突时以字段为准，并把冲突记下来交运营修数据。

### 4.3 条目结构

每条包含：编号、主题、适用的问题（候选人怎么问）、标准答法、适用范围（全平台 / 月结岗位 / 餐饮岗位……）、兜底动作（自答，或答到哪一步之后转人工）、依据与复查日期、状态。首期只做平台级，预计 20–40 条、3000 字符以内。

### 4.4 注入方式

首期全量静态注入，放在红线和阈值旁边的稳定前缀里：最简单、吃得到前缀缓存、不依赖模型想起来去调工具（零工具回合编造是已知问题）。按品牌和城市选择性注入会在会话中途打断前缀，放二期。

### 4.5 必须同批改的行为规则

1. 3.3 列的三处通识禁令加同一句豁免：「口径段已列出的标准答法视同有出处，可按原文回答；口径段没有的才转人工」；从举例里删掉已有字段或已有口径的主题。
2. 银行卡那条常驻自检改写（见 O10）。
3. 转人工工具场景 12 的举例修改（见 O3、O8）。
4. 无工具改写的证据包纳入口径库——现在它只拿到红线，政策句从红线迁走后它就看不到了。
5. 出站守卫的「岗位事实须有出处」把口径库纳入出处池。现有判据只认量化事实（金额、公里、时段），15 条口径的答法基本不含这类数字，首期风险低，但要补回归用例。
6. 全部登记台账；台账判定树新增「业务事实与标准答法 → 口径库」一支。

### 4.6 治理（已裁定：维持现状，以下不作为前置，仅备查）

口径库由我们自己维护，入库走现有的方式（数据迁移或后台，测试版与正式版两行一起改），每次变更照常登记 `docs/prompt-rule-ledger.md`。下表是摸底时列的、若将来开放运营编辑才需要的事项。

| 项 | 做法 |
|---|---|
| 鉴权 | 收回策略控制器的免鉴权 |
| 保存校验 | 条数、单条长度、总长度硬上限；内部术语禁用词（BPO、RPO、外包等）；示例人名与号码扫描 |
| 变更记录 | 恢复写入并记录操作人；或正式废弃该表，改用版本快照对比加「恢复某版本」接口 |
| 发布粒度 | 口径库单独发布，不连带红线和阶段目标；发布前给差异预览 |
| 回归 | 一套「政策问答」回归集，发布前必跑；给口径类用例补关键词与禁词断言 |
| 编辑主体 | 若将来开放给运营，要重开台账那条裁定，并定口径变更由谁审；红线、阶段目标、人格仍只由研发编辑 |
| 故障行为 | 策略读取失败时用旧缓存兜底，不要整轮失败 |

### 4.7 分期

| 期 | 内容 | 依赖 |
|---|---|---|
| 第 0 期 | 不依赖口径库的：O1、O2、O3、O5、O8；O10、O12 先改提示词；承诺话术治理 | 无 |
| 第 1 期 | 口径库载体（类型、提示词段；不做写接口和前端编辑器，条目由我们用数据迁移入库，测试版与正式版两行一起改）；平台级条目入库；同批改行为规则；迁移即回收（手册、工具说明、红线里的政策句逐条搬、逐条删） | 第 0 期 |
| 第 2 期 | 按合作模式、品牌、城市分叉的口径；工具层按键取文案；复聊 Agent 是否也读口径库 | 第 1 期跑稳 |

### 4.8 风险

- 口径写错一句，60 秒内直接影响所有线上回复。缓解：每次变更登记台账、先在测试版用调试对话核一遍再改正式版。
- 模型把模糊答法说成承诺（「做得好会涨」「随时可以走」）。缓解：每条标准答法写明不能引申到哪。
- 口径文本里出现「我帮你问」这类措辞会触发承诺对账。缓解：入库前自查，答法一律写成候选人自己去问。
- 首期提示词增加约 3000 字符，对缓存无影响，对注意力有轻微影响；条目数设上限。
