## 一、P0-2 群核验 10 秒上限漏洞（预计平均 −10～12 秒）

现状：每天约 250 个回合（约 10%）在「核验是否已在群」等约 2 分钟。`src/biz/group-task/services/group-membership.service.ts:231`
的 `if (this.hydratePromise) return this.hydratePromise;` 让拉取途中到达的调用方绕过 `awaitHydrateBounded`。

- [ ] 第 1 步：该分支改走 `awaitHydrateBounded`，补并发调用方的行为测试。改后这些回合按「未核验」降级，与现有 10 秒截断语义一致
- [ ] 第 2 步：后台定时预热，回合只读缓存。约束：缓存冷或缺键仍返回 `verified=false`，不能当空集；`doHydrate` 改为写临时键再整体替换（现为先删后写，非原子）；白名单用全部兼职群；在 10 分钟 TTL 前预留约 2 分钟预热耗时；多实例用 Redis 锁保证单实例刷新
- [ ] 验证：`turn_data_sources` 中群核验 ≥15 秒的回合数降到 0；观察「重复拉群」类反馈是否上升

设计依据：该文件 52-53 行注释「调用方只等 10s，超时按「未核验」降级，预热本身继续在后台跑完」（v11.6.0 原意）。

## 二、P1-1 排队调度（预计平均 −8～12 秒，唯一明显拉低中位数的一项）

现状：只含一条消息的回合（占 70%）入队约 2 秒，但入队后到开始处理中位数 16.6 秒（配置的静默窗口是 5 秒），
最快 7 秒，25% 超过 25 秒；与时段负载、同会话上一轮是否结束、工作槽位（生产 20）均无关。
推算可解释约 8～9 秒（5 秒窗口 + 约 20 次 Upstash 往返，Redis 在 ap-southeast-1），其余 7～8 秒未定位。

- [ ] 第 1 步：补打点，不改行为、不加迁移。记录任务被取出、拿到执行槽、拿到会话锁、静默窗口检查结果及是否重排、取完待处理消息，以及各段 Redis 调用耗时；打点在内存里攒好后一次写入。跑一个工作日
- [ ] 第 2 步：按定位结果选择——队列交付慢则把队列与锁迁到与服务器同地域、共享且持久化的 Redis；串行往返多则合并为管道（保持「先写消息再建任务」顺序与加锁原子性）；窗口被反复重排则修触发源
- [ ] 待确认：生产服务器所在地域；如需迁移，是否接受新增同地域 Redis 实例

设计约束：不得用进程内定时器替换队列（违反 v5.6.1「SIGKILL 不再丢候选人消息」）；如需提前触发，每条消息仍照建队列任务作保底。

## 三、P1-2 给思考设上限（预计平均 −1～2 秒，主要砍长尾）

现状：主模型深度思考，单步输出超过 2,000 token 平均 82 秒；约 13% 的回合有思考超过 1,000 token 的步骤。
按阿里云百炼文档，qwen3.7 只认 `enable_thinking` 与 `thinking_budget`；我们传的 `reasoningEffort` 很可能不生效，
`thinking_budget` 未传（`src/llm/llm-executor.service.ts` 的 qwen 分支），环境变量 `AGENT_THINKING_BUDGET_TOKENS` 也不会下发给 qwen。

- [ ] 实测 `reasoningEffort` 对 qwen3.7-plus 是否有效（同一请求对比思考 token）
- [ ] 给 qwen 接上 `thinking_budget`，用回归集离线对比 1,000 / 1,500 两档：回归通过率、BadCase 类别、守卫改写率、耗时、缓存命中率
- [ ] 质量底线由用户与运营确认后再上线；「关闭思考」（估算 −8～10 秒）质量风险大，只在回归集通过后小流量试

理论收益（到上限即停、质量不变）：上限 1,500 约 −1.3 秒，1,000 约 −2.1 秒，500 约 −4.2 秒。

## 已决定不做（勿再提）

- 查岗工具直接接收地名：与地理域「歧义禁止猜测、城市冲突需确认、区级只报估算距离」设计冲突
- 查岗空结果在工具内自动放宽：放宽维度属语义决策，查岗说明已有细则
- 处理中途收到新消息整轮重跑：用户决定保持现状
- 回复后提前释放会话锁及其替代方案（跟进任务顺序、锁重检退避）：与「turn-end 在释放锁前完成」冲突，替代方案收益太低
- 拉群改为回复后异步及「同轮压缩拉群耗时」：与同轮拉群需求冲突，替代方案收益太低
- 删除默认降级链中重复的主模型：默认链被复聊、识图共用，主聊路由已去重
- 同一工具连续调用上限：4 月已实现
