# 运行时与业务数据模型改造执行计划

最后更新 2026-11-11。数据模型改造待实施，范围为 Cake 生产 `public` 中的 27 张业务表，以及读写这些表的 API、任务、报表和页面。下文容量与样本数据来自 11 月 5 日基线 `5e50c37b`，不表示今天的实时状态。

11 月 11 日核对的已发布基线为 `v11.15.4`：新普通 execute 回复采用 `single_pass`，群任务和复聊使用独立任务链。本次第一批先修复 pending 输入按身份确认和 replay 下标问题、清理无调用入口及过时说明；不实施本计划 P0–P9 的数据模型变更。后续按实际发布版本重新核对迁移、调用方和退出条件，再分批推进。

实施负责人由本任务的后端负责人担任，负责逐批 PR、迁移和对账。前端负责人验收页面与旧客户端，数据/运营负责人确认报表和外部读者，发布负责人记录授权、执行窗口与回退版本。这些是实施角色，具体人选在第一批登记。

## 1. 最终要交付什么

1. 消息原文、一次处理尝试、一次逻辑回复、一次外部动作、一次人工裁定各有明确身份。可从真实消息追到处理流水、动作及业务结果，也能解释重试、合并输入和后台任务。恢复只依赖有事务保证的账本。
2. 同一个不可变事实只写一份完整内容，其他读者按引用或明确的投影取值。保留诊断时的原始差异、历史版本和各自的保留期限。可重建的字段须有逐字段的等价证明及回退办法。
3. 消息详情、管理中心、转化看板、日报、测试平台和 BadCase 继续给出约定的结果。每个变更都有对应的写入者、读者、数据范围、缺失语义、验收人和可回退版本。
4. 优先消除处理流水中已测到的重复大字段。运行时五表合四、旧变更日志退役和物理改名分别裁定。两项减表均成立时为 25 张，只成立一项为 26 张，两项均不成立可保留 27 张。验收看写入量、读写正确性、权限与恢复能力。
5. 最终清掉已证明可以移除的旧写、旧读、双写、兼容别名和迁移脚本入口。仍有调用方或审计义务的部分登记为正式契约，写明责任人和原因。生产 `execute` 单独验收和决策。

可以用一次报名把这几层一起验清楚。设候选人的两条输入被合并，首次尝试已落流水，进程重启后再次处理同一组输入，最后确认一次报名。预期能查到两条原消息、两次处理尝试、一个逻辑回合、两条输入归属和一个被采信的报名动作结果。消息详情可分别诊断两次尝试，日报的报名数只加一。用隔离库与供应商替身跑这条链。

## 4. 消息、聊天与测试的实施细则

**流水与快照。** 写入经过 WeCom 遥测和仓储，主行与快照子行当前分两次 upsert。详情通过 PostgREST 嵌套关系读取子行，历史数据还会回读主表旧列。主流水默认保留 90 天，模型快照默认 7 天。P1 先固定传给每个消费者的旧接口契约。小时工具统计目前直接取主表 `tool_calls`，应留作独立对照。[写入入口](../../src/channels/wecom/message/telemetry/wecom-message-observability.service.ts) · [仓储与详情投影](../../src/biz/message/repositories/message-processing.repository.ts) · [保留任务](../../src/biz/monitoring/services/cleanup/data-cleanup.service.ts) · [工具统计 SQL](../../supabase/migrations/20260724053054_fix_hourly_tool_stats_key.sql)

- P2 的候选格式须识别版本、原字段是否存在、所属尝试/版本和有序内容摘要。已有快照且能逐字段还原时才生成同一 API 响应。保留缺字段、`null`、`[]`、参数、结果、错误和调用顺序的差别。快照已过期或从未落库时，详情仍可显示主流水工具，原始响应维持相应的缺失语义。
- 先用真实 PG/PostgREST 注入主写成功子写失败、旧子遇新主、同一尝试重复 upsert 和纠正数据。若两个提交不能保证读到同一版本及完整原值，先引入受限的同事务写入或不可变版本引用。证明之前继续写完整快照。读到悬空/失配引用须显式报诊断并停止新格式放量，能取到原始副本时回读该副本。
- P3 以真实 `toolCallId` 或“尝试 + 步骤序号 + 调用序号”映射。有重名工具、重复参数、失败后重试、重新规划及跨多步调用的用例。不同尝试的同名工具可以并存。保留部分序列、模型自己的消息和输入快照，禁止从今天的聊天/策略/记忆推造历史。
- P4 的聊天样本中，96/96 个可比 `payload.text` 与 `content` 相同，57/57 条可比单输入正文和请求相同，另有 25 条合并输入。分别保留 `text`/`pureText` 的存在性及实际值。引用、富媒体、裁剪改写、多消息合并、回调请求号或其他字段不能精确还原时，保留原载荷。对长期保留的聊天历史，默认只改新写。
- P4 的测试输出先比原始响应、展示文本、断言结果和失败文本。已核对的工具数组 31 对仅 1 对相同，来源 53 对仅 48 对相同，两类完整保留差异。测试执行详情、会话历史和多轮对比都能还原后才停写相等文本。对 `execution_trace` 和 `memory_trace` 的 GIN 索引分别测查询计划与成本。一次累计扫描为零且起算时间未知，不足以删索引。覆盖外部查询、代表性容量及可重建步骤后另提索引变更。[测试执行仓储](../../src/biz/test-suite/repositories/test-execution.repository.ts) · [执行详情](../../web/src/view/test-suite/list/components/ExecutionDetailViewer/index.tsx) · [会话历史](../../web/src/view/test-suite/list/components/ConversationDetailModal/HistoryMessage.tsx) · [多轮对比](../../web/src/view/test-suite/list/components/TurnCompareView/index.tsx)

**每个涉及存储变更的发布按以下顺序进行。**

1. **测基准。** 按相同类别和流量记录新增字节（含引用/版本开销）、工具/快照覆盖、API P95、代表性 SQL 计划、错误率与恢复待办。在同配置隔离库写入同一批样本，对比新旧载荷与表、TOAST、索引的增量。标明样本数、压缩和测量误差。去重若没有净收益，保留原写法。预先写下现有 SLO 和回退阈值，缺少数值时在 P0 实测并与负责人确定。等价字段及报表计数须零未解释差异，越权、未结义务丢失、重复外部派发任一例即失败。
2. **先扩展读、再改写。** 测试库先跑迁移和完整应用，验证旧写→新读、新写→兼容读、滚动部署期间新旧写并存、旧前端→新 API、已缓存页面→刷新。跨版本会破坏旧读时先部署全部兼容读实例，并固定最低可回退版本，再允许写新格式。为需要独立停写的批次提供可验证的回退开关或已演练版本。不依赖尚不存在的租户级灰度。
3. **连接真实组件。** 按改动运行定向 Jest（`--runInBand --watchman=false`）、`pnpm run ci:check`、实际 PostgreSQL/PostgREST 的迁移/RPC/角色/并发测试，涉及队列时另跑 Redis。浏览器真实打开对应页面，比对响应和展示，并回放业务正反例。保留执行结果、跳过项及原因。测试库与发布候选使用同一套迁移。
4. **控制生产负载。** 生产读取先看计划，使用只读事务、`statement_timeout=5s`、`lock_timeout=1s`，从现有索引按作用域/时间/主键采样，标明行数上限。代表性规模的 `EXPLAIN (ANALYZE, BUFFERS)` 在隔离库执行。生产迁移和数据回填分别列出脚本、范围、停止与回退动作，取得对应授权，按兼容顺序与应用版本配套发布。优先让 7 天快照自然过期。确需回填时按索引键游标分批，起始每批至多 100 行，根据锁、复制延迟和 P95 调整。保存范围、水位、版本、成功/跳过/冲突数，用条件更新保护并发新写，尾部补差可重跑。校对总量按有界分片累计，过期与新增分开统计。
5. **验收及停止条件。** 在授权发布后的自然业务样本中只读核对新写、旧行读取和恢复任务。看真实覆盖和每条新增写入的字节差，脱敏抽查工具、完整上下文和最终回复。跨租户泄露、重复外部动作、未结义务消失、不可解释的响应/计数差异、超过既定 SLO，任一出现立即停止相关新写/回填。零流量或仅模拟通过要标明证据边界。
6. **收缩与回滚分开。** 先冻结新格式或回填，保留兼容读和检查点。需退到更早版本时，先把新格式数据还原为旧版可读的行，并核对新旧期间产生的全部记录。删列/表/索引另开 PR 和窗口，确认最后旧实例、离线读者和清理作业均已迁走，备份能在隔离库恢复，索引可重建且锁预算允许。误删时优先从隔离还原点按键补回，保留切换后的合法新写。

## 7. 独立的 execute 决策与结案

表结构改造可以在 observe 下交付。若准备切 execute，选出明确的发布候选，重新验证该版本消费的 schema 和 RPC。同一窗口只改变一种高风险行为。历史工程结论和当前线上状态分别记录。[修正后的验收标准](../technical/runtime-acceptance-2026-11-04.md) · [模式和时间边界实现](../../src/biz/action-execution/action-executor.service.ts)

- **代码与故障演练通过。** 派发前重新检查托管权限和最新业务状态。按渠道契约判断成功，普通企微回复按已验证的成功回执推进分段/ACK，需要回调的路径精确匹配原请求。未知结果不盲重派，有可靠查询或人工核实与告警。外部成功后的补账和版本保护可恢复。用第 6 节演练证明重启、重复输入、群任务、复聊和回滚后的旧 execute 义务都能收尾。
- **发布与边界就绪。** 核实生产实际 tag、已应用迁移、全部实例模式与恢复 worker，盘点边界前主聊 pending 输入、未结 execute 义务及本地补账。逐类在原模式完成、隔离或交人工。历史 observe 记录不自动转为执行义务，群任务和复聊不受主聊 cutover 约束。保留原始输入时间和身份，记录明确的 UTC `ACTION_EXECUTION_CUTOVER_AT` 和回退版本。当前开关是进程级，发布方案必须覆盖所有实例。
- **单独决策。** 给用户提交可切/不可切及依据、剩余异常和可值守窗口，获得明确授权后才设置 `ACTION_EXECUTION_MODE=execute`。实际切换后对照正常业务完成、重复防护、未知处置、补账和告警。异常时退回 observe，保留边界、账本、能识别既有 execute 义务的版本和恢复 worker。托管暂停时如实标注真实流量缺口。等待时长、历史 unknown 清零、或人为制造真实候选人故障均不作为通过门槛。
