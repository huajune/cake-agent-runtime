## 1. 背景与目标

### 1.1 问题

1. **报名后的跟进漏得多。** 当日面试提醒实际发出率只有 37%–42%，近三周被「真人介入闸」拦下 39%–51%；被拦的里 27% 面试前 24 小时内我方没有任何人提醒过候选人。等通知岗（报名时没有面试时间）零提醒，候选人等 3–9 天后来追问。报名成功同轮转人工的候选人，提醒根本没排。
2. **带外工单看不见。** 招募经理在后台手工报的名，蛋糕只有四个条件同时满足才看得见；看不见时按「没有任何预约」处理：答不上面试时间、重复收资、重复报名被拒后转人工（28 天 21 次）、零提醒零回访。
3. **人工介入卡片太多、太粗。** 群里日均约 55 张卡片（工作日 68），人工介入占六成；`other` 占 25%（233 条），其中 100 条是同一句系统模板；只有 35% 带工单号。运营没有任务清单，处理情况测不出。
4. **岗位数据有而蛋糕读不出。** 合作模式识别从未生效（发薪方、签约方答不上），结算摘要读了不存在的字段，入职流程说明漏给模型，提示词把有数据的主题当成转人工示例。
5. **报名成功后大多没拉群。** 同轮拉群率从 66% 掉到 20%–30%，两个月后才由运营发现；根因是拉群一直靠模型自己想起来调工具。

### 1.2 目标

| 目标 | 指标 | 现状 | 目标值 |
|---|---|---|---|
| 报名后提醒不漏 | 当日提醒发出率（按记录数） | 37%–42% | 真人闸删除后 ≥70%；未发出的每条有可解释原因 |
| 等通知岗有跟进 | 等通知工单零记录 | 08-31 起 47/50 无记录 | 100% 落 `missing_interview_time`，满 3 天建运营任务 |
| 人工介入可执行 | `other` 占比 | 25% | ≤1% |
| 人工介入可跟踪 | 运营有任务清单、到期时间 | 无 | 每次介入对应一条飞书任务 |
| 人工介入减量 | 28 天介入次数 | 927 | 减 110–140（12%–15%；口径库第 1 期在下一迭代，其对应的 40–50 条不计入本次） |
| 报名后拉群 | 首次报名后同轮拉群率 | 20%–30% | ≥90%（程序保证） |
| 岗位数据可答 | 薪资行政类介入里缺失字段含发薪/签约/合作模式的条数 | 39/28 天 | 减 25–35 |

### 1.3 不在范围内

- 面试群邀请（`interview_group_invite_required`）维持人工介入，不做成蛋糕动作。
- 任务完成自动恢复托管暂不做。
- 上岗着装说明、上岗所需材料、试工细节、流程说明属面试后流程，蛋糕一律不读（0916 裁定）。
- 策略配置后台维持纯展示、由研发维护，不做运营编辑器、审批、差异预览。
- 政策口径库（R7 第 1 期）排下一迭代，本次不做。
- 「面试预约成功」卡片（日均 14 张）是否合并为日汇总，另议。
- 下班时间转人工后是否让蛋糕说「同事明天上班后回复你」，另议。

## 2. 需求

### R1 报名后提醒与回访的发送判据（复聊）

**现状**：报名后场景有两道与候选人、工单无关的闸：①「候选人说话之后真人手打过、蛋糕没再接话」就停（`follow-up.processor.ts` 1.3 段）；②报名成功那一轮的最终处置不是正常回复（转人工、被守卫拦下）就不排提醒（`anchor.service.ts` 的 `deliverable` 判断）。两个 09-21 个案分别卡在这两道闸：真人前一天说「通知明天下午 14 点面试」被当成接管，当天提醒和回访都停；报名成功同轮转人工，两条提醒从未创建，候选人到面试过点才第一次听到面试时间。

**需求**：报名后的当日面试提醒、提前 2 天确认档、面试后回访，**只看工单和聊天记录**决定发不发。不看托管暂停状态，不看当轮回合结局，不看真人有没有说过话。

| 看什么 | 规则 |
|---|---|
| 工单（到点实时查海绵） | 在途、有面试时间、面试未过才发；时间变了按新时间重排 |
| 聊天 | 候选人有一条消息没人回 → 不发（现有待答闸，保留） |
| 聊天 | 候选人自己说不去、取消、已有结果 → 不发 |
| 聊天 | 当日提醒：真人**面试当天**已发过提醒 → 不发；前一天提醒过的照发。改时间、问 AI 面试做完没、发二维码、发地址都不算提醒 |
| 聊天 | 回访：真人在面试时间之后已问过结果 → 不发 |
| 聊天 | 真人或候选人明确约了与工单不同的时间 → 不发，给运营建「请改工单时间」任务（T2）。不能按聊天时间发：生成后有一道纠正会把钟点改成工单钟点 |
| 其他 | 真人几分钟前刚手打过话，不顺延。提前 2 天确认档同规则，但不做「当天已提醒」一条 |

**改动**：
1. 删除报名后「真人手打过就停」整道闸，不是收窄。
2. 删除锚点服务对报名/改约跟进的 `deliverable` 判断：报名或改约工具返回成功就排，不管本轮怎么收场。取消工单本来就不依赖它。（09-22 已在工作树改好，含单测，未提交。）
3. 新增停止条件「聊天里已明确约了与工单不同的时间」。
4. 改复聊提示词：「已提醒」只认面试当天的真人提醒，补「改时间」「通知面试」的例子；「招募经理已问过是否完成」只看面试时间之后的询问。登记 `docs/prompt-rule-ledger.md`。
5. 面试后回访：基准取到点时实时工单的面试时间，不取任务快照；AI 面试的面试时间是时间窗，取窗口起点。
6. 等通知岗：工单取到但面试时间为空时，落 `missing_interview_time` 后正常结束，不再抛错重试后静默消失；面试时间由空变有值时重排（见 R3）；满 3 天仍无面试时间建运营任务（T2）。
7. 观测：触发停发的那条真人/候选人消息写进触达记录；复聊页加周度漏斗与回复率；Dashboard「总触达」排除提前 2 天确认档的「不适用」记录（它让面试提醒总触达数看起来翻了一倍）；上线前先数「报名成功同轮转人工」的量。
8. 同步产品文档停止原因表（`docs/product/reengagement.md`）、架构文档停止条件表。

**验收**：
- 09-21 两个个案回放：第一个命中「聊天时间≠工单时间」，不发并产生运营任务；第二个提醒正常排上并在面试前 2 小时发出。
- 被停发的每条记录都有上表之一的原因，没有 `human_intervention_after_candidate`。
- 影响量：真人闸 09-17 收窄前每周拦 40–72 条，收窄后 3 天拦 16 条；上线两周后按周抽样核对语义判断，样本覆盖真人改时间、口头取消、婉拒、真人已提醒、对话进行中。

**同批**：同轮有已提交的报名/改约/取消结果时，转人工前必须先把结果（面试时间、地点或「等通知」）告诉候选人，不能因为调了转人工工具就整轮无回复（见 R5.1）。

### R2 带外工单对账：查到就用、不落库

**现状**：本地只有 `active_booking` 指针，写入只有蛋糕报名成功和改约归属核验通过两处；海绵没有回调。带外工单要「手机号已落进蛋糕 + 本轮有面试类关键词 + 工单在途 + 候选人从未被蛋糕报过名」四条件齐备才可见。报名查重只认 30 分钟内同岗位的指针。`postSignupWorkOrders` 把海绵非零返回码吞成空列表。托管账号 token 只能查到、也只能操作本账号下的工单（已确认）。

**需求**：

**读**（每轮 prepare，所有调用方只读）：有候选人本人手机号就用本会话托管账号的 token 查一次 `signup/list`，结果直接作为本轮预约快照，替代逐工单号查 N 次。
- 范围：状态在途（约面待确认、约面成功），且报名近 15 天或面试时间在未来。`currentStatus` 用 `queryParam` 在服务端过滤；时间条件**本地判**（服务端按报名时间过滤会漏掉老报名但面试在未来的工单）。只用本人手机号，代报同行人不参与。
- 护栏：超时 3 秒；5 分钟缓存，命中关键词穿透；取消、改约、报名成功后失效该手机号的缓存；查询失败回落现有指针路径；账号没配 token 就跳过并落观测，不能回退默认 token。
- 前置：海绵查询失败不再当成「没有工单」——非零返回码、结构异常向上抛。类型与 zod schema 补新契约字段：工单行 `signupSource`（`AI`/`SUPPLIER`）、`operationLogs`（时间、类型编码、类型名），顶层 `candidateName/gender/phone/age`；新增 `signup/self/list/v2` 方法（分页，响应为 `data.result + total`，行带 `phone/candidateName/signupSource`），运营日报用的老 `self/list` 不动。
- 不建指针表，不把带外工单写进 `active_booking`，不加字段。蛋糕侧只留两样非副本状态：提醒排没排过（复聊任务去重键）、带外事件发没发过（工单号幂等键）。`active_booking` 短期保留作查询失败兜底，观察后退役。

**下游一律读同一份快照**：

| 下游 | 做法 |
|---|---|
| 提示词「当前预约信息」 | 读快照 |
| 取消、改约归属 | 工单在快照里且通过本人校验即放行，视同自有工单，不保留原话核验 |
| 出站守卫「声称已报名但无工单」 | 按快照里有没有当前聊的岗位的在途工单判断 |
| 转人工卡片工单号、发门店定位 | 读快照 |
| 报名查重 | 快照里同岗位或同品牌在途即命中；30 分钟窗口只留给「另一账号刚建单」的并发场景 |
| 别的账号下的重复报名 | 报名查重时再查一次 `onlyCurrentAccount=false`：同岗位或同品牌在途即如实告诉候选人，用重复报名码转人工，不等海绵拒绝。仍被拒的（判重规则比查到的宽）同样处理。操作仍只能动本账号的工单 |

**副作用**（只在企微生产回合，渠道层异步，不阻塞回复；测试链路连的也是生产海绵，不能放进 prepare）：
- 判定带外：工单行 `signupSource === 'SUPPLIER'`。不再用「本库没有报名事件」推断。
- 本人校验：海绵返回的候选人姓名与会话或档案里的姓名一致才按本人工单处理（排提醒、放行取消改约）；不一致只渲染。代报标记靠模型传参不可靠。
- 会话终态置「已报名」，停掉报名前复聊；快照里已无在途工单时回退终态。到点的带外核验闸保留作兜底（它还管「已通过」「已上岗」的停发）。
- 排面试提醒和面试后回访，时间规则与自建工单相同（到场档按后台配置的提前量；报名到面试 ≥3 天再加提前 2 天确认档）。触发时点：首次发现，以及快照里的面试时间与已排锚点不一致（含由空变有值，同时补上自建的等通知单）。`operationLogs` 里的改时间、取消记录写进触达记录和「请改工单」任务，作为改动来源的依据。面试已过不排；无面试时间直接落 `missing_interview_time`。锚点用稳定键（`reconcile:wo{工单号}:iv{面试时间}`），「报名完成时间」取海绵报名时间。
- 落独立事件 `booking.linked_out_of_band`，不补发报名成功事件；后续取消改约事件带来源标记，转化分析按来源单列。

**补偿扫描**（候选人不再说话时）：每 6 小时一轮，按托管账号调 `signup/self/list/v2`（`signUpStartTime` = 15 天前，按 `currentStatus` 在途过滤，翻页），筛 `signupSource=SUPPLIER` 得到带外工单清单及手机号；再按手机号反查会话（仓库无现成索引：实施时建一份手机号→会话键的轻量映射，来源为会话状态与长期档案的写入口）。反查不到的落观测、不处理。整轮互斥、单轮条数上限、超时、指数退避，只在生产执行。

**恢复托管后**：手动恢复即时对账一次；到期恢复不做（不经过恢复函数），由下一回合和扫描兜底。暂停期间跳过的提醒重排用新锚点后缀 `:resumed`，且距面试不少于配置提前量。

**验收**：带外工单候选人问面试时间能答；取消改约放行；带外工单有提醒和回访记录；转化分析出现「带外」来源；海绵查询失败率、调用量、耗时有观测。

**前置信息**：海绵新契约 09-22 已上线（`signup/list` 加 `onlyCurrentAccount`、`signupSource`、`operationLogs`、顶层候选人信息；新增 `signup/self/list/v2`）。实施前实测：`operationLogs.operationType` 编码全集；`onlyCurrentAccount=false` 的返回范围；`self/list/v2` 的排序与单页上限。带外工单总量改为直接用 `self/list/v2` 按 `signupSource` 计数，不再从日报口径倒算。

### R3 报名成功后拉群改为程序保证

**现状**：拉群只有两处调用：拉群工具（模型调用）和复聊升档。报名成功后拉群从来不是程序流程，规则只写在拉群工具说明「触发场景 1」里，而 07-30 同一说明又加了「拉群是无岗维护场景，不是有岗推进场景」。近 4 周首次报名成功 434 轮，73% 没调拉群工具。场景①（找不到岗位）08-20 有意收窄，保留。

**需求**：
1. 报名成功后由运行时直接拉群，结果（群名、直接拉入还是发了邀请卡片、或为什么没拉）放进报名工具返回，模型只按结果说话。现有确定性闸门（城市出处、重复邀请）照用。
2. 删拉群工具说明「触发场景 1」，修正矛盾话。
3. 同 PR 登记三处：`docs/product/invite-to-group.md` 场景 1 改写为程序流程并注明场景 2、3 仍由模型判断；`docs/prompt-rule-ledger.md` 的 `invite_to_group` 行记「场景 1 职责迁到运行时、说明已回收」；`docs/principles/bitter-lessons.md` L6 追加实证（同轮拉群率 66%→约 25%，两个月后才由运营发现）。上线前不提前改产品文档。
4. 「首次报名后同轮拉群率」进周报，低于阈值告警。
5. 清理生产阶段目标里「没有合适岗位就拉群」的旧口径（生产写）。

**验收**：首次报名成功且候选人城市已知、未在群、城市有群时，同轮拉群率 ≥90%；未拉的每条有结果原因。

### R5 人工介入治理

#### R5.1 承诺话术

**现状**：蛋糕回复里出现「我让同事/负责人/店长……确认/跟进」而本轮没调转人工工具，运行时自动补一次介入，原因固定写模板「已向候选人承诺会有人来跟进」，岗位、工单、阶段全空（28 天 100 条）。教模型说这句话的正是系统：生产红线第 9 条「预约失败/系统异常时只用『我让同事确认一下』衔接」；取消、改约失败回执同时要求「说衔接语」和「调转人工工具」，而转人工工具一调用本轮就无回复，两条互斥。

**需求**：
1. 红线第 9 条改为：出错不暴露技术细节、如实说暂时处理不了；失败的工具自己带原因码、工单号、岗位转人工（生产写）。
2. 「回复一句衔接语 + 系统补介入」作为正式路径：补动作结构化（承诺原句、候选人原话、焦点岗位、工单号、阶段，按触发工具直接给原因码），不再一律记 `other`。判据排除完成时陈述（「我跟门店确认过了」），回复未投递不补。
3. 本轮有已提交的报名/改约/取消结果时，转人工前先把结果告诉候选人。
4. 排查「我先帮你提交报名，让同事确认下」9 条，确认有没有没提交却说提交了。

### R6 飞书任务

**需求**：群通知卡片照旧每次都发；另外每次人工介入在飞书任务清单建一条任务。**任务数据不落库**：任务就是飞书清单本身，蛋糕侧不建任务表、不往介入底账加字段，运营回填项留在飞书；只留一个 Redis 键（会话 + 大类 → 任务 ID，7 天过期）用于同大类再次触发时找回原任务追加评论，键丢了就新建。不读回完成状态，不自动恢复托管。

**清单**：「蛋糕·人工介入（2026Q4）」，按大类分组，季度轮换。

**表头**（13 个自定义字段）

| 组 | 列 | 类型 | 内容 |
|---|---|---|---|
| 定位 | 标题 | 系统 | `【急·现场急件】微信昵称 · 品牌-门店 · 一句话原因`；标题只放昵称 |
| 定位 | 候选人昵称 / 候选人姓名 / 手机号 | 文本 | 企微昵称；收资真名；完整 11 位；未收集留空 |
| 定位 | 托管账号 | 单选 | 显示运营认得的名字 |
| 定位 | 工单号 | 文本 | 无则留空并在描述注明 |
| 时间 | 优先级 | 单选：急/当日/常规 | 由大类派生 |
| 时间 | 任务创建时间 | 系统 | |

| 时间 | 最晚跟进时间 | 系统 due | 见算法 |

| 回填 | 本可由蛋糕完成 | 是/否 | |

**最晚跟进时间算法**（运营上班时间：工作日 9:30–18:30，无夜班，周末不上班）：
1. 起算点：上班时间内触发即触发时刻；下班时间触发取下一个工作日 9:30。
2. 时限只数上班的分钟，当天数不完顺到下一个工作日（T2 时限 2 小时，17:30 触发 → 次日 10:30）。
3. 各类时限见 R5.2 大类表。
4. 面试上限只对 T2、T6：「面试时间 − 1 小时」在上班时间内且晚于「起算点 + 30 分钟」时取较早者；面试早于下一个上班时段的，到期取起算点 9:30，标题加「下班期间触发，面试已临近/已过」，优先级提到急。
5. 最终值不早于起算点 + 15 分钟。
6. 工作日历：周末顺到周一 9:30；法定节假日与调休按国家发布的年度安排维护一份清单（先放托管配置或代码常量，口径库上线后迁入）。

依据：28 天 927 次介入里 77% 在上班时间，18:30–22:00 有 11%，夜里 4%，周末 8%；现场急件 51 次里 49 次在上班时间。

**合并**：合并键 = 会话 + 大类；T5 按岗位去重。同大类再次触发时追加评论并刷新截止时间、优先级取更急者、标题前缀。可合并量上限约 33%。

**个人信息**：披露范围与群卡片一致；清单成员只加运营本人和主管；描述里过滤身份证号、银行卡号、第三方手机号；T7 及含残障、健康、工伤内容的任务不贴对话原文；任务完成满 90 天清空姓名手机号；季度轮换时旧清单归档并移除非主管成员。

**失败**：建任务失败不阻塞群卡片和暂停动作，发飞书告警。

**上线前实测**：被指派人是否收到任务助手通知、评论是否通知负责人；客户端里创建者和来源显示；每清单自定义字段数上限；**现有 open_id 是否属于本应用**（open_id 按应用区分，现有 ID 只用于群卡片 @）；需新增权限（任务、清单、自定义字段、分组、评论读写）并重新发布应用版本。

**验收**：每次介入 1 分钟内有对应任务；到期时间全部落在上班时间内；同会话同大类 24 小时内不重复建任务。
