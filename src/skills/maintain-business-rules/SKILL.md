# 维护业务规则

Claude 与 Codex 共用本文件。先读仓库 `AGENTS.md` / `CLAUDE.md`，再从
[业务规则索引](../../../docs/business-rules/README.md) 找相关主题；跨主题变更沿落点链接追踪，避免只改一个文件就宣布规则已生效。

## 认清本次变更

- 仓库是业务口径的维护依据。主题文档是摘要和关联索引；给模型的手册正文在 `src/agent/generator/context/sections/procedural/rules/`，工具、守卫与复聊规则留在消费者附近。不要复制正文到 `docs` 后让运行时读文档，也不要引入数据库规则配置。
- `现行基线` 表示对现有实现的归档，不是重新裁定其合理性。区分已有裁定、明确的实现缺陷、尚待业务决定的问题。检查当前用户指令与可核验来源，不把旧注释或测试通过当成新授权。
- 用户要求保持行为时，冲突写入主题的「未决与冲突」，保留当前实现。新口径需要裁定时说明具体矛盾及影响，讨论期间继续不依赖裁定的工作。已获得的裁定不要反复询问。
- 只读查询给出源码、测试和适用条件即可，不为每次查询增加记录。

## 修改与关联

1. 阅读目标规则的来源、落点、验证和未决项；查实际代码及调用链。涉及 prompt 时遵循 [放置判定树](../../../docs/prompt-rule-ledger.md)，共通执行协议留在手册入口，业务片段按主题维护；不把同一教学复制到多个 prompt 位置。
2. 修改真正消费规则的实现，必要时同时调整「教」与「拦」。业务编号稳定、不可复用；新增编号用主题下一空号，删除规则保留废止记录与原因。一个规则可关联多个执行位置，通用机制使用 `businessRule: null` 并写 `mechanismReason`。
3. 同批更新主题条目的摘要、状态、来源、`落点`、`验证` 与变更记录。引用相对仓库路径和真实符号或规则 ID；不填虚构裁定人、日期或验证记录。修改 prompt 还要更新 `docs/prompt-rule-ledger.md` 对应居所/变更项。
4. 片段边界使用 `<!-- rule:IB-01 -->` / `<!-- end-rule:IB-01 -->`；入口以 `{{rule:IB-01}}` 确定顺序。注释不进入模型输入。源码头的 `// business-rules: IB-01, ...` 与主题文档反向关联；Guardrail 与 final-check 用各自定义中的 `businessRule`，不要另造 ID 清单。

## 验证与交付

```bash
pnpm run business-rules:validate
pnpm run business-rules:test -- IB SW
pnpm run ci:check
```

不带主题运行 `business-rules:test` 会执行全部主题关联的局部契约测试。它不替代真实 Agent 回归，也不自动写入飞书或生产。

`manual-loader.spec.ts` 的字节数和摘要是拆分前基线。纯结构变更应保持它通过；有意改变口径时，先补相应行为测试和裁定来源，再更新摘要，不能为了让 CI 变绿而盲目刷新。

涉及回复、预约、守卫等行为时，按仓库现有 [analyze-chat-badcases](../analyze-chat-badcases/SKILL.md) 工作流执行真实链路验证并逐条评审；标明实际评审工具/模型，不沿用历史代理身份。测试资产不可评估时记录原因，不算通过。外部写入和发布范围以用户任务授权为准。

交付说明应区分：静态关联校验、局部契约测试、真实 Agent 业务评审、已部署状态。CI 只能证明关联结构与已执行测试，不能裁定业务语义，也不能证明生产配置一致。PR 默认正式待审，合并和部署不由本 skill 自动授权。
