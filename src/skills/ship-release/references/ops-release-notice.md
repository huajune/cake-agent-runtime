# 运营版上线通知

用户要"通知运营今天上线了哪些功能、修复了哪些问题"时，按本文整理「X 月 X 日上线通知」。

**适用场景：**

1. 当天有多个版本上线，或这次部署带上了此前被驳回、没上线的版本；
2. tag 已经打出，本版 PR 仍缺「运营说明」，自动卡片只能给技术摘要。

只上线一个版本、PR 也写了运营说明的，继续用自动发版卡片。

**范例：** [ops-release-notice-example.json](./ops-release-notice-example.json)，是 2026-10-15 实际发出的定稿。当天上线两个版本，其中一个并入了此前被驳回的版本。只参考结构、条目粒度和文风；里面的版本、时间、人数、账号和岗位数都是当天的事实，不能照搬。

## 一、口径：写上线前后的净变化

1. **起点 = 当天第一次上线前，生产实际在跑的版本**，不是上一个 tag。部署被驳回或取消的版本从没上过线，它的内容要并入本次。找法：
   - 列出最近的部署：`gh run list --workflow "Build and Deploy" --limit 20 --json databaseId,createdAt,conclusion`。
   - 逐个用 `gh run view <id> --json jobs` 看 `deploy` job 的 conclusion，取当天第一次上线之前、最近一个 deploy job 为 success 的 run。不能按 run 的整体状态筛：notify 被拒的 run 整体显示 failure，但已经上线了。
   - 取这次部署的 tag：`gh run view <id> --log | grep -m1 -oE 'RELEASE_TAG: v[0-9.]+'`。这里匹配 GitHub Actions 自动打印的 step `env`，不是 shell 脚本的 echo（已核验成功部署 run `38693523473`，输出 `RELEASE_TAG: v11.13.1`）。若日志已过保留期或没有匹配，必须核对该 run 的实际 `release_tag` 输入或部署镜像证据；证据缺失时停止，不猜测版本边界。
   - 再用 `git rev-parse <tag>^{commit}` 得到起点提交。不要直接用 run 的 `headSha`：它是派发时 master 的最新提交，回滚重部署时和实际部署的代码不一样。
2. **终点 = 当天最后一个 deploy job 成功的 run 所部署的 tag**，取法同上。终点之后还没部署的改动不写进本通知。需要预告时单独写一句，只写当前状态（如"发布 PR 已开，还没部署，上线时间另行通知"），不写预期效果。
3. **只写起点到终点之间，运营或候选人能感知到的变化：**
   - 开发中引入、发版前已经修掉的问题，线上从没出现过，不写成"修复"。
   - 当天先改后撤回的，净效果为无变化，不写。中间窗口里是否真的影响了候选人，用生产数据确认（例如查跳过记录的条数），有影响再决定是否加一句说明。
   - 起点里已有的能力不写成新功能，只写新增部分。
   - 配置或数据已经提前生效的（比如直接写进生产库的账号配置），注明"X 月 X 日已生效"。
   - 不写纯工程改动：评审流程、文档、发版元数据、回同步。只改观察记录或告警统计的也不写，例如只记录、不拦截的规则少了误报；这类改动既不改变候选人收到的回复，也不改变运营看到的界面和提醒。
4. **PR 的「运营说明」只当找漏项的线索，不能照搬。** 它是相对该 PR 合入前的代码写的，参照的可能是开发中版本，也可能本身就说过头。每条都按起点重新核实、重新写；不按 PR 分组，不带 ✅/⏳ 状态。

## 二、结构与文风

- **标题**：「X 月 X 日上线通知」，卡片标题由脚本加产品前缀。
- **开头一句**：写今天上线了哪些版本，各自几点部署完成。时间取 deploy job 的 `completedAt`，换算成北京时间；不取 notify 的时间。有并入的版本，写"含此前没有单独上线的 vX 的全部内容"。
  - 当天更早已经发过自动卡片的，补一句"本通知汇总今天全部上线内容，HH:MM 的 vX 发版卡片以本通知为准"。
  - 那张卡片内容有误时（漏了并入的版本、把已上线写成待发布等），这份通知就是 SKILL.md 第 9 步要求的更正，开头点明更正的是哪张卡片。
- **三个分区**：🆕 新上线功能 / 🔧 问题修复 / ⚠️ 需要运营留意。
  - 编号短条，每条一两句，同类合并，总数控制在 25 条以内。
  - 🆕 和 ⚠️ 的条目写成"**加粗短标题**：说明"；🔧 的条目直接写现在的行为，不加粗。
  - 不出现 PR 号、文件名、字段名、工具名和内部术语（guardrail、replan、JSON 模式等）。
  - 限定条件不能省，省了就说过头了。例如"按小时计薪的兼职岗""AI 已经查到要改哪一张时""今天 14:44 以后新收到的消息开始生效"。
  - **对比词按起点写**："不再""以前""只""也会""改为""更多"这类词，比较对象必须是起点线上的真实行为，不能是开发中版本，也不能是当天只跑了几个小时的中间版本。起点没有这项能力的，直接按最终规则写成新功能，不用对比词。放宽还是收紧，也按起点判断。
  - **例子要两头成立**：新功能的例子要在终点代码里真实成立。修复条目里写的旧问题和例子，要能证明在起点确实会出错，证据来自起点代码、PR 里的新旧对照或生产记录；"可能会出错"的情况不写。
- **"需要运营留意"只放四类：**
  1. 运营要采取行动的：写明截止时间和看板入口，入口名称要和界面原文一致；
  2. 会多看到或新看到的提醒；
  3. 需要推动外部方修正的；
  4. 线上现在仍存在、要等后续版本才修的问题：写线上实际表现和运营怎么应对，不能只写下个版本会怎么改。

  涉及数字的，带上统计时间。

## 三、核实

每条说法都要两头核：

- **终点成立**：在终点代码里找到对应实现，并顺着调用链确认真的会走到（例如候选人原话先被解析成什么条件，再进入匹配）。记成 `<提交>:<文件>:<行>`。
- **起点没有**：按行为搜，不按终点的文件路径搜，因为代码可能在本批改动里搬过家。
  - 用 `git grep -n '<函数名/关键词/提示词原句>' <起点>` 找。
  - 代码里找不到，再查起点的提示词、数据库策略配置和生产记录，看这种行为是否已经出现过。
  - 起点已有的，只写新增部分。
- **修复条目还要证明问题在起点线上真的出现过**：查出引入问题的提交。符合下面任一条的，就是开发中问题，不写：
  - `git merge-base --is-ancestor <引入提交> <起点>` 结果为否；
  - 修复 PR 正文写着"发版前回归发现"。

还要现查的事实：

- **数量**：人数、条数现查生产库，只读，带时间范围和 LIMIT，写明统计时间。PR 正文和迁移里的数字是当时的，不能当成现在的数字。例如：PR 正文里写的是 99 位，上线当晚现查，0 点会被恢复的只剩 78 位。
- **生效条件**：
  - 行为受开关控制的（环境变量，或 `system_config`、`hosting_config` 等数据库配置），查生产的实际取值和打开时间；查不到就不写。
  - 配置先于代码写进生产库的，按配置生效的日期写。
  - 只对上线后新写入的数据生效的（新标记、新字段、新消息），写明从几点起生效，以及上线前已有的数据会怎样。
  - 依赖迁移的，确认生产迁移已经执行（`pnpm run db:status:prod`，或只读查数据）。
- **时间和版本**：取 `gh run view <id> --json jobs` 的实际记录。
- **界面和卡片原文**：运营会照着找的词（看板入口名、卡片字段），grep `web/` 或渲染器确认原文。

流程，按这个顺序：

1. **起草**：每条附证据位置。
2. **分视角怀疑式核查**：
   - 新功能：是否成立、是否说过头、是否早已存在；
   - 问题修复：问题是否在起点线上真实存在过；
   - 运营留意：查生产数据、开关取值和界面原文；
   - 漏项与越界：对照 `git log <起点>..<终点>` 和各 PR 的「运营说明」，找漏掉的重要变化，以及写了但没上线、已撤回或纯工程的内容。
3. **定稿**：逐条记录采纳和驳回的理由。
4. **抽查**：主执行人亲自再核数字、界面名称和生效条件。

在 Claude Code 里，第 2 步用 Workflow 并行跑这四个视角；其他环境按同样四个视角依次做。

交给用户审阅时，附一份"和上一版相比改了什么"的短清单：数字修正、删除项、收窄项。用户能直接看出哪些地方被核实改动过。

## 四、发送

1. **先给用户看定稿。** 用户确认内容和发送渠道后才发；只说"整理一下"不等于授权发送。
2. **发版群就是自动发版卡片发的群**，即蛋糕私聊监控群，webhook 为 `PRIVATE_CHAT_MONITOR_WEBHOOK_URL`。
3. **自动发版卡片要不要发，在每次部署的 `notify` 审批时就定下来。**
   - 用户确认改用人工通知后，请用户把 `notify` 审批 reject 并写明原因；也可以经用户在对话里明确同意后代为操作。这样群里不会出现两份通知。用户确认之前，不要动这个审批。
   - deploy job 已成功的 run 会因此整体显示 failure，在汇报里说明即可，不要重跑这个 run：重跑会再次触发 notify 审批。
   - 自动卡片已经发出的，无法撤回，按「二」里开头一句的写法说明以本通知为准。
4. **把定稿写成 JSON**，结构见脚本头注释和范例。每条写成一段，不分子条目：多层列表在手机上难读。条目不要自带编号或项目符号，脚本会自动编号。
5. **先预演**：在主仓库目录运行 `node scripts/ops-release-notice/send-notice-card.js <notice.json> --dry-run`。
   - 把打印出的标题和各段正文逐段读一遍，这就是要发出去的原文。
   - 再看各分区字数和请求体大小（飞书自定义机器人上限 20 KB）。
6. **再去掉 `--dry-run`，只发一次。**
   - 返回 `code: 0` 才算成功，卡片会 @所有人，和自动发版卡片一致。
   - 发送成功后，脚本会在 JSON 旁边写 `.sent` 标记，挡住重复发送。
   - 报超时或网络错误时不要直接重跑：飞书可能已经收到。先请用户看群里有没有这张卡片，确认没收到再发。
   - worktree 里没有 `.env.production` 时，脚本会去主仓库读取。不要把 `.env.production` 复制进 worktree。
7. **事后确认**：读不到群消息时，告诉用户"内容待群内确认"，并保留发送用的 JSON。
