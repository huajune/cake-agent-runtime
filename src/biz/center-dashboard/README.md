# 自招中心运营后台范围

员工使用已开通的手机号和密码登录。总部、河南自招、上海自招分别是独立租户，每家外部供应商各自一个租户。上海智能体组归总部，自己承接的业务记在总部。总部员工可以跨租户查看业务，河南、上海自招及供应商员工可以查看本租户所有小组。仅专用管理员 `cakeadmin` 管理账号、权限和平台 AI 回复总开关。

**发版状态（2026-11-20）**　当前分支已将员工组织和聊天归属接到 `tenants`。中心聊天查询使用记录上的租户，小组开关按登记组织核对。用户清单、处理流水和复聊等仍按当前已确认的 Bot 筛选。总部沿用原业务接口，跨租户只读和外部调用仍待验收。正式开户安排在租户版验收后。目标数据流、迁移步骤与验收条件见[租户与账号设计](../../../docs/product/organization-members-and-business-accounts.md)。

## 日常绑定与交接

1. 同事在 Stride 扫码，Stride 管理员将企微号放入小组。在蛋糕「系统 → 账号管理」点击「同步 Stride」即可立即读取最新目录。正式运行时每 5 分钟自动同步一次。
2. `cakeadmin` 在开户弹窗选择所属组织和「负责小组」，也可以稍后从成员行点「绑定托管小组」。选组后显示组内账号，支持绑定空组。接手同组织其他负责人的小组时，核对原负责人并勾选确认。手机号待补的成员也可以先绑定。开户时选组与创建登录账号在同一事务中完成。
3. 蛋糕按首次核实时间登记已绑定小组里的新号。确认实际换组或离开目录时，管理员在「待确认的托管号交接」核对原组与现组，填写实际交接时间。目标组尚未登记时，先为该组绑定负责人。中间经过多个组且缺少可靠时间的消息保留待核对。
4. 中心的聊天查询在交接待确认期间隐藏可能归错的消息。确认后按消息发生时间分批核对，每批最多 300 条。交接前和交接后的聊天各归当时有记录的组织。后台按登记的归属核验可操作的小组，以及 Stride 现组与登记一致的 Bot。首次批量导入使用的 Stride 备注仅用于核对旧名册。

## 当前分支的中心查询范围

| 菜单         | 河南范围                                 |
| ------------ | ---------------------------------------- |
| 托管用户     | 本中心机器人对应的用户与统计，只读       |
| 托管开关     | 仅本中心小组开关；不显示、不能操作总开关 |
| 聊天记录     | 本中心机器人会话和消息                   |
| 消息处理流水 | 本中心流水与运营详情                     |
| 二次触发追踪 | 本中心记录、跟进文案与状态流转           |

「托管开关」按蛋糕登记的组织展示小组。尚未绑定的小组列在总部的「归属待确认」。中心员工可以操作本中心各小组的开关。

前端根据服务端给出的权限展示菜单和控件。河南及上海自招的聊天列表、详情、总数和趋势共用 `tenant_dashboard_chat_read`，取服务端员工的组织 ID，省略归属待核对的消息。其他运营查询仍使用原来的机器人范围。流水详情裁剪原始请求头、提示词和内部 JSON。总部当前沿用原接口，需补齐来源标注和按目标组织校验写入。

用户列表来自范围内聊天记录，token 数来自范围内流水；长期业务趋势读取按机器人落库的日报与运营事件，避免旧会话日统计跨机器人累加。查询窗口最多一年、单页有上限、数据库超时 4 秒、客户端超时 5 秒；失败不回退到全表扫描。用户清单使用会话与机器人复合游标，浏览器逐页取齐后沿用原搜索和排序，超出整轮预算时明确失败，不展示截断总数。用户趋势只统计候选人发送量，业务趋势统计双方消息量。

## 后台账号

员工用个人手机号和密码登录。专用管理员用 `cakeadmin` 和单独交付的密码登录。Supabase Auth 验证两种身份。当前分支在员工业务请求中按 Auth 用户 ID 核对服务端账号表 `dashboard_accounts`、启用状态和组织。只有 `cakeadmin` 可以操作全局 AI 回复开关，并在「系统 → 账号管理」开通账号、重置密码、调整组织及停用账号。河南全体员工共用上表的范围，小组开关写入前刷新目录并核验，成功后记录操作人和小组。

成员档案、海绵业务账号与托管号的目标关系及迁移顺序见[统一账号体系设计](../../../docs/product/organization-members-and-business-accounts.md)。

### 环境初始化

1. 在测试环境依序验证三项账号迁移、`20261120150000_tenants_and_chat_ownership.sql` 和 `20261120151000_tenant_chat_reads.sql`，确认索引构建窗口、查询计划及历史归属覆盖，再在发布窗口应用到正式环境。保留前序中心读取 RPC 和后台专用数据库权限。在 Supabase Auth 启用 Email 和 Phone 密码认证，关闭自助注册。管理员使用预确认的内部邮箱标识。后台只接纳已开通名单中的 Auth 身份。
2. 前端构建读取 `NEXT_PUBLIC_SUPABASE_URL` 和公开的 `NEXT_PUBLIC_SUPABASE_ANON_KEY`。NestJS 使用同一项目的 URL 和服务端 `SUPABASE_SERVICE_ROLE_KEY`。浏览器仅向 Supabase 发起认证，业务数据经 NestJS 读取。
3. 发布任务自动初始化专用管理员。在测试环境单独办理时，在受信任终端创建权限为 0700 的私有目录，再执行 `node --env-file=.env.local -r ts-node/register scripts/dashboard-accounts.ts bootstrap <私有目录>`。初始密码随机生成并写入该目录的 `cakeadmin.private.json`。已有账号重试时保留原密码。管理员已登录时，可在「账号管理」中重置自己的密码。遗失全部凭据时，由持有该项目服务权限的运维按 `cakeadmin.ready.json` 里的 Auth 用户 ID 重设密码。
4. 全体托管同事使用下文的正式发布流程。单独登记待开通名单可用 `scripts/dashboard-accounts.ts import-henan <私有成员名单.json>`。同一人归并为一条登录记录，负责小组按 Stride 小组 ID 保存。组内可以暂时没有 Bot，也可以有多个。
5. 生产切换由同一次发布协调迁移、启用两种密码认证、初始化专用管理员及前后端。生产命令显式选用生产配置。自动化需要访问已标注的接口时，给服务端和调用方设置全新的 `CAKE_MACHINE_API_TOKEN`。旧浏览器构建使用过的共享凭据须退役。企微回调、静态页面和既有健康探针沿用各自入口。
6. 登录验收覆盖无会话访问、同一网络中的不同员工账号、普通总部员工与 `cakeadmin` 的权限差异，以及停用后旧会话的下一次业务请求。租户验收另需覆盖两个河南账号共享全中心、上海自招与供应商各自隔离、总部全租户查看及跨租户只读、Bot 调组保留历史、异步重试使用原业务租户和未启用的外部服务零调用。

### 随正式发布初始化全员账号

在本机用 `node --env-file=.env.production -r ts-node/register src/cli/dashboard-onboarding.ts prepare <私有目录> <原始名单>` 生成 `roster.json`。准备阶段只保留姓名、组织、负责小组、已知手机号和用于对齐现有托管配置的飞书成员 ID，并记录目标 Supabase 项目。发布前名单留在本机。

进入正式发版窗口后，发布人通过部署 SSH 在服务器建立仅部署用户可访问的 `/data/cake/private/dashboard-onboarding/staff`（0700），将这份 `roster.json` 以 0600 权限交到该目录。正式发布脚本在切换新服务前核对账号表、两种认证方式、整批成员和 Stride 当前小组归属，新服务健康检查通过后先创建独立的 `cakeadmin`，再建立全部成员档案，再按已核实的手机号开通登录。缺手机号的同事显示「待补手机号」，管理员收到号码后从该行点「开通」即可。上海智能体负责人归总部，上海自招员工只看上海自招团队，河南员工看整个河南中心。首次发布缺少名单会在切换前提示补齐。姓名或归属冲突需先核对，重复执行沿用已保存的密码和停用状态。

开户成功后，专用管理员的初始密码从 `cakeadmin.private.json` 私下交付给管理员保管人。员工密码从同一私有目录领取 `handoff.private.json`，按人交付手机号和独立随机密码。此文件仅列本批新开的账号。管理员回执为 `cakeadmin.ready.json`。员工完成回执 `complete.json` 只保留数量和批次摘要，交付完可移走密码文件并保留回执。中断后在同一目录重试，保留 `credentials.work.json` 直到批次完成。
