# 自招中心运营后台范围

员工使用已开通的手机号和密码登录。总部、河南自招、上海自招分别是独立组织，每家外部供应商各自一个组织。上海智能体组归总部，自己承接的业务记在总部。总部员工可以跨组织查看业务，河南、上海自招及供应商员工可以查看本组织所有小组。仅专用管理员 `cakeadmin` 管理账号、权限和平台 AI 回复总开关。

**验收进度（2026-11-27）**　测试库已登记 17 个小组和 12 个在用 Bot。已验证手机号与密码免短信登录、河南和上海自招的组织范围、总部跨组织查看，以及自助改密、管理员重置、停用、恢复和注销。正式员工随发版开户。[组织与账号设计](../../../docs/product/organization-members-and-business-accounts.md)

## 日常托管绑定

1. 同事在 Stride 扫码，Stride 管理员将企微号放入小组。在蛋糕「系统 → 账号管理」点击「同步 Stride」即可立即读取最新目录。正式运行时每 5 分钟自动同步一次。
2. 系统管理员从左侧菜单最底部进入「账号管理」。为组织管理员开户时只选所属组织。为组长开户时可选「负责小组」，也可以稍后从该账号所在行点「绑定托管小组」。选组后显示组内账号，支持绑定空组。接手同组织其他负责人的小组时，核对原负责人并勾选确认。开户时选组与创建登录账号在同一事务中完成。
3. 每个企微号固定属于小组的组织。组内加号、同组织调整小组后同步 Stride 即可。若目录把已登记的企微号列入其他组织，先核对 Stride 中的分组，再重新同步。

## 后台账号

员工以手机号和密码登录。Supabase Auth 用户关联 `tenant_members` 的有效成员，成员所属组织通过外键引用 `tenants`。总部「账号管理 → 登记组织」可以新增组织，后台为其生成 ID。账号名单以组织为分组，展开后可查看成员及角色。开户、托管绑定和显示名称读取同一份登记数据。

| 页面 | 普通组织账号的范围 |
| --- | --- |
| 托管用户、聊天和趋势 | 查看本组织的业务记录。组织管理员和组长都可在「托管用户」里暂停或恢复本组织候选人的会话。 |
| 消息处理流水、二次触发 | 列表、详情、趋势与报表按业务发生时的组织查询。 |
| 托管开关 | 查看本组织的小组，可操作已登记给本组织的小组开关。 |

总部个人账号可跨组织查看，并操作本组织小组。仅 `cakeadmin` 可以管理账号与平台 AI 总开关。新供应商可先登记、开户，之后按需接通渠道和外部服务。详情见[组织、成员与业务账号设计](../../../docs/product/organization-members-and-business-accounts.md)。

### 环境初始化

1. 核对目标环境、在用 Bot、已登记时段及查询计划，按[部署指南](../../../docs/workflows/deploy-guide.md)核对本版 23 份迁移，最后一份为 `20261127103000_current_dashboard_account.sql`。在 Supabase Auth 启用 Email 和 Phone 密码认证，关闭自助注册。管理员使用预确认的内部邮箱标识。后台只接纳已开通名单中的 Auth 身份。
2. 前端构建读取 `NEXT_PUBLIC_SUPABASE_URL` 和公开的 `NEXT_PUBLIC_SUPABASE_ANON_KEY`。NestJS 使用同一项目的 URL 和服务端 `SUPABASE_SERVICE_ROLE_KEY`。浏览器仅向 Supabase 发起认证，业务数据经 NestJS 读取。
3. 正式发布任务使用本批核准的管理员密码文件初始化专用管理员。在测试环境单独办理时，在受信任终端创建权限为 0700 的私有目录，再执行 `node --env-file=.env.local -r ts-node/register scripts/dashboard-accounts.ts bootstrap <私有目录>`。缺少预设密码文件时，单独执行的命令会为新账号生成随机密码。本批新开的密码写入 `cakeadmin.private.json`，已有账号重试时沿用原密码。已知当前密码时，管理员可在登录页点「修改密码」。遗失全部凭据时，由持有该项目服务权限的运维按 `cakeadmin.ready.json` 里的 Auth 用户 ID 重设密码。
4. 全体托管同事使用下文的正式发布流程。单独登记待开通名单可用 `scripts/dashboard-accounts.ts import-henan <私有成员名单.json>`。同一人归并为一条登录记录，负责小组按 Stride 小组 ID 保存。组内可以暂时没有 Bot，也可以有多个。
5. 生产切换由同一次发布协调迁移、启用两种密码认证、初始化专用管理员及前后端。生产命令显式选用生产配置。自动化需要访问已标注的接口时，给服务端和调用方设置全新的 `CAKE_MACHINE_API_TOKEN`。旧浏览器构建使用过的共享凭据须退役。企微回调、静态页面和既有健康探针沿用各自入口。
6. 登录验收覆盖无会话访问、同一网络中的不同员工账号、普通总部员工与 `cakeadmin` 的权限差异，以及停用后旧会话的下一次业务请求。组织验收另需覆盖两个河南账号共享全中心、上海自招与供应商各自隔离、总部全组织查看及跨组织只读、组织内新增托管号和调整小组、异步重试使用原业务组织和未启用的外部服务零调用。

中心可查看本组织的流水运营摘要。回合完整请求、HTTP 调用清单及单次原文仅总部可读。中心调用这三类接口时返回 403。[查询接口](../../../docs/architecture/monitoring-system-architecture.md#api-端点列表)

发布时将成员表迁移与读取新表名的服务版本配套切换。测试库的完整字段和逐表组织归属见[组织数据表与字段](../../../docs/db/tenant-schema.md)。

### 随正式发布初始化全员账号

在本机用 `node --env-file=.env.production -r ts-node/register src/cli/dashboard-onboarding.ts prepare <私有目录> <原始名单>` 生成 `roster.json`。准备阶段保留姓名、组织、负责小组、已知手机号、可选的角色和用于对齐托管配置的飞书成员 ID，并记录目标 Supabase 项目。名单可用 `tenantRole` 指定 `tenant_admin`（组织管理员）或 `group_leader`（组长）。旧名单可以照常使用，新建员工档案默认是组长，重复导入未指定角色的名单会保留已有角色。发布前名单留在本机。

进入正式发版窗口后，发布人通过部署 SSH 将 `roster.json` 和本批核准的员工密码文件 `credentials.work.json`、管理员密码文件 `cakeadmin.work.json` 一并放入仅部署用户可访问的 `/data/cake/private/dashboard-onboarding/staff`（0700）。文件权限均为 0600。首批正式开户缺少对应的密码文件时，部署会在切换服务前提示补齐。中断后直接用服务器原目录重试。

发布脚本先核对账号表、认证方式和开户名单，再把 Stride 已确认的小组、Bot 和生效时间登记到蛋糕。旧服务处理完登记前的待回复消息后才切换。归属冲突或队列超时会中止切换，可用同一名单重试。新服务健康检查通过后先创建独立的 `cakeadmin`，再建立全部成员档案，再按已核实的手机号开通登录。账号管理只列出已注册的账号。缺手机号的成员先在原名册补齐并同步，管理员随后从「开通账号」办理。已注销的成员保留档案，批量初始化会跳过。上海智能体负责人归总部，上海自招员工只看上海自招团队，河南员工看整个河南中心。首次发布缺少名单会在切换前提示补齐。姓名或归属冲突需先核对，重复执行沿用已保存的密码和停用状态。

开户成功后，专用管理员的初始密码从 `cakeadmin.private.json` 私下交付给管理员保管人。总部从 `handoff.private.json` 核对本批实际新开的员工账号，按清单逐人交付。管理员回执为 `cakeadmin.ready.json`。员工完成回执 `complete.json` 只保留数量和批次摘要，交付完可移走密码文件并保留回执。
